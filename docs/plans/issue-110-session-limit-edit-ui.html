1요약

docs/plans/session-limit-and-home-utils.md §5 작업 E — 세션당 문제 수(_정보 탭 문제수 값)의 사용자 편집 경로를 완성하는 캡스톤 이슈다. 선행 A(#102)·B(#103)·C(#106)·D(#109)가 전부 머지되어 읽기(settings.sessionLimit)·쓰기(POST /api/settings)·상한 파라미터화·유틸 바가 이미 갖춰져 있다. 이 이슈는 그 부품들을 잇는 클라이언트 UI만 추가한다: 등록 화면(RegisterScreen) 상단에 문제수 필드를 두고, 홈 수정 메뉴에 "1회 문제 수 수정" 옵션을 더해 그 필드로 이동·포커스시킨다. Worker(worker/) 변경은 없다 — 쓰기 API는 이미 존재한다.

2현황 분석

선행 작업이 만든 부품과, 이 이슈가 아직 잇지 않은 빈틈:

  • src/lib/wordsApi.ts:41 fetchWords가 { profile, words, settings }를 반환하고, settings.sessionLimit은 이미 src/screens/HomeScreen.tsx:45에서 소비되어 세션 큐 상한에 쓰인다. RegisterScreen.tsx:68도 같은 fetchWords를 부르지만 지금은 words만 꺼내 쓰고 settings는 버린다.
  • worker/routes/settings.ts:33 handleSettingsPost가 이미 배선되어 POST /api/settings를 처리한다 — 요청 { sessionLimit }(정수 1~500 아니면 400, 문구는 worker/lib/settings.ts의 MIN_SESSION_LIMIT=1·MAX_SESSION_LIMIT=500 사용), 응답 { sessionLimit }. 그러나 클라이언트에 이 엔드포인트의 호출자가 없다 — src/lib/api.ts·registerApi.ts·wordsApi.ts 어디에도 postSettings 함수가 없다.
  • src/components/HomeUtilBar.tsx:66 menuItems는 [{ label: '단어 등록', onSelect: onNavigateRegister }] 하나뿐이다. 주석(6행)에 "1회 문제 수 수정"은 후속 작업(E) 소관이라 명시돼 있다. HomeUtilBar.test.tsx:58의 테스트가 "옵션은 '단어 등록' 하나뿐"임을 단언한다 — 이 이슈에서 이 단언이 깨져야 정상이다(2개로 갱신).
  • src/App.tsx:19,67,88 register 진입 경로가 onNavigateRegister: () => setScreen('register') 하나뿐이라, 어느 경로로 들어와도 RegisterScreen에 포커스 대상을 전달할 방법이 없다.
  • src/screens/RegisterScreen.tsx는 붙여넣기 → 확인 → 탭 선택 → 제출 흐름만 갖고 있다(44~325행). 상단에 문제수 필드가 들어갈 자리(RegisterHeader 바로 아래, 251행의 첫 register-field 위)가 비어 있다.
  • src/lib/registerApi.ts:21의 extractErrorMessage(비정상 응답의 {error} 본문 우선 추출)가 이미 존재하는 패턴이다 — POST /api/settings의 400 오류 문구("sessionLimit은 1~500 사이의 정수여야 합니다")를 그대로 보여주려면 같은 패턴이 필요하다.
  • docs/design-prd.md §3(71~86행)의 수정 메뉴 서술이 "메뉴 옵션은 현재 '단어 등록' 하나뿐이다 … '1회 문제 수 수정'은 플랜 §5 작업 E에서 추가되며, 그때까지 비활성 자리 표시도 두지 않는다"로 이 이슈의 완료를 이미 전제하고 있다 — 이 문장은 이 이슈에서 갱신되지 않으면 배포 후 거짓이 된다.
  • docs/PRD.md §9.3(273~292행)에는 문제수 필드 단계가 없다. §7.3(POST /api/settings 명세)은 이미 있다(#103에서 추가).
  • 이 레포에 RegisterScreen.test.tsx가 아직 없다(src/screens/HomeScreen.test.tsx만 화면 테스트 존재) — 이 이슈에서 신규 작성.

3설계

  • postSettings 위치: src/lib/api.ts에 추가한다(플랜 §4 파일 영향표가 이 파일을 지목) — postAnswer·postReviewFail과 같은 층위의 도메인 함수로 자연스럽다. 다만 오류 표시는 "Worker {error} 본문 우선"이 요구사항이라 registerApi.ts의 extractErrorMessage 패턴이 필요한데, api.ts가 registerApi.ts를 import하면 계층이 뒤집힌다(registerApi.ts가 api.ts의 소비자). 대신 같은 3~5줄짜리 순수 함수를 api.ts에 비공개로 하나 더 둔다 — 이미 HANZI_RE류의 "동일해야 함" 주석 붙은 중복을 레포가 허용해 온 관행과 같다.
  • 문제수 필드 위치: 별도 컴포넌트로 추출하지 않고 RegisterScreen 본문에 인라인 섹션으로 둔다(현재 필드 3개짜리 폼도 전부 인라인) — 상태 4개(sessionLimit·limitInput·limitSaveStatus·limitError)뿐이라 분리 이득이 적다.
  • "현재값 표시" 해석: 별도 읽기전용 텍스트 + 입력란 2개를 두지 않고, 숫자 입력란을 현재값으로 프리필하는 것으로 "표시"를 겸한다 — 입력란 하나가 이미 현재값을 보여주면서 바로 수정 가능한 표준 패턴이고, 별도 텍스트는 같은 값의 중복 표시라 정보 이득이 없다.
  • 검증 함수 위치: validateSessionLimit은 RegisterScreen.tsx 내부 비공개 함수로 둔다(registerValidation.ts의 validateNewTabName과 형태는 비슷하지만, 그 파일은 "등록 배치 검증"이 주제라 세션 설정 검증을 넣으면 파일 책임이 흐려진다). 컴포넌트 동작 테스트로 경계를 검증한다(HomeUtilBar 테스트 관행과 동일 — 순수 함수 단위 테스트가 아니라 상호작용 테스트).
  • 등록 플로우와의 독립성: 문제수 필드의 상태(limitInput 등)는 등록 배치 상태(text·confirmedText·submitPhase 등)와 완전히 분리된 useState 묶음으로 두고, handleSaveLimit과 handleSubmit은 서로의 상태를 읽거나 쓰지 않는다 — 이슈 완료 조건의 "필드 저장이 등록 배치에 영향 없음"을 상태 분리로 구조적으로 보장한다.
  • 포커스 배선: 모달 없이 같은 RegisterScreen으로 이동하는 설계(플랜 §3.5)라, "포커스 대상"은 진입 시점에 결정되는 불리언 하나(focusSessionLimit)면 충분하다. App.tsx에 registerFocusLimit 상태를 두고, navigateRegister(focusLimit) 헬퍼로 HomeScreen의 두 콜백(onNavigateRegister·신규 onEditSessionLimit)을 통일한다. 라우터 도입 등 구조 변경은 하지 않는다(플랜 §4 "구조 변경 없음" 명시).
  • 포커스 실행 시점: RegisterScreen은 wordsStatus가 ready가 되어야(즉 settings.sessionLimit을 알아야) 입력란이 실제 값으로 존재한다. useEffect를 wordsStatus에 걸고, 1회만 실행되도록 useRef 플래그로 가드한다(재시도 시 재포커스로 커서를 뺏지 않기 위함).
  • 기각한 대안: 모달/별도 화면 — 플랜 §7 Q7에서 소유자가 이미 기각(§3.5). 문제수 필드를 Dropdown.tsx처럼 별도 컴포넌트로 뽑는 안 — 재사용처가 없고 상태가 그 자리에서만 쓰여 분리 이득이 없음.

5리스크

리스크영향완화책
포커스 이펙트가 wordsStatus 변화마다 재실행되어 "다시 시도" 후 재포커스로 커서를 뺏음낮음 — 사용성 저하useRef 1회 실행 가드로 최초 ready 전환에만 반응
HomeUtilBar.test.tsx의 기존 "옵션 하나뿐" 단언을 못 찾고 놓치면 CI 실패중간 — 빌드 레드§4 단계 7에서 명시적으로 갱신 대상 지정, 전체 스위트 실행으로 확인
숫자 입력 type="number"가 브라우저마다 비정수(소수점) 입력을 허용해 클라 검증을 우회낮음 — 최종 강제는 Worker가 400으로 막음(§3.3)정규식(/^\d+$/) 기반 validateSessionLimit으로 문자열 단계에서 이미 비정수를 걸러 저장 버튼을 비활성화
등록 화면이 React.lazy라 Suspense 경계 안에서 신규 상태·이펙트가 초기 렌더 순서에 영향낮음기존 wordsStatus 게이트를 그대로 재사용해 로딩/에러 분기 구조를 건드리지 않음

6테스트 계획

  • api.test.ts postSettings: 성공 시 { sessionLimit } 반환 + Authorization 첨부 + JSON 바디 확인. 400 {error: "..."} 응답이면 그 메시지로 reject. 본문이 JSON이 아니면 상태 코드를 담은 폴백 메시지로 reject.
  • RegisterScreen.test.tsx — 문제수 필드: fetchWords mock의 settings.sessionLimit(예: 30)이 입력란 초기값으로 표시되는지. 저장 클릭 시 postSettings 호출 인자·성공 시 반영값 재표시+성공 문구. 경계값 0·501·"abc"(비정수) 입력 시 저장 버튼 비활성 + 오류 문구, 입력값은 그대로 유지됨. 저장 실패(mock 400) 시 오류 문구 표시 + 입력값 유지(초기화되지 않음).
  • RegisterScreen.test.tsx — 독립성: 문제수 필드를 수정/저장해도 붙여넣기 textarea·확인·탭 선택·제출 버튼 상태(canSubmit 등)가 변하지 않음. 반대로 등록 배치를 진행 중이어도 문제수 필드 저장이 정상 동작.
  • RegisterScreen.test.tsx — 포커스: focusSessionLimit prop이 true면 wordsStatus가 ready가 된 뒤 문제수 입력란이 document.activeElement가 됨. prop이 false/미지정이면 포커스 이동 없음.
  • HomeUtilBar.test.tsx: 수정 메뉴 옵션이 정확히 ["단어 등록", "1회 문제 수 수정"] 순서로 렌더. 두 번째 항목 클릭 시 onEditSessionLimit 호출 + onNavigateRegister 미호출 + 메뉴 닫힘.
  • HomeScreen.test.tsx: 기존 setup에 onEditSessionLimit mock 추가해도 기존 단언(단어 등록·프로필 전환 경로) 무수정 통과 확인.
  • 기준선: npm run test 전체 스위트(현재 380개 통과, 이 워크트리에서 npm install 후 확인) — 이번 변경으로 늘어난 개수 외에 기존 테스트가 깨지지 않는지.
