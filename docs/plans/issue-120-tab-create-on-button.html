등록 화면 '생성' 버튼이 실제로 시트에 새 탭을 만들어야 한다

damdam6/vocabulary-study 브랜치 feat/120-tab-create-on-button ← main 라벨 enhancement 2026-07-28

1요약

#118의 탭 우선 흐름에서 "생성" 버튼은 클라이언트 선택지 추가만 하고 실제 구글 시트 탭 생성은 제출 시 createTab에 남겨뒀다. 소유자 확정(2026-07-28)으로 (b)안을 채택 — 생성 버튼을 누르면 그 시점에 POST /api/tabs로 시트에 실제 탭이 생긴다(빈 탭은 감수, v1 §8 Q5 결정 공식 뒤집기). Worker에 라우트를 신설하고 register의 탭 생성 로직을 공통 lib로 추출해 재사용하며, 클라이언트는 서버 성공 후에만 선택 전환하고 제출 페이로드에서 createTab을 제거한다. 문서 3곳 (PRD §7.3 · design-prd §6 · word-registration-system §8 Q5)을 함께 개정한다.

2현황 분석

  • 클라 생성 버튼: src/screens/RegisterScreen.tsx:197-205의 handleCreateTab이 로컬 상태 localTabs에만 이름을 추가하고 selectedTab을 전환한다 — 서버 호출 없음. 선검증은 src/lib/registerValidation.ts:167-172의 validateNewTabName(트림 후 빈 값·_ 시작 차단).
  • 제출 시 탭 생성: src/screens/RegisterScreen.tsx:211이 createTab = !tabs.includes(effectiveTab)를 계산해 registerWords 바디에 실어 보내고, Worker worker/routes/register.ts:58-74가 그때 탭을 만든다 — 기존 단어 탭이 있으면 첫 탭 1:1 헤더 복사, 0개면 DEFAULT_TAB_HEADERS[contentType] 부트스트랩(#95) 후 addSheet + A1 헤더 PUT.
  • 기존 /api/tabs: worker/routes/tabs.ts는 GET 핸들러(handleGetTabs)뿐이고 worker/index.ts:73-80도 GET만 배선한다. 탭 목록은 worker/lib/words.ts:12-15의 getWordTabTitles(_ 접두 제외)가 공급.
  • 이름 규칙 원본: worker/lib/register.ts:99-111의 normalizeTabName — 비문자열·트림 후 빈 값·_ 시작을 400 사유 문자열로 반환. 이 lib 파일은 헤더 주석에 "Sheets 호출 없이 순수 함수"라고 계약을 못박고 있다(worker/lib/register.ts:3).
  • 클라 API 레이어: src/lib/registerApi.ts — apiFetch 경유 + 비정상 응답의 Worker {error} 본문 우선 추출(extractErrorMessage) 패턴. RegisterRequest.createTab?: boolean 필드 보유.
  • 테스트 지형: Worker는 "테스트 파일 = isolate" 규약(프로필 구성 다이제스트 캐시가 isolate당 고정, worker/test-utils.ts) — 폴백(zh) 구성은 worker/routes/tabs.test.ts·register.test.ts, zh+generic 2프로필 구성은 register.generic.test.ts·index.sheet-isolation.test.ts가 선례. 클라는 src/screens/RegisterScreen.test.tsx의 #118 스위트가 생성 버튼 동작(로컬 확정·createTab 바디)을 고정 중.

3설계

  • 공통 lib 추출 — worker/lib/tabs.ts 신설: createWordTab(env, sheetId, tab, wordTabs, contentType) — wordTabs 0개면 DEFAULT_TAB_HEADERS[contentType], 아니면 첫 탭 1:1 헤더 복사 → addSheet → A1 PUT. register 라우트의 인라인 블록(register.ts:65-73)을 이 함수 호출로 대체해 두 경로가 한 구현을 공유한다. 기각: worker/lib/register.ts에 두기 — "Sheets 호출 없는 순수 함수" 모듈 계약 위반. worker/lib/words.ts에 두기 — 읽기 전용 조회 모듈에 쓰기 로직 혼입.
  • POST /api/tabs: worker/routes/tabs.ts에 handleCreateTab 추가 — JSON 파싱 실패·비객체 400 → normalizeTabName(body.name) 재사용(오류 문자열 그대로 400) → getWordTabTitles 대조: 포함이면 생성 없이 {name, created: false}(멱등, "그 탭을 선택하라"), 아니면 createWordTab 후 {name, created: true}. worker/index.ts에 POST 분기 배선 + 500 캐치(failed to create tab) — 기존 라우트 관례 동일. 인증·프로필 해석은 기존 /api/ 공통 블록이 그대로 적용.
  • 클라 API: src/lib/registerApi.ts에 createTab(name) 추가 — POST /api/tabs, 실패 시 extractErrorMessage로 Worker {error} 우선 throw. RegisterRequest에서 createTab 필드 제거(클라는 더 이상 보내지 않음 — Worker의 createTab 경로 자체는 계약 호환으로 유지, 제거는 비범위).
  • 등록 화면: handleCreateTab을 서버 호출로 전환 — 호출 중 'creating' 상태로 버튼 비활성("생성 중…"), 성공 시 응답 name을 tabs 상태에 편입(중복 없이)하고 선택 전환 + 입력 초기화, 실패 시 입력란 아래 오류 문구(Worker 본문 우선)·입력값 유지, 입력을 고치면 오류 클리어(문제수 필드와 같은 패턴). localTabs 상태는 통째로 제거 — 생성된 탭은 항상 실존하므로 서버 목록 상태 하나로 충분하고, 제출의 createTab 계산도 사라진다. 파일 상단 #118 주석 블록 개정.

5리스크

리스크영향완화책
addSheet 성공 후 A1 헤더 PUT 실패(부분 생성) 헤더 없는 빈 탭이 남음 — 재시도하면 멱등 경로(created:false)라 헤더가 채워지지 않음 register의 기존 createTab 경로와 동일 순서·동일 위험(신규 악화 없음). 등록은 A2부터 쓰므로 기능 파손 없음. 빈 탭 감수는 이슈가 명시적으로 승인한 트레이드오프.
배포 전파 윈도우 중 구버전 Worker(POST /api/tabs 없음) + 신버전 클라 혼재 생성 버튼이 404(비JSON 본문) 오류 클라 오류 표시가 폴백 문구(HTTP 상태 포함)로 안내하고 입력이 유지돼 재시도로 회복. Worker+assets 단일 배포라 윈도우는 짧다(#23 버전 헤더 관측 가능).
클라 tabs 상태 편입과 서버 목록의 정합 드롭다운·중복 대조가 어긋날 수 있음 생성 성공 시점에 탭이 시트에 실존하므로 로컬 편입 = 서버 재조회와 동일 결과. 중복 대조는 allWords의 탭 필터라 새 탭(단어 0)에선 자연히 빈 집합.
normalizeTabName 재사용 시 비문자열 오류 문구가 "tab은 문자열이어야 합니다"로 필드명(name)과 불일치 직접 API 호출자에게만 문구가 다소 어긋남(클라는 항상 문자열 전송) 이슈가 "normalizeTabName 재사용"을 명시 — 규칙·문구 단일 원본 유지가 우선. 실사용 경로 영향 없음.
