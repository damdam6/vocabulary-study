리스크영향완화책
StrictMode 공개 게이트실제 앱의 모드1 공개·자동 음성 유실 가능src/main.tsx가 StrictMode를 사용한다. Mode1Card :104 cleanup의 true 설정을 먼저 통합 테스트로 재현하고 최소 수명 수정 후 빠른 판정·실제 언마운트도 재검증한다. 현재는 정적 조사 가설이며 테스트 재현 미실행이다.
더블이 결론을 미리 구현상수 MP3/상수 hit가 저장·직렬화 결함을 숨김버킷은 put으로 받은 바이트만 보관하고 매번 새 stream을 만든다. 실제 route/service/storage/provider adapter·controller/transport를 대체하지 않는다. HTTP 파서는 실제 Response를 읽는다.

기록 callback의 flush성공/실패 시 중간 요청 수 차이를 채점 회귀로 오판고정 판정 transcript와 최종 효과를 비교하고 C7에서 실제 App callback을 별도 검증한다. localStorage·handler·flushing 완료를 케이스마다 정리한다.

실환경 오인·범위 확대모의 통과를 R2·음질·모바일 출시 승인으로 오인#149 준비는 비의존. bucket/secret/배포/청취/실측은 수행하지 않고 출시 대기로 적는다. 구조적 redesign은 재현·영향·관련 소유 이슈만 findings로 인계한다.

6테스트 계획

  • S1 — 첫 생성·조건부 저장·새 세션 재사용. 짧은 A열+B열과 200자 문장+빈 B열을 매개변수화한다. 첫 controller 공개 → POST 인증 → get null → 실제 Qwen adapter/MP3 검증 → put 1회(If-None-Match: *) → GENERATED/SAVED → 정확한 Blob 바이트·play 1회. ctx.drain 뒤 controller/cache를 dispose하고 새로운 controller/cache와 새 요청 ctx로 다시 공개한다. 버킷 Map만 유지하며 STORED/PRESENT, 동일 바이트, 추가 put/provider 0을 확인한다. 두 번째 provider는 실패하도록 설정해 hit가 upstream 가용성과 독립임을 보인다. 이 테스트의 “새 세션”은 새 클라이언트 자원이며 실제 기기/R2 증거는 아니다.
  • S2 — 조회 장애. get이 reject하면 실제 라우트 503 tts_storage_unavailable, socket/합성/put/play 0. 실패를 miss로 취급하지 않는다. 상세 timeout·손상 조합은 기존 service/storage 테스트로 연결한다.
  • S3 — 쓰기 장애와 사용 가능한 생성 음성. 정상 합성 뒤 put reject → GENERATED/UNCONFIRMED 200. 실제 ttsApi가 해당 진단과 Blob을 받아 native Audio 더블의 play까지 도달한다. 같은 세션 수동 재생은 추가 요청 없이 같은 Blob을 재사용한다. ctx.tasks를 drain하고 실패 observation이 회수되며 저장 성공으로 기록되지 않음을 확인한다. 저장 대기 초과/늦은 성공은 service.test.ts:149의 기존 실행 증거로 연결한다.
  • S4 — 제공자 인증과 앱 인증의 분리. 정상 앱 인증 + provider Upgrade 401 → 공개 503, WWW-Authenticate 없음. 실제 apiFetch를 통과해도 저장 앱 인증·프로필 유지, unauthorized callback 0, put/play 0. 잘못된 앱 인증은 실제 401 → 인증 삭제·callback 1, R2/provider 0의 대조를 둔다. 테스트용 고정 값만 사용한다.
  • C1 — 모드1 실제 연결. 앞면은 요청 0. 계산 style을 0이 아닌 transform으로 제어하고 플립 때 요청 1; 응답을 먼저 완료해도 play 0; 자기 transform 완료 후 1. StrictMode와 중복 event/상태 재렌더에서도 1이다. 로딩 중 클릭은 요청 1로 합쳐지고, 준비 후 5회 replay는 한 Audio에서 이전 source를 해제하며 기록/판정/추가 fetch를 만들지 않는다. 별도 deferred 응답 사례에서 플립 직후 O/X로 이동한 뒤 늦은 응답과 fallback을 풀어도 이전 play 0, 학습은 즉시 다음으로 간다.
  • C2 — 모드2 실제 연결. 일반 오답과 공백 입력 오답을 각각 제출한다. 결과 DOM에 정답이 보인 뒤에만 실제 fetch가 시작되고 JSON text는 사용자의 답이 아닌 word.hanzi이다. 병음 없음도 허용한다. StrictMode에서 공개당 요청/play 1, 수동 버튼은 기록·제출·다음 이동 0. 즉시 정답은 TTS 요청 0이고 answer 기록과 진행은 즉시 수행한다.
  • C3 — 숨김·이탈·완료. 재생 중 visibilitychange hidden에서 pause → src 제거 → URL revoke를 관찰한다. visible 복귀만으로 fetch/play가 증가하지 않고 수동 클릭으로만 재생한다. 준비 중 pagehide/종료는 실제 transport signal을 abort하고 늦은 응답을 풀어도 play 0이다. 마지막 문제 빠른 판정에서 완료 feedback animation을 아직 끝내지 않아도 이전 오디오는 정지한다. unmount 뒤 timer·listener·활성 URL이 남지 않는다.
  • C4 — 실제 App 로그인 복귀. 고정 words 응답으로 Home의 학습 시작 버튼부터 Study로 들어간다. provider 오류를 나타내는 공개 503에서는 로그인 전환/인증 삭제 없이 판정 가능하다(S4가 실제 서버 변환을 보증). 별도 앱 401 응답에서는 실제 unauthorized handler → LoginScreen 표시 → Study unmount → 요청 취소·오디오 해제를 검증한다. 로그인 뒤 새 세션이 옛 Blob/자동 공개 상태를 이어받지 않는지도 확인한다.
  • C5 — generic/off/구 서버. 실제 Home/App 경로에서 generic, zh+enabled:false, tts 필드 없는 응답을 매개변수화한다. 버튼/fetch/play 0으로 학습·완료가 정상이며 capability가 localStorage의 다른 값으로 덮이지 않는다. 상세 words 포맷 오류는 wordsApi 선행 테스트를 재사용한다.
  • C6 — 정상/실패/off 동등 회귀. 큐를 q1 모드1 학습 정답, q2 모드1 학습 오답, q3 모드2 복습 빈 오답, q4 모드2 학습 정답으로 고정한다. q3는 다음 클릭 전까지 머무르고 최종 통계는 {correct:2, wrong:2}, 큐 분모는 4, 재출제 없음이다. 예상 기록은 q1/q4 answer와 q3 review-fail뿐이며 timestamp·mode·isReview·profileId를 직접 명시한 기대값과 비교한다. TTS 200(UNCONFIRMED 포함), 503 실패, off 각각에서 같은 결과여야 한다. 기록 HTTP를 모두 성공시키는 실행과 고정된 answer/review-fail을 5xx로 만드는 실행을 구분해 실제 localStorage 재시도 엔트리도 비교한다. 조용한 TTS 실패는 어떤 큐 항목도 추가하지 않는다.
  • C7 — 기존 API 성공 flush. 실제 App에서 진입 flush가 끝난 뒤 현재 프로필의 기존 answer 1건을 적재한다. TTS 200은 실제 성공 handler를 거쳐 그 answer를 1회 재전송하고 큐에서 제거한다. TTS 자체는 적재되지 않는다. 503/off에는 같은 시점의 flush가 없으며 이후 공통 성공 API/flush 조건을 동일하게 주면 같은 기록/최종 큐가 된다. 따라서 중간 HTTP 횟수의 단순 동등 비교로 정상 동작을 실패 처리하지 않는다.
  • 실행 순서. 개발 중 npm test -- worker/tts.integration.test.ts src/screens/StudyScreen.tts.integration.test.tsx. 대표 결함 수정 시 해당 기존 카드/서비스 테스트도 실행한다. 완료 시 npm test, npm run lint, npm run build, git diff --check. 실행 시각·HEAD·파일/테스트 수·exit code와 실패/경고를 verification.md에 기록한다. 테스트 이름은 S1–S4/C1–C7 식별자와 연결하고 예상 횟수와 아직 미실행인 항목을 섞지 않는다.
