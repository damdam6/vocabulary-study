세션 설정 — Worker '_정보' 탭 읽기 + words 응답 settings 동봉

damdam6/vocabulary-study 브랜치 feat/102-info-tab-settings-read ← main 라벨 enhancement 2026-07-28

1요약

세션당 문제 수가 클라이언트 상수 60으로 고정돼 있어 시트(프로필)마다 학습량을 다르게 줄 수 없다. 이 이슈는 그 설정의 읽기 경로만 만든다 — 스프레드시트 안 '_정보' 탭(A열 키 / B열 값)을 파싱하는 순수 파서 worker/lib/settings.ts를 신설하고, GET /api/words 응답 최상위에 settings: { sessionLimit } 블록을 동봉한다. 읽기는 관대하게 — 탭 없음·키 없음·비정수·범위 밖은 전부 기본 60으로 폴백해 words 호출을 절대 실패시키지 않는다. 탭 이름이 _로 시작하므로 기존 "_ 접두 = 학습 제외" 규약(PRD §4.1)에 걸려 words 출제·tabs 목록·등록 대상에서 이미 자동으로 빠진다 — 제외용 코드 변경이 0이다. 쓰기 API는 작업 B, 클라이언트 소비는 작업 C 소관으로 이 PR 범위 밖이다.

2현황 분석

기준 문서는 docs/plans/session-limit-and-home-utils.md §3.1·§3.2(2026-07-28 확정, Q1~Q7 소유자 확인)이고, 이 이슈는 그 문서 §5의 작업 A다. B·C·D와 병렬 루트이며 캡스톤 E가 네 작업 모두에 의존한다.

현재 상한 60이 사는 곳 (클라이언트 — 이번 범위 밖)

  • src/lib/sessionQueue.ts — export const SESSION_CAP = 60. 복습 대기 "오래된 순 최대 60개" 컷과 세션 총 상한이 같은 상수를 공유한다.
  • src/lib/homeStats.ts — 같은 이름의 로컬 상수 60이 중복돼 있다.
  • 두 지점의 파라미터화·상수 일원화는 작업 C 소관 — 이 PR은 src/를 건드리지 않는다.

Worker 읽기 경로

  • worker/routes/words.ts:17-34 — getWordTabTitles로 학습 탭 목록을 얻고, 탭별 A2:F를 Promise.all로 읽어 { fetchedAt, words, profile }을 반환한다. 응답 최상위 블록을 추가할 자리가 여기다.
  • worker/lib/words.ts:12-15 — getWordTabTitles가 titles.filter((title) => !title.startsWith("_"))로 _ 접두 탭을 제외한다. words·tabs·등록 헤더 원본 선택이 이 한 함수를 공유하므로, '_정보' 탭은 여기서 이미 걸러진다.
  • worker/lib/register.ts:107 — 등록 대상 탭 이름이 _로 시작하면 차단한다(§4.1과 모순 방지). '_정보'를 등록 대상으로 지정하는 경로도 이미 막혀 있다.
  • worker/lib/sheets.ts:39-48 — getValues(env, sheetId, tab, range)는 빈 범위를 []로 돌려주고, 뒤쪽 빈 셀은 API가 생략하므로 행 길이가 들쭉날쭉할 수 있다(파서가 감안해야 함).
  • worker/lib/sheets.ts:131-150 — 비 2xx는 SheetsApiError로 throw된다. 없는 탭을 읽으면 400(Unable to parse range)이 오는데, worker/lib/words.ts:60-66·88-92가 이미 그 400을 "찾지 못함"으로 흡수하는 선례를 만들어 뒀다 — settings 파서도 같은 방식을 따른다.
  • worker/index.ts:45-52 — /api/words는 예외를 잡아 500으로 바꾼다. settings 읽기 실패가 여기까지 올라가면 words 전체가 죽으므로, 폴백은 반드시 라우트 아래에서 끝나야 한다.
  • worker/index.ts:38-43 — /api/health는 profile만 싣는다. 플랜 §3.2에 따라 settings는 넣지 않는다(로그인 시점에 불필요).

계약·테스트 기준선

  • worker/index.sheet-isolation.test.ts:103-130 — words 배열 형태를 toEqual로 못 박고 있다. 최상위에 필드를 더하는 것이므로 이 단언은 그대로 통과한다.
  • 같은 파일 :86-95 — 호출된 모든 Sheets URL이 인증된 프로필의 sheetId만 담는지 전수 검사한다. '_정보' 읽기도 profile.sheetId로 나가야 이 테스트를 통과한다.
  • 같은 파일 :54-77의 목은 알 수 없는 탭 조회에 { values: [] }를 돌려준다 → 기존 스위트는 자연히 "탭 없음 → 60" 경로를 타게 된다.
  • docs/PRD.md §4.1(_ 접두 제외)·§6.1("상한 60문제")·§7.3(GET /api/words 응답 예)이 개정 대상이다. docs/PRD-general.md는 profile 블록만 정의하므로 이번 개정 대상이 아니다.

3설계

'_정보' 탭 계약 (플랜 §3.1 — 소유자 확정)

  • 탭 이름은 '_정보'. 기존 _ 규약 재사용이 핵심 — 제외·차단 특례 코드가 0이다. (비접두 '정보'로 만들면 단어 탭으로 스캔·출제된다.)
  • 헤더 행 없음. A열 = 키, B열 = 값. 행 위치 자유 — A열에서 키를 트림 후 정확 일치로 탐색해 그 행의 B열을 읽는다.
  • 모르는 키는 무시(전방 호환). 이번에 인식하는 키는 문제수 하나.
  • 읽기는 관대: 정수 1~500만 채택하고, 그 외(탭 없음·키 없음·빈칸·비정수·0·501·음수·소수)는 기본 60 폴백.

모듈 경계 — 순수 파서 + 얇은 fetch 래퍼

신설 worker/lib/settings.ts를 두 층으로 나눈다. 이슈가 요구하는 테스트(정상·행 위치 자유·이상값 폴백·모르는 키 무시)는 전부 시트 호출 없이 첫 층에서 검증된다.

  • DEFAULT_SESSION_LIMIT = 60 · SESSION_LIMIT_KEY = "문제수" · SETTINGS_TAB = "_정보" · SETTINGS_RANGE = "A:B" — 상수를 여기 한곳에 모아 작업 B(쓰기 API)가 그대로 재사용한다.
  • parseSettings(rows: string[][]): SheetSettings — 순수 함수. A:B 값 배열에서 키 행을 찾아 { sessionLimit }을 만든다. 짧은 행(B열 생략)·공백·중복 키(첫 유효값 우선)를 전부 감당한다.
  • readSettings(env, sheetId): Promise<SheetSettings> — getValues로 '_정보'!A:B를 1회 읽어 파서에 넘긴다. 어떤 예외도 밖으로 내보내지 않고 기본값으로 흡수한다(400·5xx·네트워크 모두). "없는 탭 = 400"을 흡수하는 findWordRow(worker/lib/words.ts:60-66)의 선례를 넓힌 형태.

words 응답 합성 (플랜 §3.2)

  • worker/routes/words.ts에서 탭 제목 조회·단어 읽기와 병렬로 settings를 읽는다 (Promise.all — 직렬 왕복을 추가하지 않는다).
  • 응답: { fetchedAt, words, profile, settings: { sessionLimit } }. words·profile 형태 불변.
  • /api/health·/api/tabs는 손대지 않는다.

기각한 대안

  • 전용 GET /api/settings — 홈 진입마다 왕복이 하나 더 는다. words 동봉은 profile 블록의 선례를 따른다(플랜 §8).
  • /api/health에도 동봉 — 로그인 시점에는 불필요하고, 상한이 두 응답에 중복 정의되면 어느 쪽이 최신인지 모호해진다.
  • 읽기도 엄격(이상값 → 500) — 손으로 고친 시트의 오타가 학습 전체를 멈춘다. 읽기 관대·쓰기 엄격(작업 B)이 확정 결정이다.
  • '정보' 탭 예약 특례 — words·tabs·register 세 곳에 제외 코드를 새로 넣어야 한다. Q1에서 기각됐다.
  • 파서를 lib/words.ts에 얹기 — 작업 B의 쓰기 경로가 같은 상수·행 탐색을 필요로 하므로 전용 모듈이 맞다.

4작업 단계

  1. worker/lib/settings.ts 신설 — 상수 + 순수 파서 parseSettings. A:B 행 배열에서 A열을 트림해 문제수와 정확 일치하는 행을 찾고, B열을 트림 후 정수 판정 (Number.isInteger + 1~500 범위)한다. 불일치·부재·짧은 행은 DEFAULT_SESSION_LIMIT(60). 모르는 키 행은 그냥 건너뛴다. 메모: 정수 판정에 Number.isInteger만 쓰면 "0x1E"·"1e2" 같은 표기가 통과하므로 /^\d+$/로 숫자 문자열 형태를 먼저 강제한 뒤 범위를 본다. 중복 키는 "첫 유효값"이 아니라 첫 행 우선 — 규칙이 예측 가능하다. worker/lib/settings.ts
  2. 같은 파일에 readSettings(env, sheetId) 추가 — 시트 1회 읽기 + 전 예외 흡수. getValues(env, sheetId, "_정보", "A:B") 결과를 파서에 넘기고, try/catch로 모든 실패(없는 탭 400·권한 403·5xx·네트워크)를 기본값으로 흡수한다. 예외 삼킴이 디버깅을 가리지 않도록 console.warn 한 줄을 남긴다(worker/index.ts의 console.error 관용 따름). worker/lib/settings.ts, worker/lib/sheets.ts(읽기만)

5리스크

리스크영향완화책
settings 읽기 실패가 /api/words 전체를 500으로 떨어뜨림 치명 — 설정 오타 하나로 학습 불가 readSettings가 모든 예외를 삼키고 60을 반환. 라우트에서 await 되기 전에 이미 흡수됨. "읽기 실패 → 200 + 60" 테스트로 못 박는다.
'_정보' 탭이 단어 탭으로 스캔돼 출제됨 높음 — 설정 행이 문제로 나옴 worker/lib/words.ts:14의 _ 필터가 이미 제외한다. 신규 코드 없이 회귀 테스트로 증명 ('_정보'가 있는 시트의 words 응답에 그 탭 항목이 없음).
시트 읽기 1회 추가로 words 응답 지연 낮음 탭 제목 조회와 Promise.all 병렬 — 직렬 왕복이 늘지 않는다. 플랜 §3.2가 비용 1회를 이미 허용.
기존 words 테스트가 응답 필드 추가로 깨짐 중간 단언이 body.words·body.profile에 국한돼 최상위 추가는 안전 (index.sheet-isolation.test.ts:103·138). 테스트 무수정 통과가 완료 조건.
구 클라이언트가 새 필드를 만나 오동작 낮음 클라는 아직 settings를 읽지 않는다(작업 C). 미사용 필드는 무시된다 — 플랜 §5의 "A 단독 배포 안전".
범위 이탈(쓰기 API·클라 파라미터화까지 손댐) 중간 — 리뷰 비대·작업 B/C와 충돌 src/와 POST /api/settings는 이 PR에서 건드리지 않는다. 완료 조건에 명시.

6테스트 계획

  • 파서 정상 — [["문제수","30"]] → sessionLimit: 30.
  • 행 위치 자유 — [["메모","…"],["버전","2"],["문제수","25"]] → 25.
  • 모르는 키 무시 — 인식하지 않는 키가 섞여도 문제수만 반영, 예외 없음.
  • 공백 트림 — [[" 문제수 "," 30 "]] → 30.
  • 경계 채택 — 1 · 500 → 그대로. 경계 밖 — 0 · 501 · -5 → 60.
  • 비정수 — "삼십" · "30.5" · "" · B열 누락(짧은 행) → 60.
  • 탭/키 없음 — [] · [["메모","x"]] → 60.
  • words 동봉 — '_정보'에 문제수|30이 있는 시트 → 응답 settings.sessionLimit === 30.
  • words 폴백 — '_정보' 탭이 없는 시트 → 200 + sessionLimit: 60.
  • 읽기 실패 내성 — '_정보' 조회에 400/500을 돌려주는 목 → words는 여전히 200, sessionLimit: 60, words 정상.
  • '_정보' 자연 제외(회귀) — '_정보' 탭이 있는 시트의 words 응답에 tab: "_정보" 항목이 하나도 없고, GET /api/tabs 목록에도 없다.
  • 시트 격리 — settings 읽기를 포함한 모든 Sheets URL이 인증 프로필의 sheetId만 포함.
  • 기존 스위트 무수정 통과 — npm test 전체 green (특히 index.sheet-isolation.test.ts의 words 형태 단언).
  • 정적 검사 — npm run lint(oxlint) · npm run build(tsc -b + vite build) green.
