1요약

등록 일반화 플랜(docs/plans/registration-generalization.md §5 작업 D, 마지막 스위치)의 실행 이슈다. 선행 작업 A(#94)·B(#95)·C(#96)가 모두 머지되어 Worker와 등록 화면이 generic 콘텐츠를 처리할 수 있으므로, 이제 홈 화면의 "단어 등록 ›" 링크를 막고 있던 contentType === "zh" 조건만 제거하면 된다. 코드 변경은 HomeScreen.tsx 한 줄(조건 제거)뿐이고, 등록 화면·검증·Worker 로직은 건드리지 않는다. 나머지 작업은 docs/design-prd.md §3(홈 화면 등록 링크 서술)과 §6(등록 화면 contentType 분기 — #96에서 이미 구현됐지만 문서가 아직 zh 전제로 남아 있음)을 실제 구현에 맞게 개정하는 것이다.

2현황 분석

홈 화면 등록 링크 조건 (#78의 잔재)

  • src/screens/HomeScreen.tsx:140-145 — 등록 링크가 {profile?.contentType === "zh" && (<button …>단어 등록 ›</button>)}로 감싸여 있다. 주석(140행)도 "zh 프로필 전용(#78)"이라고 못 박아 두었다. 이 조건 하나가 generic 프로필의 등록 진입을 막는 유일한 지점이다.
  • 이 블록은 status(loading/error/ready) 조건 밖에 있어 로딩·에러 상태와 무관하게 평가된다 — 조건을 제거해도 "오늘 학습 상태와 무관하게 항상 노출"이라는 기존 배치 규칙(§3 서술)은 그대로 유지된다.
  • profile state는 getStoredProfile()(src/lib/api.ts:41)로 초기화되고, fetchWords() 성공 시(HomeScreen.tsx:37-43)에만 갱신된다 — 조건 제거는 이 흐름에 영향 없다.

등록 화면은 이미 generic을 처리한다 (#96, 문서만 안 따라감)

  • src/lib/contentLabels.ts:33-43 — registerTableHeaders(contentType)는 zh일 때 {headword:"한자", note:"병음", meaning:"뜻"}, 그 외(generic)엔 {headword:"표제어", note:"보조 표기", meaning:"뜻"}를 반환한다. registerPlaceholder(contentType)는 zh 전용 hanzi/pinyin/meaning JSON 예시와 generic 전용 term/note/meaning(+"contentType":"generic") JSON 예시를 각각 반환한다.
  • src/screens/RegisterScreen.tsx:236이 registerPlaceholder(contentType)를 textarea placeholder로, src/screens/RegisterTable.tsx:21-30이 registerTableHeaders(contentType)를 테이블 헤더로 이미 사용 중이다 — §6 개정은 이 실제 동작을 문서화하는 것뿐, 코드 변경이 필요 없다.
  • src/App.tsx:88 — RegisterScreen은 getStoredProfile()?.contentType ?? 'zh'를 내려받는다. 등록 링크가 열린 뒤에도 이 배선은 변경 불필요.

design-prd.md의 낡은 서술

  • docs/design-prd.md:82 — "단어 등록 링크: contentType: "zh" 프로필에서만 노출. generic 프로필은 숨김 (PRD-general §7 — 등록 파이프라인이 중국어 전제라 일반 콘텐츠엔 아직 미제공)." → 선행 작업이 모두 머지된 지금 사실이 아니다.
  • docs/design-prd.md:83 — 프로필 전환 링크 위치 서술에 "(등록 링크가 숨겨진 프로필에서는 시작 버튼 바로 아래)"라는 분기 문구가 있다 — 등록 링크가 항상 노출되면 이 분기 자체가 없어져 정리가 필요하다.
  • docs/design-prd.md:143-156(§6) — "근거 목업 없음 — 학습 플로우와 달리 이번에 신규 설계"라는 헤더 인용은 유지하되, 본문에 zh/generic 라벨·placeholder·테이블 헤더 분기가 전혀 서술돼 있지 않다(#96 구현 기준 미반영).
  • docs/design-prd.md:191-205(§10 이슈 매핑) — #78 행이 "등록 링크 zh 조건부"라고 적어 두어 이번 변경과 모순된다.

테스트 하네스 현황

  • 리포에 React 컴포넌트 테스트 하네스가 없다(src/lib/contentLabels.ts:1-6 주석이 이유를 명시 — 분기 로직을 lib로 뽑아 vitest로만 고정하는 관행). HomeScreen 전용 테스트 파일은 존재하지 않는다 (src/lib/homeStats.test.ts만 있음). 완료 조건의 "HomeScreen 관련 기존 테스트 통과"는 곧 전체 npm test(vitest run) 스위트가 계속 초록임을 뜻한다.

3설계

선택한 설계: 코드에서는 HomeScreen.tsx의 조건부(profile?.contentType === "zh" &&)를 제거하고 버튼을 무조건 렌더링한다 — 다른 렌더 조건(로딩/에러 무관 항상 노출)은 그대로 둔다. 이슈가 명시한 대로 등록 화면·검증·Worker 로직은 건드리지 않는다(이미 #96·#95에서 generic을 처리하도록 배선이 끝났다).

문서는 실제 구현(#96)을 뒤늦게 반영하는 것이므로, §6에 zh/generic 분기표를 신설해 §4.6과 같은 형식(표 + "미지정은 대체 문자열이 아니라 속성 자체를 생략한다는 뜻" 같은 원칙 서술)으로 정리한다 — 이 리포에서 이미 검증된 패턴을 §6에도 적용해 문서 스타일 일관성을 유지한다.

기각한 대안

  • 등록 링크 조건을 profile?.contentType === "zh" || profile?.contentType === "generic"처럼 명시적 화이트리스트로 남기는 안 — 세 번째 콘텐츠 타입이 추가될 때마다 또 고쳐야 해서 이슈가 요구한 "조건 제거"(전 프로필 노출)의 취지에 어긋난다. ContentType이 현재 "zh" | "generic" 두 값뿐이라 무조건 노출과 결과가 동일하면서 더 단순하다.
  • §6을 §4.6처럼 별도 하위 절(예: "6.1 콘텐츠 타입 분기 정리")로 쪼개는 안 — §6 전체가 아직 그리 길지 않고 분기 대상이 3개 항목(라벨·placeholder·테이블 헤더)뿐이라, 별도 소절 없이 표 하나로 §6 본문에 붙이는 편이 간결하다. §4.6은 zh/generic 차이가 §4.1~4.3 세 군데에 흩어져 있어 별도 정리 절이 필요했던 경우였다.

4작업 단계

  1. 홈 화면 등록 링크의 contentType === "zh" 조건을 제거하고 버튼을 무조건 렌더링한다. 위 주석 문구("zh 프로필 전용(#78)")도 "전 프로필 노출(#100)"로 갱신한다. 완료. src/screens/HomeScreen.tsx
  2. design-prd §3 "단어 등록 링크" 불릿을 "전 프로필 노출"로 개정하고, 개정 근거로 등록 일반화 플랜(§5 작업 D)과 선행 이슈 #94·#95·#96 포인터를 남긴다. "프로필 전환 링크" 불릿에서 "(등록 링크가 숨겨진 프로필에서는 시작 버튼 바로 아래)" 분기 문구를 제거한다(등록 링크가 항상 있으므로 위치가 고정됨). 완료. docs/design-prd.md (§3, 약 82-83행)
  3. design-prd §6에 zh/generic 분기표를 신설한다 — contentLabels.ts의 registerTableHeaders(테이블 헤더: 한자/병음/뜻 ↔ 표제어/보조 표기/뜻)와 registerPlaceholder(textarea placeholder: zh는 hanzi/pinyin/meaning 예시, generic은 "contentType":"generic" 포함 term/note/meaning 예시) 실제 반환값을 그대로 문서화한다. #96 실구현 기준. 완료. docs/design-prd.md (§6, 약 143-156행)
  4. design-prd §10 이슈 매핑 표에서 #78 행의 "등록 링크 zh 조건부" 문구를 정정하고, #100 행을 신설해 §3·§6 본문 수정 사실을 남긴다. 완료. docs/design-prd.md (§10, 약 191-205행)
  5. npm test(vitest run 전체 스위트)로 회귀가 없는지 확인하고, npm run build로 타입체크·번들이 깨지지 않는지 확인한다. 이어서 npm run dev로 브라우저에서 zh·generic 두 프로필 모두 등록 링크가 뜨는지 육안 확인한다(백엔드 로그인 없이도 localStorage의 vocab-study:password·vocab-study:profile을 직접 시딩하면 홈 화면까지 바로 진입 가능 — §6 테스트 계획 참고). 완료 — vitest 309개 전체 통과, 빌드 통과, cmux 브라우저로 generic/zh 두 프로필 모두 홈 화면에서 "단어 등록 ›" 링크 노출 확인.

5리스크

리스크영향완화책
실제 배포 환경에 generic 콘텐츠 프로필이 아직 없을 수 있음 이 이슈만으로는 눈에 보이는 사용자 영향 없음(로컬 검증만 가능) 플랜(§5)이 이미 "D 전까지는 어떤 머지도 사용자 가시 변화가 없다"고 명시 — 이 이슈부터가 그 스위치이며, zh 프로필 동작이 그대로 보존되는지만 확인하면 충분하다
브라우저 수동 검증 시 localStorage 시딩값이 실제 로그인 응답 스키마(PublicProfile)와 어긋나면 다른 화면에서 오류가 날 수 있음 검증 절차 자체의 신뢰도 저하(실제 버그는 아님) src/lib/api.ts의 PublicProfile 타입·saveProfile 직렬화 형식을 그대로 따라 시딩하고, 홈 화면 등록 링크 노출 여부만 확인 대상으로 좁힌다

6테스트 계획

  • npm test — 전체 vitest 스위트(contentLabels.test.ts·registerValidation.test.ts 포함)가 그대로 초록인지 확인. 이번 변경이 lib 로직을 건드리지 않으므로 회귀가 없어야 한다.
  • npm run build — tsc -b && vite build로 타입체크와 번들링이 깨지지 않는지 확인.
  • npm run dev 브라우저 수동 확인: devtools 콘솔에서 localStorage.setItem('vocab-study:password','x')와 localStorage.setItem('vocab-study:profile', JSON.stringify({id:'t',name:'t',modes:['m1','m2'],contentType:'generic'}))를 실행한 뒤 새로고침 → 홈 화면에 "단어 등록 ›" 링크가 뜨는지 확인(변경 전엔 숨겨졌던 케이스). contentType:'zh'로 바꿔도 동일하게 노출되는지 재확인(기존 동작 불변 확인).
  • 등록 화면 진입까지 클릭해 placeholder·테이블 헤더가 §6 개정 내용과 일치하는지(코드 변경 없는 부분이지만 문서·구현 일치 여부를 눈으로 재확인) 함께 본다.
