#122기능 개선

새 단어 탭 생성 시 시트 서식 자동 적용 — 헤더 색상·1행 고정·기록 열 회색 배경

damdam6/vocabulary-study 브랜치 feat/122-new-tab-sheet-styling ← main 라벨 enhancement 2026-07-30

1요약

새 단어 탭 생성(createWordTab)이 지금은 탭 추가와 1행 헤더 값만 쓰고 서식을 적용하지 않는다. 이번 작업에서 한 번의 :batchUpdate로 탭 추가 + 1행 고정 + 헤더 색상 + D열 이후 기록 영역 배경을 함께 적용한다. 적용할 서식 값은 추측이 아니라 참조 시트(en 프로필의 '단어1' 탭)를 Sheets API로 실측해 확정했다: A1·C1 #FFD966, B1 #D9EAD3, D열부터 전 행 #666666(진회색), 1행 고정. _정보 탭 생성 경로는 기존 그대로 무서식으로 유지한다.

2현황 분석

  • 생성 흐름: worker/lib/tabs.ts:13 createWordTab이 ① 헤더 결정(첫 탭 1:1 복사 또는 기본 헤더) → ② addSheet → ③ updateValues로 A1 헤더 쓰기 순서로 동작한다.
  • addSheet: worker/lib/sheets.ts:61 — { addSheet: { properties: { title } } } 단일 request만 보내는 POST :batchUpdate. 서식·행 고정·sheetId 지정 없음.
  • 호출 경로 2곳: POST /api/tabs(worker/routes/tabs.ts:40, 등록 화면 "생성" 버튼)와 POST /api/words/register의 createTab 계약 호환 경로(worker/routes/register.ts:67). 둘 다 createWordTab을 공유하므로 한 곳만 고치면 된다.
  • 무서식 유지 대상: _정보 탭 생성(worker/routes/settings.ts:58)도 같은 addSheet를 쓴다 — 시그니처를 바꾸지 않으면 자동으로 기존 동작 유지.
  • 서식 실측 (서비스 계정으로 두 시트 조회): zh 시트의 HSK6급 탭은 볼드 헤더 + 1행 고정만 있고 배경색이 없다. 이슈의 참조 스크린샷 서식은 en 프로필 시트의 '단어1' 탭과 일치 — A1 #FFD966 / B1 #D9EAD3 / C1 #FFD966, D열부터 우측·아래 전체 #666666, frozenRowCount: 1. 글자색·볼드는 지정돼 있지 않다(배경만) — 그대로 재현한다.
  • 테스트 현황: worker/routes/tabs.test.ts:51 등 5개 suite(tabs·tabs.generic·register·register.generic·settings)의 fetch 스텁이 :batchUpdate body에서 addSheet request만 골라 처리하고 나머지는 무시한다 — 서식 request가 추가돼도 기존 스텁은 깨지지 않지만, 서식을 검증하는 assertion은 어디에도 없다.
  • 권한: OAuth 스코프가 이미 spreadsheets 전체 권한이라 추가 설정 불요.

3설계

  • 레이어 분리: sheets.ts(전송 래퍼)에 범용 batchUpdateSpreadsheet(env, sheetId, requests)를 추가하고, 기존 addSheet는 그 위의 thin wrapper로 재구현한다 (settings 경로 시그니처·동작 불변). 서식 내용(색·범위)은 단어 탭 도메인 지식이므로 tabs.ts가 request 배열을 구성한다.
  • sheetId 선지정: 같은 배치의 repeatCell이 새 탭을 참조하려면 응답을 기다릴 수 없으므로, crypto.getRandomValues로 31비트 양의 정수 gid를 만들어 addSheet.properties.sheetId에 직접 지정한다 (이슈 기대 동작 1). Workers 런타임에서 crypto.getRandomValues는 표준 지원.
  • request 구성 (순서 보장 — API는 배열 순서대로 처리):
    1. addSheet: { sheetId: gid, title, gridProperties: { frozenRowCount: 1 } } — 1행 고정을 생성 시점에 포함.
    2. repeatCell ×3: 1행의 A(노랑)·B(연두)·C(노랑) 각 1셀, fields: "userEnteredFormat.backgroundColor".
    3. repeatCell ×1: { sheetId: gid, startColumnIndex: 3 } — 행 범위·끝 열 생략 = D열부터 그리드 전체(open-ended), 배경 #666666. 헤더 D1도 포함되는 것이 참조 시트와 동일.
  • 색상 상수: { red: 255/255, green: 217/255, blue: 102/255 }처럼 255분수로 표기해 hex와의 대응을 코드에서 바로 읽게 한다.
  • 기각한 대안: (a) addSheet 응답에서 sheetId를 읽어 2번째 batchUpdate로 서식 적용 — 왕복 2회 + 탭만 생기고 서식은 실패하는 부분 실패 창이 생겨, 이슈가 명시한 "한 번의 batchUpdate"에 반함. (b) 서식 내용을 sheets.ts에 하드코딩한 addFormattedSheet — 도메인 지식이 전송 래퍼로 새는 구조라 기각. (c) gid 충돌 시 재시도 로직 — 충돌 확률이 기존 탭 수/231로 무시 가능해 단순성 우선으로 미도입.

5리스크

리스크영향완화책
무작위 gid가 기존 sheetId와 충돌 batchUpdate 400 → 탭 생성 실패(500 응답) 확률 ≈ 기존 탭 수/231로 무시 가능. 실패해도 SheetsApiError로 관측되고 재시도(버튼 재클릭)로 해소 — 재시도 로직 미도입은 의도된 단순화.
D열 이후 #666666 + 기본 검정 글자의 낮은 대비 기록 열 텍스트 가독성 저하 참조 시트가 실사용 중인 동일 서식(글자색 미지정)이므로 그대로 재현 — 이슈 스펙. 변경 원하면 후속 이슈.
서식 request가 늘어난 batchUpdate에 기존 테스트 스텁이 반응 무관 suite 실패 모든 스텁이 addSheet만 골라 처리하는 무시 루프임을 확인함(register.test.ts:44 등) — 전체 테스트로 재확인.
실 시트 스모크가 사용자 시트에 흔적을 남김 임시 탭 잔존 검증 직후 deleteSheet로 해당 탭만 제거. 기존 탭·기존 값 경로(values.update/append)는 건드리지 않음.

  • 신규(경계): settings.test.ts — _정보 탭 생성 request가 서식 없는 { addSheet: { properties: { title } } }임을 고정.
  • 회귀: 멱등 경로(기존 탭 이름 → created: false)에서 batchUpdate 미발생, 0개 부트스트랩·_ 접두 제외·register createTab 경로 등 기존 테스트 전부 통과.
  • 정적 검증: npm run lint, npm run build(tsc -b 포함).
  • 실 시트 스모크: wrangler dev로 임시 탭 생성 → Sheets API 실측으로 1행 고정 + 색상 4종이 참조 값과 일치함을 확인 → 탭 정리.
