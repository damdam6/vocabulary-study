세션 설정 — 클라 세션 상한 파라미터화 (SESSION_CAP 인자화 + settings 수신)

damdam6/vocabulary-study 브랜치 feat/104-session-limit-param ← main 라벨 enhancement 2026-07-28

1요약

시트별로 세션 문제 수를 다르게 설정할 수 있게 하는 플랜(docs/plans/session-limit-and-home-utils.md §5 작업 C)의 클라이언트 절반이다. Worker가 GET /api/words 응답에 settings.sessionLimit을 동봉하는 것은 별도 작업(A)이 담당하며, 이 작업은 A 머지 여부와 무관하게 클라 로직이 그 값을 소비할 수 있도록 준비하는 것이 목표다. sessionQueue.ts·homeStats.ts의 하드코딩된 60을 limit 인자로 바꾸고 두 곳의 중복 상수를 하나로 일원화하며, fetchWords가 settings 블록을 수신·검증해 홈 화면 배선(HomeScreen.tsx)에 흘려보낸다. Worker·UI 신규 요소는 이 작업 범위 밖이다.

2현황 분석

  • src/lib/sessionQueue.ts:12 — export const SESSION_CAP = 60. buildSessionQueue가 복습 대기 "오래된 순 최대 60개" 컷(:54)과 학습 중 슬롯을 채운 뒤의 총 상한(:64)에 이 상수를 그대로 참조한다.
  • src/lib/homeStats.ts:10(수정 전) — 로컬 const SESSION_CAP = 60 중복. sessionCount 산식 Math.min(SESSION_CAP, Math.min(reviewDue, SESSION_CAP) + learning)이 sessionQueue.ts의 로직과 별도로 같은 상수를 하드코딩하고 있었다.
  • src/lib/wordsApi.ts:17(수정 전) — fetchWords가 서버 응답에서 profile·words만 골라 반환하고 settings 필드는 애초에 없었다(작업 A 이전에는 서버도 안 보낸다).
  • src/screens/HomeScreen.tsx:36-42,79 — fetchWords 결과로 computeHomeStats를 호출하고, 시작 버튼 클릭 시 buildSessionQueue를 호출한다. 둘 다 limit 인자를 넘기지 않아 각 함수의 기본값(60)에 의존하는 구조라, 함수 시그니처만 확장하면 호출부 배선만 추가하면 된다.
  • src/lib/studySession.ts:9,85 — 세션 진행 중 학습 오답 재삽입 시 state.queue.length < SESSION_CAP로 큐 성장 상한을 체크한다. 이슈 완료 조건·플랜 §5 작업 C의 파일 범위("src/lib 4파일": sessionQueue·homeStats·wordsApi·api)에 포함되지 않고, 플랜 §3.2가 "진행 중 세션은 영향 없음(큐는 시작 시 확정)"이라 명시하므로 불변으로 유지했다 — 세션 시작 시점의 SESSION_CAP 기본값 자체가 바뀌는 게 아니라 그 값을 쓰는 지점이 파라미터화되는 것뿐이라 studySession.ts의 재삽입 상한 로직과 상충하지 않는다.
  • src/lib/api.ts — PublicProfile·WordEntry 등 worker 타입의 클라이언트 쪽 미러를 모아두는 파일. settings 타입 미러를 여기 추가하는 것이 기존 패턴과 일치한다.

3설계

  • limit 인자화: buildSessionQueue(words, today, modes, rng, limit = SESSION_CAP)· computeHomeStats(words, today, modes, limit = SESSION_CAP) — 기본값을 SESSION_CAP으로 둬서 인자를 생략하면 기존 동작과 100% 동일하다(기존 테스트 무수정 통과 요건).
  • 상수 일원화: homeStats.ts의 로컬 SESSION_CAP을 제거하고 sessionQueue.ts에서 import했다 — "sessionQueue의 SESSION_CAP을 기본값 상수로 일원화"(이슈 기대 동작 1항)를 그대로 따른다.
  • settings 수신·폴백: fetchWords가 raw 응답의 settings를 검증되지 않은 값으로 받아 normalizeSettings를 거친다 — 객체가 아니거나, sessionLimit이 유한 양의 정수가 아니면 { sessionLimit: SESSION_CAP }(60)으로 폴백한다. 이는 "응답에 settings가 없거나 형태 이상이면 60"이라는 이슈 문구를 그대로 구현한 것이며, Worker(작업 A)가 이미 1~500 범위를 검증해 보내더라도 구서버·비정상 응답에 대한 방어선을 클라에도 둔다(읽기는 관대하게, 플랜 §3.1).
  • 타입 계약: api.ts에 WordsSettings { sessionLimit: number }를 추가해 기존 PublicProfile·WordEntry와 같은 "worker 타입 미러" 패턴을 유지했다. WordsResponse는 settings를 필수 필드로 갖고(정규화 후 값이므로), 정규화 이전의 raw 응답 형태는 별도 내부 타입 RawWordsResponse로 분리했다.
  • HomeScreen 배선: settings.sessionLimit을 상태로 저장해 computeHomeStats(집계 시점)와 buildSessionQueue(시작 클릭 시점)에 같은 값을 넘긴다 — 두 계산이 어긋나지 않아야 한다는 기존 주석 (HomeScreen.tsx:1-3)의 불변식을 limit 배선 이후에도 유지한다. UI 신규 요소는 추가하지 않았다(이슈 명시 범위).
  • 기각한 대안: fetchWords 밖(HomeScreen)에서 폴백 검증을 하는 방안 — API 클라이언트가 아닌 화면 컴포넌트가 계약 검증을 떠맡으면 RegisterScreen 등 다른 fetchWords 호출부마다 같은 검증을 중복해야 해서 기각했다.

4작업 단계

  1. sessionQueue.ts — buildSessionQueue에 limit: number = SESSION_CAP 5번째 인자 추가, 복습 컷·총 상한 두 곳의 하드코딩 SESSION_CAP을 limit으로 교체 src/lib/sessionQueue.ts
  2. homeStats.ts — 로컬 SESSION_CAP 상수 제거하고 sessionQueue.ts에서 import, computeHomeStats에 limit: number = SESSION_CAP 인자 추가해 sessionCount 산식에 반영 src/lib/homeStats.ts
  3. api.ts — WordsSettings { sessionLimit: number } 타입 미러 추가 src/lib/api.ts
  4. wordsApi.ts — WordsResponse에 settings 필드 추가, raw 응답을 normalizeSettings로 검증(비객체·sessionLimit 비정수·0 이하 → 60 폴백)해 반환 src/lib/wordsApi.ts
  5. HomeScreen.tsx — fetchWords 결과의 settings.sessionLimit을 상태로 저장, computeHomeStats· buildSessionQueue 호출에 배선. UI 요소 추가 없음 src/screens/HomeScreen.tsx
  6. 테스트 — sessionQueue.test.ts·homeStats.test.ts에 limit 30/1/60 경계 테스트, wordsApi.test.ts에 settings 폴백 (부재·null·배열·문자열·필드 누락·비정수·소수·0·음수) 테스트 추가. 기존 테스트는 fetchWords의 반환 형태가 실제로 settings를 항상 포함하도록 바뀐 1개 assertion만 갱신(신규 필드 추가, 기존 검증 로직 변경 없음) src/lib/sessionQueue.test.ts, src/lib/homeStats.test.ts, src/lib/wordsApi.test.ts

5리스크

리스크영향완화책
studySession.ts의 오답 재삽입 상한이 여전히 고정 SESSION_CAP(60)을 참조 이론상 limit=30으로 시작한 세션이라도 학습 중 오답 재삽입으로 30~60 사이까지 큐가 늘어날 여지가 남는다 플랜 §5 작업 C 파일 범위·완료 조건에 명시적으로 없고 "진행 중 세션 영향 없음(다음 세션부터)" 원칙과도 별개 사안이라 이번 작업 범위 밖으로 명확히 남겨둔다. 실제로 문제가 되면(예: 시트당 30문제 설정이 흔해지면) 별도 이슈로 studySession.ts에도 limit을 스레딩하는 후속 작업이 필요하다
작업 A(Worker 읽기) 미머지 상태에서 이 작업만 먼저 머지 서버가 settings를 보내지 않아 normalizeSettings가 항상 60으로 폴백 — 플랜이 명시한 "A 미머지 상태에선 기본 60으로 동작 불변" 그대로 의도된 동작. 별도 조치 불필요
