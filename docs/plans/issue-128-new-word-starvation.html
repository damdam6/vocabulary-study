새로 등록한 단어가 세션에 안 나온다 — 학습 중 큐가 '총 정답 수 많은 순'이라 신규 단어(0점)가 상한 밖으로 밀린다

구현 완료 (2026-07-30) — 작업 단계 9개 전부 반영. npm test 424/424 · npm run lint · npm run build 통과. 플랜과 달라진 점은 각 단계의 주석 참조.

1요약

새로 등록한 단어가 세션에 안 나오는 건 캐싱이 아니라 큐 선별 규칙 때문이다. buildSessionQueue가 학습 중 단어를 총 정답 수(D+E) 내림차순으로 정렬한 뒤 앞에서 잘라내므로, 0점인 신규 단어는 항상 최하위로 밀려 상한 밖으로 잘린다 — 명세대로 동작하는 것이고, 명세 자체가 신규 단어 기아를 만든다. 소유자 결정에 따라 ① 학습 중 정렬을 오름차순으로 반전하고, ② 복습이 세션 상한을 통째로 가져가는 두 번째 기아 경로를 막는 복습 몫 상한 30%를 함께 도입한다. 두 변경은 splitSessionSlots 하나로 묶어 homeStats와 sessionQueue가 같은 산식을 쓰도록 통합한다 — 전수 검증 결과 총 문제 수는 바뀌지 않으므로(아래 §3-D) 홈의 "오늘 세션 · n문제" 수치는 그대로다.

2현황 분석

흐름 — 홈 진입마다 fetchWords로 단어 전체를 새로 받고(src/screens/HomeScreen.tsx:40), 그 응답으로 현황 카드·세션 수를 계산하고(:47), "학습 시작" 클릭 시 같은 배열로 큐를 즉석에서 만든다(:84). 저장·캐시 계층이 중간에 없다 — 이슈의 캐싱 가설(③)은 이 구조상 성립하지 않는다.

현재 큐 산식 — src/lib/sessionQueue.ts:55-68

  • 복습 대기는 복습일 오래된 순으로 .slice(0, limit) — 상한 전체를 쓸 수 있다(:57).
  • 학습 중은 b.m1 + b.m2 - (a.m1 + a.m2), 즉 총 정답 수 내림차순으로 정렬한 뒤(:62) 남은 슬롯만큼 앞에서 잘라 붙인다(:67).
  • 합친 뒤 전체 셔플(:69) — 셔플은 출제 순서만 바꾸고 어떤 단어가 뽑히는지에는 관여하지 않는다. 그래서 매 세션 같은 단어 집합이 나온다.

홈 표시는 큐 산식의 사본 — src/lib/homeStats.ts:46의 sessionCount = min(limit, min(reviewDue, limit) + learning)은 위 산식을 손으로 옮겨 적은 것이다. src/screens/HomeScreen.tsx:83 주석이 "같은 산식이라 빈 큐가 나올 수 없다"는 불변식에 기대고 있어, 한쪽만 고치면 조용히 깨진다.

3원인 분석 · 설계

A. 확정 원인 — 정렬 방향이 신규 단어를 영구히 밀어낸다

새로 등록한 단어는 D=E=0이라 내림차순 정렬의 최하위다. slice는 앞에서 자르므로, 학습 중 단어 수가 세션 상한보다 많으면 신규 단어는 기존 단어가 졸업해 목록에서 빠질 때까지 출제되지 않는다. 동률(둘 다 0점)일 때는 stable sort로 시트 순서가 유지되는데 시트는 append-only라 먼저 등록한 단어가 항상 앞이다 — 0점끼리 비교해도 최근 등록분이 뒤로 간다.

실측(이슈 본문, 2026-07-30 · zh 프로필 · 서비스 계정으로 실제 시트 조회): 단어 150개 / 학습 중 145 / 복습 대기 0 / sessionLimit = 35. 점수 있는 19개가 슬롯을 먼저 채우고 남은 16자리를 0점 126개 중 시트 앞에서부터 채운다 → 시트 마지막 10행(최근 등록)의 큐 진입은 1/10. 선정에 무작위성이 없어 매 세션 동일한 35개가 나온다.

B. 두 번째 기아 경로 — 복습이 상한을 통째로 먹는다

복습 대기는 .slice(0, limit)로 상한 전체를 가져갈 수 있다(sessionQueue.ts:57). 복습 대기가 sessionLimit 이상이면 학습 슬롯이 0이 되어, 정렬을 고쳐도 신규 단어가 아예 못 들어온다. 실측 시점에는 복습 대기가 0이라 미발동이지만 A와 독립된 경로이므로 소유자 결정에 따라 이번에 함께 막는다.

C. 배제한 가설

  • 캐싱 — Worker는 /api/words에 Cache-Control을 붙이지 않고(worker 전체에 해당 헤더 없음), 클라는 단어 목록을 저장하지 않으며(localStorage엔 비밀번호·프로필·재시도 큐뿐), 홈은 진입마다 재조회한다. 캐시 계층 자체가 없다.
  • 신규 단어가 API에 안 실림(_ 접두 탭 제외·다른 시트 등록) — 실측에서 150개 전부 조회됨. 배제.

D. 설계 — 슬롯 배분을 한 함수로 통합

소유자 확정 결정 2건(정렬 반전 · 복습 몫 30%)을 src/lib/sessionQueue.ts의 순수 함수 하나로 표현하고, homeStats가 그 함수를 재사용해 산식 사본을 제거한다. homeStats는 이미 sessionQueue에서 SESSION_CAP을 import하므로 의존 방향이 그대로다(순환 없음).

/** PRD §6.1: 복습이 세션 상한을 통째로 가져가지 못하게 하는 몫 비율 (#128). */
export const REVIEW_SHARE = 0.3;

export function splitSessionSlots(reviewDue: number, learning: number, limit: number) {
  // 복습 몫 = 상한의 30%. 복습 대기가 있으면 최소 1개 — limit ≤ 3에서 floor가 0이 되는 경계 방어.
  const quota = Math.max(1, Math.floor(limit * REVIEW_SHARE));
  // 학습은 복습 몫을 뺀 나머지를 쓴다 (복습 대기가 몫보다 적으면 그만큼만 예약된다).
  const learningTake = Math.min(learning, limit - Math.min(reviewDue, quota));
  // 학습이 남긴 슬롯은 복습이 회수한다 — 몫은 하한 보장이지 낭비 상한이 아니다.
  const reviewTake = Math.min(reviewDue, limit - learningTake);
  return { review: reviewTake, learning: learningTake, total: reviewTake + learningTake };
}

총 문제 수는 바뀌지 않는다 (전수 검증). limit ∈ [1,60] × reviewDue ∈ [0,70] × learning ∈ [0,70] 전 조합(약 31만 건)에서 splitSessionSlots(...).total이 기존 min(limit, min(R,limit) + L)과 0건 불일치로 일치했고, reviewDue > 0인데 복습 배정이 0이 되는 조합도 없었다. 즉 홈의 "오늘 세션 · n문제" 숫자는 그대로이고, 이번 통합은 값 수정이 아니라 회귀 방지가 목적이다.

정렬 반전은 비교자 한 줄이다 — .toSorted((a, b) => a.m1 + a.m2 - (b.m1 + b.m2)). 동률은 stable sort로 시트 순서가 그대로 유지된다. 함께 .map()을 .slice() 뒤로 옮긴다 — 지금은 탈락할 단어까지 learningMode를 호출해 rng를 소비한다. 선정은 정렬·slice로만 결정되므로 기존 시드 고정 테스트의 집합·개수 단언에는 영향이 없다.

졸업 임박 쿼터는 두지 않는다 — 오름차순이면 4~5점 단어가 0점 126개가 한 바퀴 돌 때까지(약 25세션) 미출제된다. 소유자가 이 트레이드오프를 확인한 뒤 순수 오름차순을 선택했다. PRD §12의 종전 근거("거의 끝난 단어부터 졸업시키기")는 폐기한다.

4작업 단계

  1. 슬롯 배분 함수 신설 — REVIEW_SHARE = 0.3 상수와 splitSessionSlots(reviewDue, learning, limit)를 export한다(§3-D 코드). 비율은 상수로 두어 추후 조정 가능하게 한다. src/lib/sessionQueue.ts
  2. 큐 구성을 새 배분에 연결 — 복습·학습 각각 .slice(0, slots.review) / .slice(0, slots.learning)로 자르고, .map()은 slice 뒤로 옮긴다. 학습 중 정렬 비교자를 오름차순으로 반전한다. src/lib/sessionQueue.ts:55-68
  3. 모듈 문서 주석 갱신 — 파일 상단 JSDoc(:24-34)의 "복습 대기 전부 … 총 정답 수 내림차순" 서술을 새 규칙(복습 몫 30% · 오름차순)으로 고친다. 이 주석이 PRD §6.1의 코드 측 사본이므로 함께 틀리면 안 된다. src/lib/sessionQueue.ts:1-34
  4. 홈 산식을 같은 함수로 교체 — sessionCount를 splitSessionSlots(reviewDue, learning, limit).total로 바꾸고, HomeStats의 산식 주석(:16)도 함께 갱신한다. 산출값은 동일(§3-D 전수 검증). src/lib/homeStats.ts:16,46
  5. 기존 테스트 3건 개정 — :90 정렬 테스트를 오름차순 기준(고득점이 밀리고 0점이 들어옴)으로 대체, :137(복습 30+학습 40 → 20/40)·:202(limit 30, 복습 20+학습 40 → 9/21)의 분할 기대값을 새 산식으로 고친다. src/lib/sessionQueue.test.ts 실제: 정렬 테스트 :90은 1건이 아니라 2건으로 분리했다 — "적은 단어부터 채운다(방향)"와 "동률이면 시트 순서(stable sort)"는 한 케이스에 억지로 묶으면 어느 쪽이 깨졌는지 읽히지 않는다. :137·:202는 예측한 값(20/40, 9/21) 그대로 개정.
  6. 회귀 테스트 추가 — §6 테스트 계획의 신규 5건(신규 단어 진입 · 복습 몫 · 슬롯 낭비 없음 · limit ≤ 3 경계 · 홈-큐 불변식). src/lib/sessionQueue.test.ts 실제: 5건이 아니라 6건을 넣었다. 플랜의 "실측 재현" 항목은 "시트 마지막에 등록한 단어가 포함된다"고 적었는데 틀렸다 — 0점 풀(126개)이 상한(35)보다 크면 이번 세션에 들어가는 건 그 풀의 시트 앞 35개이고, 맞힌 단어가 1점으로 빠지며 프런티어가 세션마다 전진한다. 그래서 실측 테스트는 "큐 35개가 전부 0점"으로 단언을 고치고, 소유자 제보 시나리오(기존 학습 중 40개 시트에 5개 신규 등록 → 5개 전부 큐 진입)를 별도 테스트로 추가했다.
  7. 기능 PRD 개정 — §6.1-1을 "복습 대기 전부"에서 "세션 상한의 30%(최소 1문제), 학습이 남긴 슬롯은 회수"로, §6.1-2 정렬을 "총 정답 수가 적은 단어 우선"으로 고친다. §12 결정표의 "세션 큐 우선순위"·"학습 중 단어 출제 순서" 두 행을 기존 개정 표기 스타일(취소선 + 날짜·이슈번호 주석)에 맞춰 갱신하고, 문서 상단에 2026-07-30 개정 (4) 항목을 추가한다. docs/PRD.md:8-16, 155-164, 336-337
  8. 디자인 PRD 개정 — 홈 "오늘 세션 · n문제" 산식 문자열을 min(상한, 복습대기 + 학습중 단어 수)로 고치고, 복습 몫 30%가 총 문제 수를 바꾸지 않는다는 점을 한 줄로 명시한다. docs/design-prd.md:75

5리스크

리스크영향완화책
R1 고득점 단어 장기 미출제 순수 오름차순이라 4~5점 단어가 0점 126개를 한 바퀴 도는 약 25세션 동안 안 나온다. 졸업이 그만큼 늦어진다. 소유자가 트레이드오프를 확인하고 선택한 의도된 동작(결정 1). 쿼터는 두지 않는다 — 실사용에서 문제가 되면 별도 이슈로 재론.
R2 기존 테스트 3건이 깨진다 이슈 완료 조건은 정렬 테스트(:90) 1건만 언급하지만, 복습 몫 도입으로 :137·:202의 복습/학습 분할 단언도 함께 바뀐다(§3-D 표). 세 건 모두 새 산식 기준으로 개정하고(작업 5) 커밋 메시지에 변경 사유를 남긴다. 나머지 24건은 그대로 통과해야 한다.
R3 홈 표시와 큐 길이 어긋남 배분 구현을 잘못 짜면(예: 단순 slice(0, floor(limit×0.3))) 총합이 줄어 HomeScreen.tsx:83의 "빈 큐가 나올 수 없다" 불변식이 조용히 깨진다. 두 곳이 같은 함수를 호출하도록 통합(작업 1·4)하고, 조합 그리드로 queue.length === sessionCount를 고정하는 불변식 테스트를 넣는다.
R4 정렬 키가 비활성 모드를 포함 m1 + m2로 합산하므로 M = {m1} 프로필에서 E열에 잔존값이 있으면 그 단어가 신규 단어보다 뒤로 밀린다. PRD-general §4.1의 "비활성 모드 열은 판정에서 무시"와 어긋난다. 이번 범위 밖 — 이슈 결정에 없고, Worker가 비활성 모드 열을 쓰지 않아 실제 잔존값은 수기 입력뿐이다. 현행 유지하고 후속 이슈 후보로 기록한다.
R5 "30"의 해석 (비율 vs 개수) 이슈 본문이 표기 주의를 남겼다. 개수 30 고정이라면 상한 35에서 복습이 30문제를 가져가 학습 슬롯이 5개로 줄어 이번 수정의 취지와 정반대가 된다. 30%(비율)로 확정해 진행한다 — 선택지가 %였고, 개수 해석은 기아를 되레 악화시킨다. 승인 게이트에서 소유자에게 재확인한다.

  • [신규] 소유자 제보 재현 — 이미 학습 중인 단어 40개(상한 초과)가 있는 시트에 5개를 새로 등록, limit = 35. 신규 5개가 전부 큐에 들어온다 — 종전 내림차순에서는 5개 모두 잘렸다. 이것이 "등록했는데 안 나온다"의 직접 회귀 테스트다.
  • [신규] 실측 분포 재현 — 학습 중 145개(5점 4 / 4점 4 / 3점 4 / 2점 3 / 1점 4 / 0점 126), limit = 35. 큐 35개가 전부 0점 신규 단어이고 점수 있는 19개는 밀린다. 정정: 플랜 초안은 "시트 마지막에 등록한 단어가 포함된다"고 적었으나 틀렸다 — 0점 풀이 상한보다 크면 이번 세션은 그 풀의 시트 앞 35개이고, 맞힌 단어가 빠지며 프런티어가 세션마다 전진한다. 가장 최근 등록분의 즉시 진입은 위 "소유자 제보 재현" 테스트가 담당한다.
  • [대체] 정렬 오름차순 — 기존 :90을 뒤집는다: 고득점 59개 + 0점 2개에서 남은 슬롯을 0점 단어가 가져가고, 0점끼리 동률이면 시트 순서가 앞선 쪽이 이긴다(stable sort 유지 확인).
  • [신규] 복습 몫 상한 — limit = 35, 복습 대기 100 / 학습 중 145 → 복습 10 · 학습 25. 복습만으로 상한을 채우던 종전 동작이 사라졌음을 고정한다.
  • [신규] 슬롯 낭비 없음 — limit = 35, 복습 대기 100 / 학습 중 0 → 복습 35(상한 전부). 몫이 상한으로 오작동하지 않는지 확인.
  • [신규] 경계 limit ≤ 3 — limit = 3, 복습 5 / 학습 10 → 복습 1 · 학습 2. floor(3 × 0.3) = 0에서 복습이 굶지 않는다(PRD §12 "복습 누락 방지가 우선" 유지).
  • [신규] 홈-큐 불변식 — limit ∈ {1, 3, 30, 35, 60} × 복습/학습 개수 조합 그리드에서 buildSessionQueue(...).length === computeHomeStats(...).sessionCount. 두 산식이 다시 갈라지면 즉시 실패한다.
  • [개정] 기존 분할 테스트 — :137(60 / 30·40 → 복습 20 · 학습 40), :202(30 / 20·40 → 복습 9 · 학습 21).
  • [회귀] 그대로 통과해야 하는 것 — 복습 대기 61개 컷(:51), nextReview: null 데이터 이상 최우선(:67), 단어당 1문제·유일성(:165), 탭 구분(:176), M 파라미터화 4건, homeStats 7건 전부.
  • 정적 검사 — npm run lint(oxlint) · npm run build(tsc -b + vite).
  • 수동 확인(선택) — npm run dev 후 zh 프로필 홈에서 "오늘 세션 · 35문제"가 그대로인지, 세션에 최근 등록한 단어가 실제로 나오는지 눈으로 확인.

7완료 조건

  • 학습 중 정렬이 D+E 오름차순이다 — 동률은 시트 순서 유지(stable sort).
  • 복습 몫 상한 30%가 REVIEW_SHARE 상수로 도입됐다 — 학습 중이 적으면 남는 슬롯을 복습이 회수하고(낭비 없음), limit ≤ 3에서도 복습 대기가 있으면 최소 1문제가 확보된다.
  • homeStats.sessionCount와 큐 길이가 같은 함수(splitSessionSlots)에서 나온다 — 산식 사본 제거. 홈 표시 숫자 자체는 변하지 않는다.
  • 학습 중 단어가 상한보다 많아도 0점 신규 단어가 큐에 포함됨을 테스트가 고정한다.
  • 복습 대기가 많아도 학습 슬롯이 확보되고, 학습 중이 0이면 복습이 상한 전부를 씀을 테스트가 고정한다.
  • 기존 정렬 테스트(sessionQueue.test.ts:90)가 오름차순 기준으로 대체됐고, 분할 기대값이 바뀐 :137·:202도 함께 개정됐다.
  • docs/PRD.md §6.1-1(복습 전부 → 몫 상한)·§6.1-2(정렬 방향) 개정 + §12 결정표 "학습 중 단어 출제 순서"·"세션 큐 우선순위" 행 갱신 + 상단 개정 이력 추가.
  • docs/design-prd.md §3 세션 문제 수 산식 개정.
  • npm test · npm run lint · npm run build 전부 통과.
