1요약

3설계

1. 서비스 포트와 생산용 연결

worker/lib/tts/service.ts에서 서비스 전용 타입과 팩터리를 내보낸다. 핵심 팩터리 createTtsAudioService는 storage: ReturnType<typeof createTtsAudioStorage>, provider: TtsProvider, clock, registerBackgroundTask: (promise: Promise<unknown>) => void를 받는다. clock은 now / setTimeout / clearTimeout의 최소 포트이며 기본 구현은 단조 시간과 런타임 timer를 사용한다. 서비스 호출 입력은 { profile: Pick<Profile, "id" | "sheetId">, input: NormalizedTtsInput, config: TtsConfig, signal: AbortSignal }이다.

같은 파일의 얇은 생산용 팩터리 createR2TtsAudioService는 bucket을 받아 createTtsAudioStorage(bucket, validateMp3)를 구성하고 핵심 서비스에 위임한다. provider는 이미 검증된 설정과 시크릿으로 구성되어 주입된다. 설정 검증·인증·키 조회·Request/Response는 서비스에 넣지 않는다. #140은 이 팩터리와 현재 config/provider를 연결하며 두 설정이 일치하도록 한다. 함수 이름은 구현에서 일관되게 조정할 수 있으나 실제 검사기 연결과 테스트용 저장 포트는 반드시 남긴다.

결과는 TtsResponseDiagnostics & { audio: Uint8Array; contentType: "audio/mpeg"; pronunciationDecision: PronunciationDecision; billedCharacters?: number } 형태로 정한다. pronunciation/revision은 현재 요청에서 계산한다. billedCharacters는 실제 합성 결과에 있을 때만 유지하며 경합 승자 바이트를 반환해도 이번 요청에서 발생한 합성 계량은 관측할 수 있게 한다. 저장 객체의 과거 진단 metadata를 응답으로 복사하지 않는다.

TtsServiceError는 기존 TTS_ERROR_RESPONSES의 code/status/message를 사용한다. 초기 조회 실패는 tts_storage_unavailable, 합성 deadline은 tts_timeout이다. Qwen의 정규화된 tts_unavailable / tts_upstream_error는 유지하고 알려지지 않은 제공자 실패는 안전한 tts_upstream_error로 바꾼다. 사용자 취소는 signal.reason을 보존하고 timeout이나 저장소 오류로 바꾸지 않는다. HTTP 직렬화는 #140의 책임이다.

2. 단계와 시간 예산

단계예산·행동종료 결과
준비진입 및 키 해시 await 이후 취소 확인. buildAudioObjectKey·decidePronunciation·createSynthesisInput 재사용.취소되면 get/provider/put 모두 시작하지 않음.
최초 조회storage.get 호출 직전부터 하나의 2초 deadline. metadata·stream read·MP3 검사까지 포함.유효 hit → STORED/PRESENT. 정상 null만 합성. 예외·timeout·손상 → 503용 코드, 합성 0회.
합성miss 후 시작 직전에 12초 deadline/timer 하나 생성. 요청 취소와 합성 timeout을 하나의 AbortController에 연결해 provider에 전달. await 이후 실제 MP3도 검사하고 만료·취소 재확인.완성 MP3만 저장. 제공자 실패·부분/빈/과대/비 MP3는 put 0회. timeout → 504용 코드.
저장검증된 생성 바이트의 putIfAbsent 시작부터 하나의 2초 deadline. put 경합 시 같은 deadline의 남은 시간으로 get 한 번.saved → GENERATED/SAVED. conflict 후 유효 hit → 승자 bytes, STORED/PRESENT. put 실패·초과 또는 경합 재조회 실패/null/손상/초과 → 생성 bytes, GENERATED/UNCONFIRMED.

deadline을 절대 시각으로 보관하고 각 await 완료 시 clock.now() >= deadline 여부를 확인한다. event loop 지연·동기 검증 때문에 timer callback보다 늦은 성공이 먼저 관측돼도 예산 초과를 성공 처리하지 않는다. 경합 재조회에 새 2초를 부여하지 않으며 남은 시간이 0이면 get을 시작하지 않는다. 세 I/O 단계 예산은 최대 16초이고 키 해시·HTTP 전송은 이 수치와 구분한다.

서비스가 기다리는 Promise는 취소·deadline에서도 종료되도록 한다. signal을 무시하는 provider/저장 더블의 늦은 resolve/reject가 다음 단계를 재개하거나 미처리 rejection을 만들면 안 된다. 합성 timer는 adapter가 만들지 않으며 모든 정상·오류·취소 경로에서 timer·요청 abort listener를 제거한다. 이미 만료된 합성 signal을 저장 단계에 재사용하지 않는다.

3. 원래 put의 수명과 관측

원래 putPromise = storage.putIfAbsent(...)를 보관하고 즉시 양쪽 settle handler를 붙인다. putPromise.then(onSavedOrConflict, onFailure)로 파생한 관측 Promise를 작업 등록 포트에 저장 시작마다 한 번 넘긴다. 제한 시간용 race Promise를 등록해서는 안 된다. foreground 결과와 관계없이 등록된 Promise는 원래 put이 끝날 때까지 pending이어야 한다.

서비스 전용 관측 포트는 saved/conflict/failed와 elapsedMs, 요청 상관 식별자 및 허용된 설정 진단만 받게 한다. 기본 동작도 안전한 구조화 로그로 실제 결과를 남기고 테스트는 observer를 주입한다. 원문·병음·시트 ID·시크릿·원래 예외 객체를 관측 데이터에 넣지 않는다. observer 또는 등록 함수가 예외를 던져도 이미 검증한 생성 음성을 버리지 않고 원래 Promise의 rejection handler를 유지한다. 등록 실패는 관측하고 백그라운드 실행 보장을 주장하지 않는다.

저장 대기 중 사용자 취소는 foreground를 취소 reason으로 종료하되 이미 시작한 put의 관측 Promise를 유지한다. 취소 후 경합 재조회·재합성·추가 put은 하지 않는다. MP3 완성과 put 시작 전 취소가 관측되면 새 저장은 시작하지 않는다. timeout 뒤 늦게 저장되어도 이미 반환한 UNCONFIRMED 결과를 바꾸지 않는다. R2 기다리기 중단은 원격 R2 작업 자체의 취소를 의미하지 않는다.

7테스트 계획

  • 명령. 구현 탭에서 잠금 파일에 맞는 의존성을 준비한 뒤 npm test -- worker/lib/tts/service.test.ts worker/lib/tts/storage.test.ts worker/lib/tts/audio.test.ts worker/lib/tts/providers/qwen.test.ts. 완료 게이트는 npm test, npm run lint, npm run build다. build는 배포 명령과 구분한다. 계획 단계에서는 실행하지 않는다.
  • 조회 표. 유효 hit → 같은 바이트·STORED/PRESENT·provider/put 0회. 정상 null → provider 1회. get sync throw/reject·영구 pending·정확히 2초·늦은 null/hit/reject → tts_storage_unavailable·provider 0회. 실제 storage에서 MIME·size·손상 MP3·stream 오류와 바디가 늦는 경우를 포함한다.
  • 합성 표. miss 이후 타이머가 시작하고 provider input은 text만 포함. Qwen 오류 503/502 유지, unknown 오류 안전화. 12초에 tts_timeout과 adapter signal.abort; 12초 전 완료는 다음 단계. 빈/부분/비 MP3/4MiB 초과 결과·합성 실패·취소·늦은 합성 성공은 put 0회. 동기 MP3 검사 완료 뒤 clock deadline도 확인한다.
  • 저장 표. saved → GENERATED/SAVED. conflict → 같은 key 재조회 한 번 후 승자 바이트·STORED/PRESENT. put throw/reject/pending, 경합 reget null/reject/invalid/pending → 원래 생성 바이트·GENERATED/UNCONFIRMED. put 1,800ms + reget 200ms에서 종료하며 2,000ms를 새로 부여하지 않음. 잔여 0ms이면 재조회 0회. 어떤 저장 실패도 재합성/두 번째 put을 만들지 않음.
  • 늦은 저장과 등록. 등록한 Promise가 foreground 2초 timeout 뒤에도 pending임을 확인한 후 put의 늦은 saved/conflict/reject를 각각 settle시켜 관측 내용·한 번 등록·fulfilled 관측 Promise·미처리 rejection 0개를 확인. 저장 중 사용자 취소 뒤에도 같은 검증. observer/등록 함수 throw에도 생성 결과를 유지하며 원래 rejection을 회수.
  • 취소·자원. 진입 전, 키 생성 중, 조회 중, miss 직후, 합성 중, 합성 완료와 put 사이, 저장·경합 재조회 중 취소를 재현한다. 사용자 reason과 timeout을 구분하고 종료 뒤 timer·abort listener를 해제한다. 동시에 두 요청을 실행해 한 요청의 취소/예산이 다른 요청을 중단하지 않음도 확인.
  • 실제 모듈 조합. bucket 더블 위에 생산용 팩터리의 실제 storage+validateMp3를 사용해 miss→생성→저장→새 서비스 인스턴스 hit(후속 provider 0회), malformed cached object 차단, 조건부 put 경합을 확인한다. 유효하고 서로 다른 생성/승자 MP3 fixture로 반환 바이트 출처를 구별한다. 최소 한 사례에서 실제 createQwenTtsProvider와 Upgrade/socket 더블을 연결해 service의 12초 signal이 adapter까지 전달되고 socket을 닫는지 확인한다.
  • 계약·개인정보. absent/ignored/revision은 현재 요청 기준. 같은 A열·다른 B열은 provider text가 같고 key는 다르다. 프로필/시트/rate/revision 변화는 실제 key builder를 통과한다. 숫자 문자 수는 code point, billedCharacters는 제공될 때만 유지. sentinel 원문·병음·키·시트 ID·upstream 원문 예외가 서비스 오류·관측 데이터에 없음.
  • 실환경 미검증. 실제 DASHSCOPE_API_KEY 주입·모델 접근·과금·청취·모바일·실제 R2 저장/재조회/경합·지역/기기 변경·실측 latency는 실행하지 않는다. 합성 fixture는 MP3 구조 검사만 검증하며 음질·디코딩 성공을 보장하지 않는다.
