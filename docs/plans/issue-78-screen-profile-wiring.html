화면 프로필 배선 — 로그인 저장·홈 프로필명/전환/등록 링크·modes 연결 + design-prd §2·§3 개정

1요약

로그인 검증 성공 시 서버가 내려주는 profile을 저장하고, 홈 화면이 그 profile.modes·contentType으로 현황·세션 큐·등록 링크 노출을 계산하도록 배선한다. "프로필 전환" 저강조 링크를 추가해 비밀번호·프로필 캐시를 지우고 로그인 화면으로 돌려보내며, App은 전환 핸들러를 소유하고 StudyScreen에는 실제 렌더링 분기 없이 contentType 전달 지점만 마련한다. design-prd.md §2·§3을 프로필명 표기·전환 링크의 구체 스타일 값까지 개정해 범용화 플랜 작업 4의 마지막 잔여 디테일을 마무리한다.

3설계

  • 프로필 상태 소유: HomeScreen이 자체 state로 소유한다 — 캐시(getStoredProfile())로 초기화하고 fetchWords 응답마다 갱신·재저장한다. wordsApi.ts 주석대로 홈이 "진입마다 재조회하는 최신 프로필 원천"이라는 기존 설계와 일치시킨다. App으로 끌어올리는 대안은 App의 책임(화면 전환)을 불필요하게 넓혀 기각.
  • 프로필 전환 핸들러 소유: App이 구현(clearPassword() + setScreen('login'))하고 HomeScreen은 prop(onSwitchProfile)만 호출한다. 기존 onNavigateRegister와 동일한 패턴 — 화면 전환은 항상 App 소유.
  • StudyScreen contentType 전달: 실제 렌더링 분기 없이 최상위 컨테이너에 data-content-type 속성만 부여한다. tsconfig.app.json의 noUnusedLocals/noUnusedParameters가 죽은 prop을 컴파일 에러로 막기 때문에, 후속 이슈가 실제 분기(한자 크기·칩 문구·placeholder)를 붙일 훅 지점만 남기고 지금은 소비하지 않는 대안(prop만 받고 미사용)은 빌드가 깨져 기각.
  • profile 부재 시 StudyScreen 기본 contentType: 'zh'. PRD-general.md §9 마이그레이션 폴백 원칙과 동일한 안전망 — 어떤 이유로든 프로필 캐시가 비어 있어도 기존 zh 전용 동작을 유지한다.
  • "프로필 전환" 링크 위치: "단어 등록 ›" 아래, 같은 저강조 톤(text-muted, 0.85rem)으로 배치한다. 타이틀 옆에 두는 대안은 프로필명 표기와 시각적 위계가 겹쳐 기각. 구체 여백 값은 구현 중 index.css·design-prd.md에서 확정한다.

4작업 단계

  1. LoginScreen: verifyPassword 성공 분기(status === 'ok')에서 savePassword 옆에 saveProfile(result.profile) 호출을 추가한다. src/screens/LoginScreen.tsx
  2. HomeScreen: profile state를 getStoredProfile()로 초기화하고, fetchWords 응답의 profile로 setProfile + saveProfile(캐시 갱신)을 수행한다. computeHomeStats·buildSessionQueue에 하드코딩된 ["m1","m2"]를 profile?.modes ?? [](또는 응답에서 막 받은 profile의 modes)로 교체한다. "오늘의 학습" 타이틀 아래 프로필명을 저강조로 표기한다. "단어 등록 ›" 링크를 profile?.contentType === 'zh' 조건부로 바꾸고, 그 아래 "프로필 전환" 저강조 버튼을 추가해 새 prop onSwitchProfile을 호출한다. src/screens/HomeScreen.tsx
  3. App: api.ts에서 clearPassword·getStoredProfile을 추가로 import하고, HomeScreen에 onSwitchProfile={() => { clearPassword(); setScreen('login') }}를 배선한다. StudyScreen 렌더에 contentType={getStoredProfile()?.contentType ?? 'zh'}를 전달한다. src/App.tsx
  4. StudyScreen: StudyScreenProps에 contentType: ContentType(api.ts에서 타입 import)을 추가하고, 최상위 .study div에 data-content-type={contentType}를 부여한다. 그 외 렌더링 로직은 건드리지 않는다(실제 분기는 후속 이슈). src/screens/StudyScreen.tsx
  5. 스타일: .home-profile-name(프로필명)과 "프로필 전환" 링크 클래스를 추가하고, .home-title 하단 마진을 줄여 전체 세로 간격을 기존과 비슷하게 유지한다. 기존 토큰(text-muted, 0.8~0.85rem, home-register-link 스타일)을 재사용한다. src/index.css
  6. design-prd.md 개정: §2에 검증 성공 시 profile도 저장한다는 문구 추가. §3에 프로필명 표기 위치·스타일 값, "프로필 전환" 링크 스펙, 등록 링크의 zh 조건부 노출, 현황·큐가 실제 profile.modes를 쓴다는 문구를 추가한다. §9 결정 로그·§10 이슈 매핑에 이번 결정과 #78 행을 추가한다. docs/design-prd.md
  7. 회귀 확인: npm test(lib 테스트 전부 그린), npm run build(tsc -b — noUnusedLocals/noUnusedParameters 통과 포함), npm run lint(oxlint) 실행. package.json 251 tests passed, build clean, lint clean. 추가로 로컬 dev 서버(Worker + 실제 Google Sheets, 폴백 프로필: modes m1+m2/contentType zh)에서 cmux 브라우저 자동화로 로그인→프로필명 표시→등록 링크(zh)→프로필 전환(캐시 삭제+로그인 복귀)→StudyScreen data-content-type="zh"까지 실기 확인. modes ["m1"]만 있는 프로필·generic contentType 분기는 로컬에 PROFILES 시크릿이 없어 실기 확인은 못 했고, 타입 검사 + 기존 computeHomeStats/buildSessionQueue 단위 테스트(#75/#76)로 대체 확인.

5리스크

리스크영향완화책
HomeScreen 마운트 시점에 profile 캐시가 비어 있을 가능성(이론상 로그인 직후엔 항상 채워짐)프로필명 미표시·등록 링크 순간적 미노출fetchWords 응답 도착 즉시 갱신되어 표시 창이 매우 짧고, 조건은 "미노출"이라는 안전한 기본값으로 수렴

StudyScreen에 data-content-type 속성 추가기존 CSS 선택자와 충돌 가능성신규 속성이라 매칭되는 기존 규칙 없음 — 빌드 후 육안으로 학습 화면 스타일 무변화 확인
