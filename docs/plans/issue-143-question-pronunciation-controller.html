1요약

주입된 전송·Audio·Blob 캐시를 연결하는 React 비의존 PronunciationController를 src/lib/speak.ts에 만든다. 질문 ID와 작업 세대로 늦은 응답을 차단하고, 공개당 자동 기회 1회와 수동 재생 의도 1개를 관리한다. 준비된 음성은 동기 클릭 경로에서 즉시 재생하고 숨김·문제 이동·종료에서 작업을 무효화한다. 이 문서는 계획 산출물이며 구현·독립 리뷰·GitHub squash merge는 오케스트레이터가 지정한 별도 대화형 모델로 인계한다.

3설계

1. 생성 계약과 소유 범위

createPronunciationController({ profileId, capability, transport, audio, cache }): PronunciationController를 export한다. options 타입은 speak.ts에 정의하며 capability: TtsCapability 및 세 포트를 필수로 주입한다. controller 한 개는 세션 한 개에 속하고 주입된 Audio/cache의 정리도 소유한다. 모듈 로드·생성만으로 네트워크·재생을 시작하지 않는다. React·DOM·Worker·retryQueue를 import하지 않는다. contentType === "zh" 확인과 capability 전달은 #145가 맡으며 여기서는 enabled=false를 방어한다.

2. 입력·식별·캐시

  • activate는 외부에서 만든 sessionId + pos 문자열을 불투명한 질문 ID로 받는다. 동일 활성 ID 재호출은 입력 객체가 새로 와도 no-op이며 자동 기회를 초기화하지 않는다. 다른 ID를 활성화하면 기존 작업을 먼저 무효화하고 새 질문의 플래그·안내를 초기화한다. 같은 표제어가 새 ID로 나오면 Blob은 재사용하고 공개 기회는 새로 부여한다.
  • 브라우저용 최소 정규화·유효성 검사 함수를 speak.ts 내부에 둔다. worker/lib/tts/input.ts:30 계약과 맞춰 text/pinyin의 CRLF·CR→LF, NFC·trim, 빈 pinyin→null을 적용한다. text는 trim 전 금지 C0 확인, Han 포함, 1~200 코드 포인트 확인; 201자는 text_too_long, 빈 값·Han 없음·금지 제어문자는 invalid_text다. pinyin 1,000자 상한 위반도 invalid_text로 다루되 병음 의미 검사·강제 적용은 하지 않는다. 정상 내부 공백·tab·LF·문장부호는 보존한다. transport에는 null pinyin 필드를 생략한다.
  • 캐시 키는 JSON.stringify([profileId, effectiveRevision, normalizedText, normalizedPinyin])로 만든다. questionId·word identity·원문 단순 이어붙이기는 키에 쓰지 않는다. get/set 성공 후 pin하고 준비·차단·재생 동안 보호한다. 현재 Blob 참조를 별도로 보유해 set(...).stored === false여도 현재 질문에서 재생·반복 재생이 가능하다.
  • 질문 변경·stop·dispose에서 현재 pin과 Blob 참조를 해제하되 stop은 캐시 전체를 지우지 않는다. 차단/ended는 현재 Blob을 유지한다. 응답 revision이 현재 revision과 다르면 유효한 현재 응답에 한해 기존 캐시를 clear하고 effectiveRevision을 응답 값으로 바꾼 후 새 키로 보관한다. 오래된 응답은 revision·캐시도 바꾸지 않는다. 이 정책을 factory JSDoc과 테스트로 고정한다.

3. 작업 세대와 의도

내부 상태는 현재 질문, generation, viewReady, autoConsumed, prepareAttempted, 요청 레코드(AbortController 포함), pendingIntent(null/auto/manual), 현재 Blob·pin, 재생 시도 토큰, disposed를 갖는다. 준비 요청은 활성 작업당 한 개이며 완료 처리는 한 곳에만 붙인다. 클릭마다 then(play)를 추가하지 않는다. 공개 기회와 UI status를 독립적으로 유지한다.

명령 / 사건전이와 정책
activate(new ID)generation 증가→이전 요청/재생 무효화·abort/stop·unpin→새 질문 idle. prepare/reveal/replay 전까지 요청 0회. 동일 ID는 모든 플래그 유지.
prepare(ID)현재·유효·활성 질문만 처리. 캐시 hit는 ready, miss는 요청 한 개 시작. 자동 재생 의도는 만들지 않으며 viewReady 전에는 소리 0회. 이미 시도한 준비·실패는 prepare 반복으로 재시도하지 않는다.
reveal(ID)viewReady=true. autoConsumed가 false일 때 먼저 소비한다. 이미 prepare 실패면 재요청 없이 종료. pending manual이면 보존하고 새 auto는 만들지 않는다. 그 외 준비된 Blob 또는 최초/진행 중 요청에 auto 의도 한 개를 연결한다. 반복 reveal은 no-op.
replay(ID)명시적 수동 의도가 자동 기회를 즉시 소비한다. 공개 전 호출은 준비/수동 의도를 합치되 viewReady 전 재생하지 않는다. 공개 후 Blob이 있으면 await/예약 없이 audio.play(blob)를 호출한다. miss면 새 요청 또는 기존 요청 한 개를 공유한다. 로딩 중 연속 클릭은 manual 의도 한 개로 합친다. 이미 재생 중이면 Audio 포트의 처음부터 재생 계약을 사용한다.
요청 성공 / 실패현재 질문·generation·요청 identity·생존 검증 후에만 Blob·캐시·status를 갱신한다. 성공은 ready 및 viewReady+의도가 있으면 한 번 재생. 실패는 autoConsumed=true, 의도 소거; 최신 의도가 manual일 때만 오류 안내. prepare 실패도 공개 기회를 소진한다. 재시도는 replay로만 가능.
play 결과 / 이벤트질문·generation·재생 시도 토큰을 모두 확인한다. started→playing, blocked→blocked, error→error, ended→ready. cancelled는 오류 안내 없이 현재 Blob에 맞는 대기 상태로 정리한다. 이벤트 처리 시 해당 시도 완료를 표시해 뒤늦은 started가 playing을 되살리지 않게 한다. blocked/error는 자동 재시도하지 않는다.
stop(hidden)세대 무효화, 요청 abort, Audio stop, pending 의도/오류 안내 제거, unpin, status=idle, autoConsumed=true. 현재 ID·입력·공개 여부는 유지한다. 중복 activate/prepare/reveal로 자동 요청/재생이 돌아오지 않게 억제하며 수동 replay만 다시 준비·재생할 수 있다.
stop(advance / exit)같은 동기 정리 후 활성 ID를 null로 해제한다. 옛 ID의 prepare/reveal/replay는 무시한다. 후속 새 질문 activate가 다음 사용 시작점이다.
disabled / dispose현재 응답의 tts_disabled 또는 tts_not_configured는 세션 enabled=false로 고정하고 요청·재생·의도 및 캐시를 정리한다. 새 activate/replay로 복구하지 않는다. dispose는 생존 플래그를 먼저 끄고 모든 구독·요청·Audio·cache를 정리하며 반복 호출과 이후 명령은 no-op이다.

4. 비동기 완료와 구독의 경계

요청을 abort해도 더블/브라우저의 늦은 완료는 가능하다. 성공·실패·finally가 모두 캡처한 질문 ID+generation+작업 identity와 생존을 확인해야 한다. 같은 질문의 반복 재생도 별도 시도 토큰으로 구분한다. Audio 구독 callback은 시도 토큰을 캡처하고 새 시도/정리 때 해제한다. Audio 포트는 자체 source 세대를 보장하므로 controller가 native 이벤트·URL을 재구현하지 않는다.

getSnapshot은 변경이 없으면 같은 객체를 반환하고 공개 필드가 바뀔 때 새 객체를 발행한다. 외부가 내부 상태를 바꾸지 못하도록 snapshot을 보호한다. subscribe는 상태 변경 통지와 멱등 unsubscribe를 제공하며 초기 값은 getSnapshot으로 읽는다. 구독자 예외가 정리를 중단하지 않게 하고, 구독자가 stop/activate/dispose로 재진입하면 통지 뒤 이어지는 play/cache 갱신 전에 토큰을 재확인한다.

수동 실패 안내는 발음을 불러오지 못했어요. 다시 눌러 주세요., 수동 차단은 발음이 준비됐어요. 다시 눌러 주세요.로 고정한다. 자동 실패·차단의 message는 null이다. GENERATED/UNCONFIRMED도 정상 재생하며 서버 원문 message를 그대로 UI에 노출하지 않는다. 401의 로그인 전환과 성공 콜백은 기존 전송이 담당하고, 화면 exit/dispose 연결은 #145에서 검증한다.

6테스트 계획

  • 기본/입력: disabled 생성, activate만 호출 시 transport/play 0회; 동일 ID 반복·새 객체 입력 no-op; 다른 ID 동일 표제어는 새 공개 기회. 200/201 코드 포인트·확장 Han·빈 text·금지 C0·CRLF/tab/LF·NFC·빈/긴 pinyin 및 입력 사유 확인.
  • 공개 타이밍: prepare 성공→reveal 전 play 0회→reveal 1회; reveal→준비 성공 1회; 반복 prepare/reveal도 1회. prepare 실패→reveal 자동 재요청 0회→replay 재시도 1회. 공개 전 manual 의도도 viewReady를 기다린다.
  • 의도 병합 / AC-07: prepare/reveal/replay를 로딩 중 여러 순서로 호출해 transport 1회·최종 play 1회. 수동이 먼저면 뒤의 reveal이 재생을 추가하지 않는다. 로딩 중 manual로 바뀐 뒤 실패는 수동 안내를 낸다.
  • 캐시·수동 동기 경로 / AC-06·09: replay가 반환하기 전에 Audio 더블의 play가 호출되는지 microtask flush 없이 검사. 이미 준비한 질문 5회 클릭은 fetch 추가 0회이며 각 play는 같은 Blob. blocked 후 Blob 유지·추가 요청 없이 수동 재생, stored:false도 현재 Blob 재사용.
  • 실패 / AC-09·10: timeout/network/invalid_response 및 HTTP unavailable/storage_unavailable/upstream 오류, blocked/error/cancelled play 결과를 제어한다. 자동 message=null·재시도 0회; 수동 안내 고정·재시도 가능. UNCONFIRMED 성공은 정상 재생. unknown reject/sync throw도 명령 호출을 깨거나 미처리 rejection을 만들지 않는다.
  • 늦은 응답 / AC-08: A 요청→B activate/reveal→B 성공→A 성공/실패/disabled를 각각 완료한다. A play/cache set/통지/revision 변경 0회, B snapshot·요청 identity 유지. abort를 무시하는 더블을 사용한다. A→B→같은 A ID 재활성도 이전 세대를 재사용하지 않는다.
  • play·이벤트 역전: 동일 질문 replay 1→2 뒤 1의 started/blocked/reject, 다른 질문 전환 뒤 옛 이벤트, ended/error가 play 결과보다 먼저 도착하는 순서를 검증한다. 저장한 옛 callback도 실행해 현재 snapshot 불변을 확인한다.
  • 중단 / AC-16: loading/ready/playing/blocked 상태에서 hidden·advance·exit·dispose를 적용. signal abort·Audio stop·unpin 확인, 늦은 완료 무시. hidden 뒤 동일 activate/reveal/prepare는 요청·자동 play 0회, 공개된 질문의 replay는 정상. advance/exit 뒤 옛 ID 명령 무시.
  • 세션 자원·revision: get/set 성공 후 pin 순서, 질문 전환/stop의 unpin, 차단 시 pin 유지, dispose 시 cache/audio 정리·구독 해제. 다른 text/pinyin/profile/revision 키 분리, NFC/trim 같은 입력은 재사용. 응답 revision 변경 시 clear 후 새 키 사용; stale 응답은 cache/revision 불변.
  • disabled·구독: 현재 tts_disabled/tts_not_configured 응답은 enabled=false이며 후속 질문도 요청 0회. snapshot 참조 안정성·값 변경 통지·unsubscribe·dispose 후 no-op. 구독자에서 stop/activate/dispose 또는 예외 발생 시 현재 상태/자원 일관성.
