#127기능 개선

등록 화면 오류 행 직접 수정 — 오류 알림 배너 + 수정 모달 + '직접수정' 태그

1요약

등록 화면에서 오류(blocked) 행이 아무 안내 없이 제출에서 빠지는 문제를 없앤다. blocked 행이 있으면 중복 확인 배너와 같은 자리에 인라인 오류 배너를 띄우고, "오류 수정" 버튼으로 여는 모달에서 행마다 세 값을 모두 고칠 수 있게 한다. 저장하면 편집값으로 배치 전체가 재검증되고(표제어가 바뀌면 중복 판정도 달라지므로), 실제로 값이 바뀐 행에는 '직접수정' 태그가 상태 배지와 나란히 붙는다. 구현의 뼈대는 두 가지 — 원본 텍스트를 건드리지 않는 편집 오버레이 상태(행 index → 편집값)와, validateRegistrationInput을 파싱 단계 / 분류 단계로 쪼개 오버레이가 적용된 ParsedWord[]만 다시 분류하는 진입점이다. Worker·와이어 계약 변경은 없다.

2현황 분석

등록 화면의 검증 결과는 읽기 전용 파생 상태다. src/screens/RegisterScreen.tsx:167-173의 useMemo가 confirmedText·existingHanziInTab·contentType만 보고 validateRegistrationInput을 통째로 다시 돌린다 — 행 단위로 고친 값을 담아둘 곳이 없다.

  • 오류 행은 조용히 빠진다. 제출 대상은 rows.filter((row) => row.status !== 'blocked') (RegisterScreen.tsx:183) — 사용자 확인 절차가 없다. 중복은 hasDuplicates && !duplicatesAcknowledged 배너 (:422-433)로 명시적 확인을 받는데, 오류에는 대응 UI가 없다.
  • 고칠 수단은 원본 JSON뿐. textarea를 고치면 isDirty = confirmedText !== null && text !== confirmedText (:165) 게이트가 걸려 "확인"을 다시 눌러야 하고, 그때 배치 전체가 새로 파싱된다. 한 글자 오타 때문에 붙여넣은 JSON 전체를 뒤져야 한다.
  • 검증 함수가 파싱과 분류를 한 덩어리로 묶고 있다. validateRegistrationInput(src/lib/registerValidation.ts:93-161)은 rawText만 받아 JSON 파싱 → extract() 필드 추출 → hanziCounts 집계 → 행별 분류를 순서대로 수행한다. 이미 파싱된 ParsedWord[]를 재검증할 진입점이 없다.
  • 중복 확인은 서명 비교라 자동 리셋된다. duplicateKey(:176-181)는 duplicate 행의 표제어를 정렬·조인한 문자열이고, acknowledgedDuplicateKey와 같을 때만 확인된 것으로 본다 — 중복 집합이 달라지면 별도 리셋 코드 없이 재확인이 요구된다. 편집으로 표제어가 바뀌어도 이 메커니즘이 그대로 작동한다.
  • 표시는 순수 컴포넌트. src/screens/RegisterTable.tsx:35-53이 상태 배지 + 사유 목록만 그린다. 행 key는 `${row.hanzi}-${index}`(값 포함) — 입력 필드가 없는 표시 전용 테이블이라 무해하지만, 같은 전략을 모달 입력에 쓰면 타이핑마다 re-mount되어 포커스가 날아간다(이슈 §4 경고).
  • 컴포넌트 테스트 하네스는 이미 있다. src/test-utils.tsx(react-dom/client + React 19 act)와 src/screens/RegisterScreen.test.tsx(jsdom, 15개 케이스)가 존재한다 — contentLabels.ts·RegisterTable.tsx 주석의 "컴포넌트 테스트 하네스가 없어"는 #105 이전 기준의 낡은 서술이다. 모달·배너 동작을 DOM 테스트로 직접 고정할 수 있다.

3설계

편집값을 담는 자리를 원본 텍스트 밖에 만들고, 검증 함수를 파싱 단계와 분류 단계로 쪼개 분류만 다시 돌리는 구조로 간다. text/confirmedText를 건드리지 않으므로 isDirty 게이트(#55)와 중복 서명 비교 로직이 손대지 않은 채 그대로 유지된다.

A. 검증 함수 2단 분리

src/lib/registerValidation.ts에 두 함수를 노출하고, 기존 validateRegistrationInput은 둘을 이어 붙인 얇은 합성 함수로 남긴다 — 시그니처·반환 타입·기존 테스트 전부 불변.

  • parseRegistrationInput(rawText, contentType) → { ok: false; error } | { ok: true; words: ParsedWord[] } (JSON 파싱 · version · words 배열 · 스키마 오배치 검사 · extract())
  • classifyRegistrationRows(words, existingHanziInTab, contentType) → ValidatedRow[] (hanziCounts 재집계 + 행별 오류/중복/정상 분류)

hanziCounts가 분류 단계에서 배열 전체 기준으로 다시 계산되는 것이 핵심이다 — 같은 한자로 둘 다 blocked였던 A·B 중 A만 고치면 손대지 않은 B의 "입력 내 중복" 오류도 함께 풀린다(의도된 동작).

B. 편집 오버레이 상태

RegisterScreen에 editOverlay: Record<number, ParsedWord>를 둔다(행 index → 편집값). 파생 파이프라인을 2단 memo로 재구성한다:

  • parseResult = parseRegistrationInput(confirmedText, contentType) — deps: confirmedText, contentType
  • effectiveWords = parseResult.words.map((w, i) => editOverlay[i] ?? w)
  • rows = classifyRegistrationRows(effectiveWords, existingHanziInTab, contentType) — deps에 existingHanziInTab이 있어 탭 변경 시 분류만 재계산되고 오버레이는 유지된다

'직접수정' 플래그는 별도 상태로 두지 않는다 — 저장 시 편집값을 원본 parseResult.words[i]와 비교해 같으면 오버레이 엔트리를 지우고 다르면 넣는다. 그러면 "오버레이에 키가 있다 = 원본과 다르다 = 태그 대상"이 항상 참이라 플래그가 어긋날 여지가 없다.

오버레이 초기화는 handleConfirm에서 text !== confirmedText일 때만 — 행 구성이 달라져 index 기반 오버레이가 어긋나기 때문이다. 같은 텍스트로 "확인"을 다시 눌러 편집이 통째로 날아가는 사고를 막으려고 조건을 붙인다.

C. 배너 + 모달

  • 오류 배너: blockedCount > 0이면 항상 렌더 — dismiss 없음, 제출 차단 없음. 중복 배너와 같은 자리·같은 레이아웃 토큰을 쓰되 클래스는 분리 (.register-error-banner, red 틴트). 기존 테스트가 .register-confirm-banner로 중복 배너를 특정하고 있어(RegisterScreen.test.tsx:313) 같은 클래스를 재사용하면 선택자가 오염된다. 배치는 오류 배너가 위.
  • 수정 모달: 신규 src/screens/RegisterErrorModal.tsx (RegisterTable.tsx와 같은 계층 — 등록 화면 전용 표시 컴포넌트). blocked 행마다 registerTableHeaders(contentType) 라벨로 세 입력 + 현재 reasons 노출. 입력 key는 행 index 고정(값 포함 금지 — 포커스 유실 방지). 내부 draft 상태를 갖고 저장 시에만 부모로 올린다(취소 = draft 폐기).
  • 저장 시 모달을 닫는다. 열어둔 채 재검증하면, 방금 valid가 된 행이 편집 도중 모달 목록에서 사라지는 어긋남이 생긴다. 닫은 뒤에도 blocked가 남아 있으면 배너가 그대로 있으므로 "오류 수정"으로 다시 열어 이어서 고칠 수 있다.
  • '직접수정' 태그: RegisterTable에 editedIndexes: ReadonlySet<number> prop을 추가해 상태 배지 옆에 병기한다. ValidatedRow에 표시용 필드를 얹지 않는 이유는 그 타입이 검증 라이브러리의 계약이기 때문 — 표시 관심사는 컴포넌트 prop으로 분리한다.

기각한 대안

  • 편집 결과를 textarea 원본 JSON에 되쓰기 — text가 바뀌면 isDirty가 켜져 재확인을 요구하고, 그 순간 오버레이의 존재 이유가 사라진다. 사용자가 손으로 쓴 포맷도 파괴한다.
  • 테이블 셀 인라인 편집(모달 없이) — 소유자가 2026-07-30에 "배너 → 모달"로 확정. 좁은 화면에서 4열 테이블에 입력 3개를 넣으면 가로 스크롤이 심해지는 실무 이유도 같은 방향.
  • ValidatedRow에 edited: boolean 추가 — 분류 함수가 편집 이력을 알아야 해서 순수 분류 책임이 오염된다. 오버레이 키 존재 여부로 이미 유도 가능.
  • 제출 결과 화면에 "미수정 오류 N건" 표기 — 이슈가 명시적으로 범위 밖으로 뺐다(별건).

4작업 단계

  1. 검증 함수 2단 분리 — parseRegistrationInput(파싱·스키마) / classifyRegistrationRows(hanziCounts 집계 + 행 분류)를 export하고, validateRegistrationInput은 두 함수를 잇는 합성 함수로 축소한다. 시그니처·반환 타입·기존 테스트 전부 불변. src/lib/registerValidation.ts
  2. 분리 검증 테스트 — 기존 validateRegistrationInput 테스트가 그대로 통과하는지 확인하고, classifyRegistrationRows 직접 호출 케이스를 추가한다(정상/오류/중복 분류, 입력 내 중복이 배열 전체 기준으로 재집계되는 것, zh·generic 분기). src/lib/registerValidation.test.ts
  3. 편집 오버레이 상태 + 파생 파이프라인 재구성 — editOverlay: Record<number, ParsedWord> 도입, parseResult(파싱) → effectiveWords(오버레이 덮어쓰기) → rows(분류) 2단 memo로 교체. submittableRows·validCount· blockedCount·duplicateRows·duplicateKey를 새 rows 기준으로 옮기고, handleConfirm에서 text !== confirmedText일 때 오버레이를 비운다. src/screens/RegisterScreen.tsx
  4. 오류 수정 모달 컴포넌트 — blocked 행 목록 + 행별 세 입력(key는 index 고정) + reasons 표시, registerTableHeaders(contentType) 라벨 분기, 저장/취소 버튼, Escape = 취소. 내부 draft 상태만 갖는 제어 컴포넌트. src/screens/RegisterErrorModal.tsx (신규) 진행 메모: 플랜의 3·5단계(RegisterScreen 상태·배선)는 4단계(모달)를 먼저 만든 뒤 한 번에 편집했다 — 같은 파일을 두 번 헤집지 않으려는 순서 조정이고 결과물은 동일하다.
  5. 오류 배너 + 모달 배선 — blockedCount > 0이면 배너 렌더(중복 배너 위, 제출 비차단), "오류 수정" 클릭 시 모달 열기, 저장 시 원본 대비 diff로 오버레이 갱신(같으면 엔트리 삭제) 후 모달 닫기. src/screens/RegisterScreen.tsx
  6. '직접수정' 태그 — RegisterTable에 editedIndexes prop을 추가해 상태 배지와 병기 렌더. src/screens/RegisterTable.tsx, src/screens/RegisterScreen.tsx
  7. 스타일 — .register-error-banner(red 틴트, 중복 배너와 같은 레이아웃 토큰), .register-modal-backdrop/.register-modal/모달 행·입력, .register-tag--edited를 기존 .register-status 계열 톤에 맞춰 추가. src/index.css
  8. 화면 테스트 — 배너 노출/소멸, 모달 편집→저장 재검증(valid 승격·duplicate 전환·여전히 blocked), 입력 내 중복 짝 행 동반 해소, 태그 표시 범위, 포커스 유지, 오버레이 초기화(재확인)/유지(탭 변경), 전 행 blocked 해소 시 제출 활성화, 제출 payload가 편집값 기준인지 고정. src/screens/RegisterScreen.test.tsx
  9. 문서 개정 — docs/design-prd.md §6에 오류 배너·수정 모달·'직접수정' 태그 사양을 신설하고 "검증 규칙" 불릿의 "오류 행은 제출에서 제외" 서술을 개정, §9 결정 로그에 행 추가. docs/design-prd.md

5리스크

리스크영향완화책
모달 입력이 타이핑마다 포커스를 잃음 사실상 사용 불가 — 한 글자씩 다시 클릭해야 함 입력 key를 행 index로 고정(값 포함 금지). 포커스 유지 자체를 DOM 테스트로 고정한다.
오버레이 index가 행 구성과 어긋남 엉뚱한 행에 편집값이 덮어씌워짐 index 기반 오버레이는 parseResult가 유효한 동안만 의미가 있다 — text !== confirmedText 재확인 시 초기화. 탭 변경은 파싱을 건드리지 않아 유지.
편집으로 중복 서명이 바뀌었는데 이전 확인이 유효한 것으로 남음 확인 없이 중복이 제출에 포함됨 기존 duplicateKey(표제어 정렬·조인) 비교 방식을 그대로 쓴다 — 편집된 rows에서 파생되므로 서명이 바뀌면 자동으로 재확인이 요구된다. 테스트로 고정.
새 배너 클래스가 기존 중복 배너 선택자를 오염 RegisterScreen.test.tsx:313의 중복 배너 단언이 오류 배너로도 통과 .register-error-banner로 클래스를 완전히 분리(레이아웃 토큰만 공유).
validateRegistrationInput 분리 중 동작 드리프트 기존 검증 규칙이 조용히 달라짐 기존 테스트를 한 줄도 고치지 않은 채 통과시키는 것을 분리의 합격 기준으로 삼는다(순수 리팩터).
'직접수정' 태그가 상태 배지를 가림 제출 여부 판단 정보가 사라짐 대체가 아니라 병기 — 상태 배지는 항상 먼저 렌더한다.

6테스트 계획

  • npm test — 기존 registerValidation.test.ts를 수정 없이 통과시키는 것이 함수 분리의 합격 기준. 실패하면 분리가 동작을 바꾼 것이다.
  • classifyRegistrationRows 단위 테스트 — ParsedWord[]를 직접 넣어 정상/오류/중복 분류, 입력 내 중복이 배열 전체 기준으로 재집계되는지, zh·generic 분기를 고정.
  • 화면: blocked 행이 있으면 오류 배너 + "오류 수정" 버튼이 뜨고, 제출 버튼은 비활성화되지 않는다(정상 행이 하나라도 있을 때).
  • 화면: 모달에서 병음을 올바른 값으로 고치고 저장 → 그 행이 정상으로 승격, 오류 배너가 사라지고, 테이블에 직접수정 태그가 상태 배지와 함께 노출된다.
  • 화면: 표제어를 시트에 이미 있는 값으로 고치면 중복으로 전환되고 중복 확인 배너가 다시 뜬다(이전 확인이 무효화).
  • 화면: 같은 한자 두 행이 모두 blocked인 상태에서 한 행만 고치면 손대지 않은 짝 행의 "입력 내 중복" 오류도 함께 풀리고, 직접수정 태그는 고친 행에만 붙는다.
  • 화면: 모달 표제어 입력에 포커스를 준 뒤 값을 바꿔도 document.activeElement가 같은 입력 노드로 유지된다(index key 회귀).
  • 화면: 편집 후 textarea를 고쳐 다시 "확인"하면 오버레이가 초기화되어 태그가 사라진다. 탭 선택만 바꾸면 태그·편집값이 유지된다.
  • 화면: 전 행 blocked라 비활성이던 제출 버튼이 모달 수정으로 valid가 생기면 활성화된다.
  • 화면: 제출 payload(registerWords 인자)가 편집 후 값이고 blocked 행은 여전히 제외되며, 키는 hanzi/pinyin/meaning 그대로다 (와이어 계약·'직접수정' 미전송 고정).
  • 화면: 취소하면 편집값이 버려지고 테이블·배너가 그대로다.
  • npm run lint(oxlint) · npm run build(tsc -b + vite build) 그린.

7완료 조건

  • blocked 행이 있으면 인라인 오류 배너 + "오류 수정" 버튼 노출 — 중복 배너와 공존(오류 배너가 위), 제출을 막지 않고, blocked가 0이 되면 사라진다(별도 dismiss 없음).
  • 오류 수정 모달 — blocked 행마다 세 값 편집 + 현재 사유 표시, registerTableHeaders(contentType) 라벨 분기, 저장/취소.
  • registerValidation.ts에서 분류 단계가 ParsedWord[]를 받는 classifyRegistrationRows로 분리되고, validateRegistrationInput의 동작·시그니처·기존 테스트가 불변이다.
  • 저장 시 편집값으로 배치 전체 재검증 — valid 승격 시 제출 포함, duplicate 전환 시 중복 재확인 요구, 여전히 blocked면 사유 갱신, 입력 내 중복 해소 시 손대지 않은 짝 행도 함께 풀림.
  • 수정된 행에 '직접수정' 태그(상태 배지와 병기, 표시 전용).
  • 모달 입력 필드가 타이핑 중 포커스를 유지한다(index 고정 key).
  • 편집 오버레이가 isDirty 재확인 시 초기화되고, 탭 변경 시 유지된다.
  • 제출 payload는 편집 후 값 기준 — blocked 제외 규칙·와이어 계약 불변(Worker 변경 없음).
