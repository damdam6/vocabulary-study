등록 일반화 — 등록 화면 generic 대응 (스키마 파서·오배치 감지·라벨 분기)

damdam6/vocabulary-study 브랜치 feat/96-register-screen-generic ← main 라벨 enhancement 2026-07-28

1요약

등록 화면(RegisterScreen/RegisterTable)과 클라이언트 검증(registerValidation.ts)이 zh 전제로 고정돼 있어 generic 프로필의 콘텐츠(자유 텍스트 표제어·선택적 보조 표기)를 등록할 수 없다. 이 이슈는 docs/plans/registration-generalization.md §5 작업 C로, 파서에 contentType 분기를 추가해 generic 붙여넣기 스키마(term/note/meaning)를 기존 zh 스키마(hanzi/pinyin/meaning)와 나란히 지원하고, 두 스키마 간 오배치를 명시적으로 감지하며, 화면이 contentType에 따라 placeholder·테이블 헤더·lang 속성을 분기하도록 만든다. 와이어 계약(hanzi/pinyin/meaning 운반자)과 zh 경로 동작은 완전히 불변으로 유지한다. 홈 진입 링크(#78)와 Worker 재검증(작업 B)은 이 이슈 범위 밖이다.

2현황 분석

  • src/lib/registerValidation.ts는 contentType 개념이 전혀 없다. HANZI_RE(registerValidation.ts:27)가 한자 유니코드 기본 블록만 허용하도록 하드코딩돼 있고, extract()(registerValidation.ts:40)는 항상 hanzi/pinyin/meaning 소스 필드만 읽는다. validateRegistrationInput(registerValidation.ts:50)의 행 단위 검증(registerValidation.ts:76-97)은 한자 범위 검사·병음 필수·isPinyinMatch(pinyin-pro) 일치 검사를 무조건 적용한다 — 시그니처에 contentType 인자 자체가 없다.
  • src/screens/RegisterScreen.tsx:159가 validateRegistrationInput(confirmedText, existingHanziInTab)를 2개 인자로 호출한다. textarea placeholder(RegisterScreen.tsx:243)는 zh 예시 JSON을 하드코딩한다.
  • src/screens/RegisterTable.tsx:23-25가 테이블 헤더를 "한자"/"병음"/"뜻"로 하드코딩하고, RegisterTable.tsx:30의 A열 <td>가 lang="zh-Hans"를 무조건 부여한다.
  • src/App.tsx:88는 <RegisterScreen onGoHome={...} />를 contentType prop 없이 렌더한다. 같은 파일의 StudyScreen 렌더(App.tsx:74)는 이미 contentType={getStoredProfile()?.contentType ?? 'zh'} 패턴으로 프로필 저장소에서 값을 읽어 내려준다 — 재사용할 기존 관례.
  • src/lib/contentLabels.ts가 #80/#92로 정착시킨 패턴이 하나 있다: 컴포넌트 테스트 하네스가 이 저장소에 없으므로(확인 결과 src/screens/*.test.tsx 파일이 존재하지 않음) contentType별 표시 분기(라벨·placeholder·lang)를 전부 순수 함수로 뽑아 vitest로 고정한다. modeChipLabel·headwordLang·mode2Hint·mode2Placeholder가 이미 이 패턴으로 Mode1Card.tsx/Mode2Card.tsx/StudyScreen.tsx에서 쓰이고 있다.
  • src/lib/registerApi.ts:44-49의 ParsedWord/RegisterRequest 와이어 타입은 이미 hanzi/pinyin/meaning 운반자 필드명을 쓴다. 이 파일과 Worker(worker/)는 이 이슈 완료 조건에서 명시적으로 "변경 없음"이다 — 즉 파서의 내부 표현(ParsedWord/ValidatedRow)과 와이어 필드명은 그대로 두고, 오직 붙여넣기 JSON의 소스 필드명(zh: term/note ↔ generic: hanzi/pinyin)만 갈아끼우면 된다.

3설계

  • validateRegistrationInput에 세 번째 인자 contentType: ContentType = "zh"를 추가한다. 기본값을 "zh"로 두면 기존 2-인자 호출(zh 테스트 15건)이 코드 수정 없이 그대로 통과해 플랜 §6의 "zh 회귀 기준선"을 시그니처 자체가 보장한다.
  • extract(raw, contentType)가 contentType별 소스 필드를 골라 읽는다 — zh는 hanzi/pinyin/meaning, generic은 term/note/meaning. 결과는 항상 동일한 ParsedWord 운반자 형태(hanzi/pinyin/meaning)로 채워지므로 그 아래 화면·API 계층은 필드명 분기를 몰라도 된다(플랜 §3.3 요구사항 그대로).
  • 스키마 오배치 감지는 파싱·버전·words 배열 형태 검사 다음, 행 단위 검증 전에 top-level 오류로 처리한다. 규칙: 대상 프로필이 "generic"인데 body.contentType !== "generic"이면 "zh 스키마로 보임" 오류, 대상 프로필이 "zh"인데 body.contentType === "generic"이면 "generic 스키마로 보임" 오류. "필드 없음 = zh" 원칙(플랜 §3.1)을 지키기 위해 zh 프로필 쪽 검사는 정확히 "generic" 값일 때만 차단한다 — 다른 임의 문자열까지 차단하면 기존 zh 킷 출력을 오분류할 위험이 있다(대안 기각).
  • 행 단위 검증은 contentType별로 완전히 분리한 분기로 작성한다 — zh 분기는 기존 코드를 그대로 옮기고(사유 문구·순서 불변), generic 분기만 신규 작성(term/meaning 비공백 강제, note 선택, "표제어"류 문구, 한자 범위·pinyin-pro 검사 없음). 공통 로직을 억지로 추출하는 대안은 기각한다 — 사유 문구·검사 항목 자체가 서로 다른데 강제로 결합하면 플래그투성이 단일 함수가 돼 오히려 zh 회귀 위험을 키운다.
  • 표시 전용 분기(테이블 헤더 3종, A열 lang, textarea placeholder)는 registerValidation.ts가 아니라 contentLabels.ts에 추가한다 — #80/#92가 정착시킨 관례를 그대로 따르고, A열 lang은 신규 함수 없이 기존 headwordLang()을 재사용한다(StudyScreen 표제어와 의미가 같다).
  • App.tsx는 StudyScreen과 동일한 한 줄 패턴(getStoredProfile()?.contentType ?? 'zh')으로 RegisterScreen에 contentType을 내려준다. RegisterScreen 내부에서 getStoredProfile을 직접 호출하는 대안은 기각한다 — 화면이 프로필 저장소를 직접 알게 돼 StudyScreen과의 일관성이 깨진다.

5리스크

리스크영향완화책
zh 행 단위 검증 로직을 옮기는 과정에서 문구·순서가 미묘하게 달라짐 zh 회귀 기준선(플랜 §6 핵심 요구) 위반 기존 코드 블록을 리팩토링 없이 그대로 zh 분기로 이동, generic 분기는 별도로 신규 추가
오배치 감지 조건을 과하게 엄격히 짜면 contentType 필드가 "generic"도 "zh"도 아닌 임의 값일 때 정상 zh 입력까지 차단 zh 사용자가 이유 없이 등록 차단됨 zh 프로필 검사는 "body.contentType === 'generic'인 경우만 차단"으로 한정 — 그 외 값은 전부 zh로 간주(§3.1 "필드 없음 = zh")
RegisterTable의 React key(${'{'}row.hanzi{'}'}-${'{'}index{'}'})가 generic 표제어(공백·특수문자 포함 가능)에도 재사용됨 없음 — index가 함께 있어 충돌 불가(사전 확인 결과 안전) 해당 없음, 확인 사항으로만 기록
