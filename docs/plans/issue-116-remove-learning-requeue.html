#116기능 개선 (규칙 제거)

학습 중 오답 재삽입 제거 — 방금 본 단어가 같은 세션에 다시 나온다

damdam6/vocabulary-study 브랜치 feat/116-remove-learning-requeue ← main 라벨 enhancement 2026-07-28

1요약

학습 중 오답 시 같은 문제를 세션 큐 맨 뒤에 1회 재삽입하던 v1 규칙(PRD §6.2, #18)을 제거한다. 방금 정답까지 본 단어를 같은 세션에서 다시 묻는 것은 단기 기억으로 맞히게 만들어 학습 효과가 없고, 그렇게 오른 D/E 카운트가 실제 암기 없이 졸업(3회)을 앞당기기 때문이다. 오답 시 기록 API를 쏘지 않는 현행 동작은 그대로라 그 단어는 학습 중 상태로 남고 다음 세션에 자연히 재출제된다 — 세션 간 간격이 곧 재학습 간격이다. 부수 효과로 세션 큐가 시작 시점에 고정되어 진행도 분모(queue.length)가 세션 중 절대 변하지 않으며, 재삽입만을 위해 존재하던 #113의 세션 상한 스레딩(홈 → App → 학습 화면 → startSession)이 통째로 불필요해진다.

2현황 분석

재삽입은 순수 리듀서 한 곳에서만 일어난다. src/lib/studySession.ts:98-101의 recordAnswer가 학습 중 오답일 때 큐 맨 뒤에 복사본을 push한다:

  • src/lib/studySession.ts:11-14 — StudyQuestion이 SessionQuestion<WordEntry>에 requeued: boolean을 더한 형태. 이 플래그의 유일한 용도가 "재재삽입 금지(1회만)" 판정이다.
  • src/lib/studySession.ts:98-101 — 조건 !question.requeued && state.queue.length < state.limit일 때 [...state.queue, { ...question, requeued: true }]. 큐가 길어지므로 진행도 분모가 판정 시점에 즉시 +1 된다.
  • src/lib/studySession.ts:23-27, 50-53 — StudySessionState.limit과 startSession(questions, limit = SESSION_CAP). limit은 오직 위 재삽입 상한 판정에만 쓰인다(모듈 내 다른 참조 없음).
  • 복습 오답은 :87-93에서 먼저 갈라져 review-fail effect만 내고 큐를 건드리지 않는다 — 이번 변경과 무관하며 그대로 유지된다.

#113이 깐 limit 배선은 재삽입 전용이다. 큐 구성용 상한은 홈이 buildSessionQueue(..., sessionLimit)로 직접 쓰고 있어(src/screens/HomeScreen.tsx:84-87) 이번 변경과 무관하다. 반면 아래 경로는 재삽입이 사라지면 전부 죽은 코드가 된다:

  • src/screens/HomeScreen.tsx:16 — onStart: (queue, limit) => void의 둘째 인자. handleStart가 sessionLimit을 함께 올린다(:84-87).
  • src/App.tsx:29, 46-50, 78 — sessionLimit 상태와 그것을 StudyScreen에 내려주는 limit prop.
  • src/screens/StudyScreen.tsx:33-34, 47-48 — limit prop과 startSession(queue, limit). 이 화면에서 limit의 다른 용도는 없다(진행도는 session.queue.length를 쓴다, :128-129).

기존 테스트에서 재삽입 커버리지는 src/lib/studySession.test.ts에 집중돼 있다: :72-77(requeued=false 초기화), :115-128(재삽입·분모 증가), :130-139(1회 제한), :141-149(SESSION_CAP 상한), :157-207(#113 limit 상한 describe 5건), :209-227(재삽입 포함 집계 흐름). 화면 레벨에는 src/screens/HomeScreen.test.tsx:109-136의 limit 스레딩 테스트가 있다. SESSION_CAP 자체는 sessionQueue·homeStats에서 계속 쓰이고, "시트 설정이 큐 길이를 좌우한다"는 계약은 src/lib/sessionQueue.test.ts:187·src/lib/homeStats.test.ts:60이 독립적으로 지키고 있다 — 즉 studySession에서 limit을 걷어내도 설정 반영 커버리지는 남는다.

문서에 재삽입이 서술된 곳: docs/PRD.md:160(§6.1 "§6.2 오답 재삽입 제외" 단서), :164(§6.2 재삽입 규칙 본문), :330(§12 결정표 "학습 중 오답의 세션 내 재출제 = 큐 뒤에 1회"), docs/design-prd.md:93(§4.1 "진행도 분모는 동적"), :121(§4.5 진행 규칙), :195(§9 결정 로그 "진행도 분모 = 동적 증가"), docs/PRD-general.md:103(세션 규칙 요약에 "학습 중 오답 1회 재삽입"). 코드 주석 중에는 src/lib/sessionQueue.ts:12(SESSION_CAP 설명이 "§6.2 재삽입 상한도 같은 값" 이라고 말한다)도 사실과 어긋나게 된다. docs/plans/*.html은 당시 기록물이라 손대지 않는다.

Worker(worker/)에는 재삽입 개념이 없다 — 큐 구성·진행은 전부 클라이언트 책임(PRD §7.3)이라 이번 변경은 프런트엔드에 갇힌다.

3설계

규칙을 제거하는 것이 곧 설계다. recordAnswer의 학습 중 오답 분기는 "집계만 올리고 effect는 none"으로 축소된다 — 복습 오답 분기와 대칭이 되고, 큐를 만드는 코드가 startSession 한 곳으로 줄어 세션 큐는 시작 시점에 고정된다.

  • requeued 플래그 제거 → StudyQuestion이 SessionQuestion<WordEntry>와 동일해진다. 인터페이스를 지우는 대신 export type StudyQuestion = SessionQuestion<WordEntry> 별칭으로 남긴다 — Mode1Card/Mode2Card/RecordEffect가 이 이름을 쓰고 있어(src/screens/Mode1Card.tsx:10, Mode2Card.tsx:9) 도메인 이름을 유지하는 편이 변경 폭이 작다.
  • limit 제거 범위: StudySessionState.limit → startSession의 인자 → StudyScreen의 prop → App의 sessionLimit 상태 → HomeScreen.onStart의 둘째 인자까지, 재삽입만을 위해 존재하던 배선을 끝까지 걷어낸다. 홈이 buildSessionQueue에 넘기는 sessionLimit은 그대로 둔다(큐 구성 상한은 여전히 시트 설정).
  • 기록 규칙 불변: 학습 중 오답은 여전히 API 호출 없음(effect: none), 복습 오답은 review-fail. 오답 단어가 학습 중으로 남아 다음 세션에 다시 나오는 것은 getWordState의 기존 동작이라 추가 코드가 필요 없다.

기각한 대안 (이슈 본문의 결정 계승):

  • 최소 간격 재삽입(k문제 뒤 배치) — 짧은 세션에서는 여전히 금방 재노출되고, "정답을 방금 봤다"는 단기 기억 문제는 간격으로 해소되지 않는다.
  • 재삽입 유지 + 재삽입분 카운트 미기록 — 재삽입 정답도 D/E에 기록되는 현 구조를 바꾸는 복잡도 대비, 세션에서 빼고 다음 세션에 맡기는 쪽이 단순하고 일관적이다.
  • limit 배선만 남겨두기 — StudyScreen이 쓰지 않는 prop을 유지하면 "세션 상한이 학습 화면에도 걸린다"는 잘못된 신호가 남는다. 이슈의 완료 조건이 "상한 판정 코드 제거"를 명시하므로 죽은 배선까지 걷어낸다.

5리스크

리스크영향완화책
limit 배선을 홈까지 걷어내면서 시트 문제수 설정(#102·#113)이 큐 구성에서도 빠지는 사고 세션 문제 수가 항상 60으로 되돌아감 — 사용자에게 바로 보이는 회귀 HomeScreen.handleStart의 buildSessionQueue(..., sessionLimit) 인자는 손대지 않는다. 4단계 테스트가 "큐 길이 = 35"로 이를 화면 레벨에서 고정하고, sessionQueue.test.ts·homeStats.test.ts의 limit 테스트가 그대로 남아 이중으로 지킨다.
StudyQuestion을 별칭으로 바꾸면서 Mode1Card/Mode2Card의 타입이 깨질 가능성 빌드 실패 두 카드는 question.word/mode/isReview만 읽고 requeued를 참조하지 않는다(Mode1Card.tsx:13, Mode2Card.tsx:13). 별칭 유지로 import 경로도 그대로다. 8단계 npm run build가 최종 확인.
학습 효과 자체의 변화 — 틀린 단어를 같은 날 다시 보지 못한다 단기적으로 세션당 노출 횟수 감소 이슈에서 소유자가 명시적으로 결정한 트레이드오프(단기 기억으로 맞히는 정답이 D/E를 부풀리는 문제가 더 크다). 오답 단어는 학습 중 상태로 남아 다음 세션 큐 우선순위에 자연히 들어온다.
진행도 분모가 고정되면서 기존 UI 가정과 어긋날 여지 표시 오류 StudyScreen은 이미 session.queue.length를 그대로 렌더하므로(:128-129) 코드 변경이 필요 없다 — 분모가 변하지 않게 될 뿐이다. design-prd §4.1 서술만 개정한다.

6테스트 계획

  • vitest — 재출제 없음: 학습 중 오답(모드1·모드2 각각) 후 next.queue가 입력 큐와 길이·내용 모두 동일하고, 그 단어가 큐 뒤쪽에 추가되지 않는다.
  • vitest — 분모 불변: 학습 중 문제 여러 개를 전부 오답으로 소진하는 동안 매 판정마다 state.queue.length가 시작값 그대로이고, 종료 시 wrong이 문제 수와 같다.
  • vitest — effect 불변: 학습 중 오답 { kind: "none" }, 학습 중 정답 answer(isReview:false), 복습 정답 answer(isReview:true), 복습 오답 review-fail + 큐 길이 불변 — 네 케이스가 그대로 통과.
  • vitest — 집계: 정오가 섞인 세션의 correct/wrong 합이 문제 수와 일치하고, 큐 소진(isDone) 시점이 시작 큐 길이와 정확히 맞는다.
  • vitest — applyWordUpdate·gradeMode2: 무수정 통과(재삽입과 무관한 기존 계약 보존).
  • vitest(jsdom) — 홈: settings.sessionLimit: 35 환경에서 "학습 시작" 시 onStart가 큐 하나만 인자로 받고, 그 큐 길이가 35(시트 설정 상한)다.
  • 전역: npm test(전체 스위트), npm run lint(oxlint — 미사용 import/변수 검출), npm run build(tsc -b 타입 체크 포함) 모두 그린.
  • 수동 확인: grep -rn "requeue" src/ 결과 없음, git status에 worker/ 변경 없음.

7완료 조건

  • 학습 중 오답 후 같은 세션에서 그 단어가 다시 출제되지 않는 테스트 통과
  • 진행도 분모(queue.length)가 세션 내 불변임을 오답 다수 시나리오로 검증
  • requeued 플래그·큐 복사 분기·limit 상한 판정 제거, 기존 재삽입 테스트를 새 규칙 테스트로 대체
  • 복습 오답 동작 불변(재출제 없음 · review-fail effect) 테스트 유지
