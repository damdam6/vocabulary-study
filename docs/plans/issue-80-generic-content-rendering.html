1요약

#78에서 contentType("zh" | "generic")이 프로필 → App → StudyScreen까지는 배선됐지만, 실제 렌더링 분기는 아직 없다 — StudyScreen.tsx:118은 data-content-type 속성만 부여할 뿐이고 Mode1Card/Mode2Card는 contentType prop 자체를 받지 않는다. 이 이슈는 그 마지막 배선을 완성한다: lang="zh-Hans"·한자 글자수 적응 크기·모드2 입력란의 중국어 속성·모드 칩 문구를 contentType === 'zh'일 때만 적용하고, generic은 중립 렌더링(고정 크기·속성 미부여·중립 문구)으로 분기한다. 아울러 B열(보조 표기, 코드상 word.pinyin) 빈칸 시 그 줄을 숨기는 규칙을 콘텐츠 타입 무관 공통으로 적용한다. 진행/채점 로직(studySession.ts)은 손대지 않는다.

B열(보조 표기) 데이터: WordEntry.pinyin: string(src/lib/api.ts:134, worker 쪽 worker/lib/words.ts:30-35에서 시트 B열을 pinyin: pinyin ?? ""로 파싱). 빈칸은 null이 아니라 ""로 들어오므로 숨김 조건은 word.pinyin !== ''. 항상 렌더링되는 지점은 Mode1Card.tsx:36과 Mode2Card.tsx:40 두 곳뿐.

contentType 배선 현황(#78): App.tsx:74가 getStoredProfile()?.contentType ?? 'zh'로 StudyScreen에 전달, StudyScreen.tsx:32 prop 선언 주석에 "실제 렌더링 분기…는 후속 이슈"라고 명시돼 있다(= 이 이슈). Mode1Card/Mode2Card는 아직 contentType prop이 없다 — 이번에 추가해야 한다. HomeScreen.tsx:141의 profile?.contentType === "zh" && 분기가 이미 이 저장소의 zh/generic 분기 관례다.

테스트 하네스 제약: vitest.config.ts는 순수 node 환경이고 React 컴포넌트 테스트 설정(jsdom·RTL)이 이 저장소에 전혀 없다(hanziSize.ts:2-5 주석이 같은 이유로 스케일 로직을 lib로 뽑았다고 명시). 새 테스트 인프라 도입은 이 이슈 범위 밖이므로, 텍스트/속성 결정 로직만 hanziSize.ts와 같은 패턴으로 lib 순수 함수로 뽑아 vitest로 고정하고, JSX 배선 자체는 수동(dev 서버) 확인으로 보완한다.

src/lib/studySession.ts 전체 확인 결과 lang/한자 크기/병음 렌더링/칩 문구 관련 코드가 전혀 없음을 확인 — 진행·채점 로직은 이 변경의 영향권 밖이다.

3설계

  • 필드명은 그대로 둔다. WordEntry.hanzi/pinyin을 headword/secondary 등으로 리네이밍하는 건 worker 파서·시트 계약·다수 파일에 번지는 별도 리팩토링이며 이슈 완료 조건에도 없다 — 이번 변경은 순수 렌더링 분기다.
  • 결정 로직은 src/lib/contentLabels.ts로 분리 (신규) — modeChipLabel·headwordLang·mode2Hint·mode2Placeholder 4개 순수 함수. hanziSize.ts와 동일한 이유(테스트 하네스 없이도 vitest로 분기를 고정)로 화면 컴포넌트에 인라인 삼항 대신 이 방식을 택한다. 앞면 CSS 클래스 선택("어떤 사이즈 클래스를 쓸지")은 사소한 문자열 조립이라 Mode1Card 안에 인라인으로 남긴다(hanziFontSize 호출 자체는 zh 분기일 때만).
  • "미적용"은 속성 자체를 생략한다는 뜻으로 해석한다(이슈 완료 조건 문구 그대로) — generic일 때 lang/placeholder는 대체 문자열을 넣는 게 아니라 undefined로 둬 React가 속성을 렌더링하지 않게 한다.
  • 모드2 힌트 문구("이 뜻의 한자를 입력하세요")도 분기 대상에 포함한다 — 이슈 완료 조건엔 없지만 완전히 같은 범주의 zh 하드코딩이라, 빼면 generic 프로필에서 "한자를 입력하세요"라는 명백히 틀린 문구가 남아 이슈의 근본 취지(§7 "generic은 일반 텍스트로 표시")를 어긴다. 완료 조건에 항목을 추가해 추적한다.
  • generic 앞면 크기: 글자 수 적응 스케일은 "zh 전용 유지"(이슈 본문 명시)이므로 generic은 고정 크기 CSS 클래스 .flip-hanzi--generic(48px, letter-spacing: normal — 한자 전용 자간 0.04em은 라틴 문자에 불필요)를 신설한다. 대안으로 84/64/52 스케일을 generic에도 그대로 쓰는 안을 검토했으나, "영어 표현" 같은 긴 구는 84px에서 카드 밖으로 넘칠 위험이 커 기각 — 고정값이 더 안전하고 단순하다. 긴 텍스트 대비 overflow-wrap: break-word를 .flip-hanzi 공통 규칙에 추가(zh 짧은 한자엔 시각적 영향 없음).
  • 모드2 입력란 placeholder: generic은 undefined(placeholder 없음) — 힌트 문구가 이미 안내하므로 대체 placeholder를 새로 지어내지 않는다(이슈에 없는 문구를 임의로 확정하지 않기 위함).
  • B열 빈칸 숨김은 콘텐츠 타입과 무관한 공통 규칙이라 contentLabels.ts가 아니라 각 컴포넌트에 {word.pinyin !== '' && (...)} 인라인 가드로 둔다 — Mode2Card.tsx:42의 기존 wrongAnswer !== '' 가드와 동일 관용구라 일관성이 있다.

5리스크

리스크영향완화책
컴포넌트 테스트 하네스 부재로 실제 JSX 분기(속성 렌더링 자체)는 자동 테스트로 못 잡음회귀를 vitest만으로 100% 보장 못함텍스트/속성 결정 로직은 contentLabels.ts 유닛 테스트로 고정하고, JSX 배선은 npm run dev 수동 확인(zh·generic 양쪽)으로 보완
generic 앞면 고정 크기(48px) 값은 이번 구현에서 처음 확정하는 디자인 결정소유자가 다른 값을 원할 수 있음단일 CSS 규칙이라 조정 비용 낮음, design-prd에 결정 근거 명시
모드2 힌트 문구 변경은 완료 조건에 없던 범위 확장범위 외 변경으로 보일 수 있음현황 분석·설계에서 근거 명시, 완료 조건에 별도 항목으로 추가해 추적
