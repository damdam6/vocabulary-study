1요약

홈 화면 맨 아래에 저강조 텍스트 링크로 숨어 있는 진입 액션 2개(단어 등록 › · 프로필 전환)를 헤더 상단 우측의 라운드 사각 아이콘 버튼 2개로 승격한다. 수정 버튼(노트+연필)은 경량 팝오버 메뉴를 열고 이번 이슈에서는 옵션이 "단어 등록" 하나뿐이며(“1회 문제 수 수정”은 후속 작업 E 소관 — 비활성 자리 표시를 두지 않는다), 사람 버튼(상반신 실루엣)은 확인 단계 없이 즉시 프로필 전환한다. 아이콘은 외부 라이브러리 없이 인라인 SVG로 자체 제작하고, 팝오버의 바깥 탭 닫힘은 커스텀 드롭다운이 이미 쓰는 pointerdown 패턴(#66)을 그대로 재사용한다. 세션 큐·현황 집계·Worker·등록 화면 로직은 건드리지 않는다 — 두 액션의 위치 이동이 이 작업의 전부다. 문서는 docs/design-prd.md §3을 개정한다.

근거 플랜: docs/plans/session-limit-and-home-utils.md §3.4 · §5 작업 D (2026-07-28 확정, Q5·Q6 소유자 결정 반영).

2현황 분석

홈 화면의 현재 구조 — src/screens/HomeScreen.tsx는 위에서 아래로 날짜(:84) → 타이틀 "오늘의 학습"(:85) → 프로필명(:86) → 현황 카드 3개 (:106-121) → 스페이서(:123) → 미전송 인디케이터(:125-130) → "오늘 세션 · n문제"(:132) → "학습 시작" 버튼(:134-138) 순으로 렌더한다. 그 아래 마지막 두 요소가 이번에 옮길 대상이다.

  • 단어 등록 링크 — src/screens/HomeScreen.tsx:140-143. onNavigateRegister prop을 호출하는 <button class="home-register-link">. 주석이 명시하듯 "오늘 학습 상태와 무관하게 항상 노출"이며, #100(등록 일반화 작업 D)에서 contentType === "zh" 조건이 제거돼 전 프로필에 무조건 노출된다.
  • 프로필 전환 링크 — src/screens/HomeScreen.tsx:145-148. onSwitchProfile prop 호출. 실제 동작은 src/App.tsx:55-58의 switchProfile() — clearPassword()로 저장된 비밀번호·프로필 캐시를 지우고 로그인 화면으로 되돌린다. 확인 다이얼로그 없음.
  • 스타일 — src/index.css:849-865. 두 링크가 한 규칙을 공유한다 (align-self:center · margin-top:14px · 0.85rem · --text-muted, hover/active에 --accent-light).
  • App과의 계약 — src/App.tsx:64-70이 onStart· onNavigateRegister·onSwitchProfile 세 prop을 넘긴다. 유틸 바는 같은 두 prop을 그대로 소비하므로 App은 손댈 필요가 없다.

재사용할 팝오버 패턴 — src/components/Dropdown.tsx:29-50이 이미 "열려 있을 때만 document에 리스너를 붙이고, pointerdown 대상이 컨테이너 밖이면 닫는다 + Escape로 닫고 트리거로 포커스 복귀" 패턴을 갖고 있다(#66에서 click → pointerdown 전환, 터치 환경 대응). 이번 메뉴는 선택(listbox)이 아니라 액션(menu)이라 Dropdown 컴포넌트를 그대로 쓰지는 못하지만, 닫힘 로직은 같은 모양으로 옮긴다.

테스트 인프라 현황(중요) — 이 레포에는 컴포넌트 테스트가 하나도 없다. vitest.config.ts는 test: {}로 환경 지정이 없어 기본 node에서 돌고, 25개 테스트 파일 309개 테스트가 전부 순수 함수 단위 테스트다(src/lib/*.test.ts, worker/**/*.test.ts). 커스텀 드롭다운(#56)·pointerdown 전환(#66)도 테스트 없이 육안 검증으로 머지됐다. 이슈의 완료 조건 1번("유틸 바 렌더·메뉴 열림/바깥 닫힘·이동·전환 테스트")을 만족하려면 DOM 환경을 이번에 처음 들여와야 한다 — §3에서 방식을 결정한다.

참고: 완료 조건 2번의 "기존 홈 테스트"는 실제로는 존재하지 않는다(홈 관련 테스트는 순수 집계 로직인 src/lib/homeStats.test.ts뿐이고 이 작업의 영향을 받지 않는다). 따라서 "갱신"할 대상은 없고, 전체 스위트가 무수정으로 계속 통과하는 것이 이 조건의 실질이다.

CI — PR에는 .github/workflows/ai-review.yml(AI 코드 리뷰)만 돌고 테스트 잡은 없다 (smoke.yml은 main push 전용). 따라서 npm test·npm run build· npm run lint는 로컬에서 직접 돌려 확인한다.

3설계

3.1 컴포넌트 분리 — 유틸 바를 src/components/HomeUtilBar.tsx로 뽑는다. 아이콘 SVG 2개 + 메뉴 열림 상태 + 바깥 닫힘 이펙트 + 키보드 처리까지 합치면 60줄 남짓인데, HomeScreen은 "세션 큐 구성·현황 집계"가 본업이라 섞으면 흐려진다. src/components/Dropdown.tsx가 같은 이유로 이미 분리돼 있어 레포 관행과도 맞고, 후속 작업 E("1회 문제 수 수정" 옵션 추가)의 변경 지점이 이 파일 하나로 국소화된다. Props는 { onNavigateRegister, onSwitchProfile } — HomeScreen이 App에서 받은 두 prop을 그대로 내려보내므로 src/App.tsx는 무변경이다.

3.2 마크업·접근성

  • 헤더를 .home-header 플렉스 행으로 감싼다 — 좌측 .home-header-text(날짜·타이틀·프로필명, 기존 요소·클래스·마진 그대로) / 우측 <HomeUtilBar>, justify-content: space-between + align-items: flex-start. 참고 이미지(BERNICE)의 우상단 자물쇠 버튼과 같은 자리다.
  • 버튼 2개는 <button type="button"> + aria-label ("수정" / "프로필 전환"). 아이콘 <svg>는 aria-hidden="true"· focusable="false"로 접근성 트리에서 제외한다.
  • 수정 버튼: aria-haspopup="menu" · aria-expanded · aria-controls (useId()로 생성 — Dropdown.tsx:24와 동일 관행).
  • 메뉴: <ul role="menu"> + <li role="none"><button role="menuitem">. 옵션은 "단어 등록" 하나. 열릴 때 첫 항목에 포커스, Escape로 닫고 트리거로 포커스 복귀, ArrowDown/ArrowUp으로 항목 간 이동(지금은 1개라 사실상 no-op이지만 E에서 옵션이 늘어나도 그대로 동작), 바깥 pointerdown으로 닫힘.
  • 메뉴에서 "단어 등록"을 고르면 onNavigateRegister() 호출 + 메뉴 닫기. 사람 버튼은 메뉴 없이 곧바로 onSwitchProfile()(확인 단계 없음 — 플랜 Q5).

3.3 아이콘(인라인 SVG 자체 제작) — 외부 아이콘 라이브러리 도입 없음(플랜 §8 결정). 24×24 뷰박스에 fill="none" · stroke="currentColor" · stroke-width="1.6" · stroke-linecap/linejoin="round"로 통일해 버튼의 color만 바꾸면 hover 톤이 따라오게 한다.

  • 수정: 노트(모서리 둥근 사각 윤곽 + 안쪽 가로줄 2개) 위에 연필(대각 획 + 촉 삼각)이 겹친 형태.
  • 사람: 머리 원(circle) + 어깨 아치(path) — 상반신 실루엣.

3.5 테스트 방식 결정 — jsdom만 추가, 렌더 헬퍼는 자체 제작

  • 채택: jsdom 하나만 devDependency로 추가하고, react-dom/client의 createRoot + React 19가 react에서 내보내는 act로 마운트하는 최소 헬퍼 src/test-utils.tsx를 만든다(worker/test-utils.ts 선례와 같은 자리·같은 이름 규칙). 환경은 테스트 파일 상단 // @vitest-environment jsdom 도크블록으로 해당 파일에만 적용해, 나머지 순수 함수 테스트 23개 파일은 지금처럼 빠른 node 환경을 유지한다 (vitest.config.ts는 무변경).
  • 기각: @testing-library/react(+@testing-library/dom) 추가 — 편하지만 이 레포는 아이콘 라이브러리조차 "기능 하나에 의존성 추가는 과함"으로 기각한 곳이고(플랜 §8), 필요한 API가 "마운트·클릭·이벤트 디스패치·언마운트"뿐이라 20줄 헬퍼로 충분하다. 다만 구현 중 act 경고나 비동기 처리로 헬퍼가 커지면 이 판단을 뒤집고 @testing-library/react를 도입한다(리스크 표 참조).
  • 기각: 테스트 없이 육안 검증만(#56·#66 선례) — 이슈 완료 조건 1번이 명시적으로 테스트를 요구한다.
  • jsdom에는 PointerEvent 생성자가 없을 수 있으므로, 바깥 닫힘 테스트는 new MouseEvent('pointerdown', { bubbles: true })를 document.body에 디스패치한다 — 리스너는 타입 문자열로 매칭되므로 실제 구현 경로를 그대로 탄다.

3.6 문서 개정 범위 — 이슈 완료 조건은 docs/design-prd.md §3만 요구하지만, docs/PRD.md §9.1(:255)·§9.3(:267)이 "학습 시작 아래 저강조 텍스트 링크"를 등록 화면의 진입 경로로 못박고 있어 이 작업 뒤엔 사실과 어긋난다. 두 줄짜리 진입 경로 문장만 정정해 문서가 거짓말하지 않게 한다(기능 PRD의 다른 내용·구조는 불변 — 세션 상한·API는 후속 작업 A·B·E 소관).

5리스크

리스크영향완화책
레포 첫 DOM 테스트 — jsdom+act 자체 헬퍼가 예상보다 손이 많이 갈 수 있음 (act 경고, 비동기 상태 갱신, PointerEvent 부재) 구현 지연, 테스트가 실제 동작이 아니라 헬퍼를 검증하게 될 위험 pointerdown은 MouseEvent로 디스패치(리스너는 타입 문자열 매칭). 헬퍼가 30줄을 넘거나 act 경고를 못 잡으면 §3.5 결정을 뒤집어 @testing-library/react를 도입하고 플랜에 사유를 적는다 — 완료 조건이 테스트 존재를 요구하지, 특정 라이브러리 부재를 요구하지 않는다
헤더를 플렉스 행으로 감싸면서 기존 여백이 틀어짐 — .home-profile-name의 margin:0 0 20px이 현황 카드와의 간격을 만들고 있고, 프로필이 없으면 그 여백도 사라진다 홈 레이아웃 미세 회귀(현황 카드가 붙거나 뜸) 텍스트 요소들의 클래스·마진을 그대로 둔 채 감싸기만 한다. 프로필 없을 때의 간격 동작은 현행과 동일하게 유지(이번 이슈에서 고치지 않음). 육안 확인 시 프로필 있음/없음 두 경우 모두 본다
후속 작업 E와의 경계 — 수정 메뉴에 "1회 문제 수 수정"을 미리 넣고 싶은 유혹 반쪽 UI(동작하지 않는 옵션)로 머지 이슈·플랜 §5가 명시적으로 금지 — 옵션은 "단어 등록" 하나만. 비활성 자리 표시도 두지 않는다. 테스트에서 메뉴 항목 수가 1인지 단언해 회귀를 막는다
role="menu" 접근성 구현이 어중간해질 수 있음(포커스 트랩·roving 미구현) 키보드 사용자 경험 저하 완료 조건은 "기본 보장" — 항목이 실제 <button>이라 Tab이 통하고, 열릴 때 첫 항목 포커스 · Escape 복귀 · 화살표 이동까지 구현한다. 포커스 트랩은 옵션 1개 메뉴에 과해 도입하지 않는다(플랜에 명시)
등록 화면 진입 경로가 유틸 바 뒤로 한 단계 깊어짐(탭 → 메뉴 → 옵션) 등록 동선이 길어졌다는 체감 소유자 확정 사항(플랜 Q6·§3.4)이라 그대로 따른다. 대신 메뉴는 팝오버라 탭 2번이면 끝나고, "항상 노출" 성질은 유지된다
package-lock.json 변경(jsdom 및 전이 의존성) diff 크기 증가, 리뷰 노이즈 devDependency 1개만 추가(npm i -D jsdom) — 런타임 번들·배포에는 영향 없음을 PR 본문에 명시한다

6테스트 계획

  • 기준선 회귀 — npm test: 기존 25파일 309테스트가 무수정으로 계속 통과해야 한다 (이 작업은 순수 로직을 건드리지 않는다). 신규 DOM 테스트는 // @vitest-environment jsdom 도크블록으로 격리되어 나머지 파일의 실행 환경을 바꾸지 않는다.
  • 유틸 바 렌더 — 버튼 2개가 각각 aria-label="수정"·aria-label="프로필 전환"로 존재하고, 아이콘 <svg>는 aria-hidden="true"다.
  • 메뉴 열림 — 수정 버튼 클릭 시 role="menu"가 나타나고 aria-expanded가 true로 바뀐다. role="menuitem"은 정확히 1개이며 라벨은 "단어 등록"이다(작업 E 옵션 선반영 금지의 회귀 방어).
  • 바깥 pointerdown 닫힘 — 메뉴가 열린 상태에서 document.body에 pointerdown을 디스패치하면 메뉴가 사라진다. 메뉴 안쪽에 디스패치하면 유지된다.
  • Escape 닫힘·포커스 — Escape keydown으로 닫히고 document.activeElement가 수정 버튼으로 돌아온다. 열릴 때는 첫 메뉴 항목이 포커스를 받는다.
  • 액션 배선 — "단어 등록" 항목 클릭 → onNavigateRegister 1회 호출 + 메뉴 닫힘. 사람 버튼 클릭 → onSwitchProfile 1회 호출(메뉴는 열리지 않음).
  • 하단 링크 부재 — HomeScreen 렌더 결과에 .home-register-link·.home-switch-profile-link가 없다. 텍스트 "단어 등록 ›"·"프로필 전환"이 하단 영역에 남아 있지 않은지도 함께 확인.
  • 학습 상태 무관 노출 — fetchWords가 아직 응답하지 않은 로딩 상태에서도 유틸 바 버튼 2개가 렌더된다(등록 진입의 기존 성질 승계).
  • 타입·번들 — npm run build(tsc -b + vite build) 통과. npm run lint(oxlint) 무경고.
  • 육안 확인 — npm run dev + cmux 브라우저. localStorage에 vocab-study:password·vocab-study:profile을 직접 시딩해 홈 진입 후: 아이콘 2개가 헤더 우상단에 나란히 · 탭하면 메뉴가 우측 정렬로 열림 · 화면 아무 데나 탭하면 닫힘 · "단어 등록" → 등록 화면 · 사람 아이콘 → 로그인 화면 복귀 · 하단에 링크 없음. 모바일 기준 뷰포트(390×844)에서 44px 이상 터치 타겟인지도 본다.
