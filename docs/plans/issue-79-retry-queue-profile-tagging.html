#79기능 개선

재시도 큐 프로필 태깅 — 현재 프로필 필터 flush + 영구 실패(4xx) 폐기

damdam6/vocabulary-study 브랜치 feat/79-retry-queue-profile-tagging ← main 라벨 enhancement 2026-07-27

1요약

재시도 큐(src/lib/retryQueue.ts) 엔트리에 적재 시점의 활성 프로필 id를 태깅하고, flush는 현재 로그인한 프로필의 항목만 FIFO로 전송하며 다른 프로필의 항목은 건드리지 않고 보존한다. 태그 없는 레거시 항목은 읽기 시점에 현재 프로필 소속으로 승격한다(#43의 무태그 kind 승격과 같은 접근). src/lib/api.ts의 postAnswer·postReviewFail은 상태 코드를 실은 ApiError를 던지도록 바꿔, flush가 4xx(영구 실패)는 그 항목만 폐기하고 다음 항목을 계속 전송하며, 네트워크 예외·5xx는 기존처럼 중단·잔여 유지로 분기하게 한다. 홈 미전송 인디케이터(getRetryQueueLength)도 현재 프로필 항목만 카운트하도록 맞춘다.

2현황 분석

src/lib/retryQueue.ts:21-23 RetryQueueEntry는 {kind, record}뿐 — 프로필 정보가 없다. readQueue()(retryQueue.ts:31-44)는 태그 없는 항목을 {kind:"answer", record}로 승격하는 #43 시절 로직만 있고 profileId 개념이 없다.

flushRetryQueue()(retryQueue.ts:86-115)는 큐 전체를 프로필 구분 없이 FIFO로 순회하며, catch 블록 하나가 while 루프 전체를 감싸 첫 실패에서 무조건 중단한다 — 4xx(영구 실패)와 네트워크/5xx(일시 실패)를 구분하지 않아, 프로필 전환 후 이전 프로필 기록이 새 프로필 시트로 전송되면 404(단어 없음)로 큐 머리가 영구히 막히거나, 표제어가 우연히 같으면 다른 시트에 오기록된다.

enqueue()(retryQueue.ts:58-64)는 인자로 받은 엔트리를 그대로 append — 활성 프로필을 조회하지 않는다. getRetryQueueLength()(retryQueue.ts:54-56)는 프로필 구분 없이 배열 길이를 그대로 반환해, 홈 인디케이터(src/screens/HomeScreen.tsx:58,125-130)가 다른 프로필의 미전송분까지 카운트한다.

src/lib/api.ts:156-166 postAnswer와 :179-187 postReviewFail은 비정상 응답에 new Error(...)를 던져 상태 코드를 구분할 수 없다. 활성 프로필은 getStoredProfile()(api.ts:41-49)로 조회 가능 — id 필드를 포함한 PublicProfile(api.ts:34-39)이 로그인/단어 조회 응답에서 캐시된다(#78·#77 완료).

서버 측 4xx 근거: worker/routes/answer.ts 비활성 모드 400, 단어 없음 404; worker/routes/review-fail.ts 바디 파싱 실패 400, 단어 없음 404 — 모두 재시도해도 영원히 같은 결과이므로 폐기 대상. Google Sheets API 오류 등은 잡히지 않는 예외나 5xx로 표면화되어 일시 실패로 취급해야 한다.

3설계

엔트리 태깅: RetryQueueEntry 두 variant 모두에 profileId?: string를 추가한다. enqueue()가 getStoredProfile()?.id를 내부에서 조회해 새 엔트리에 태깅한다 — enqueueAnswer/enqueueReviewFail 외부 시그니처는 그대로 두어 StudyScreen.tsx 호출부를 건드리지 않는다(적재 시점에 활성 프로필을 알아내는 책임은 retryQueue 모듈 내부로 국한).

레거시 승격: readQueue(currentProfileId)로 시그니처를 바꿔, profileId가 없는 엔트리를 currentProfileId로 채워 반환한다(#43의 kind 없는 항목 승격과 동일한 map 패턴). 승격은 읽기마다 재계산되지만, flush가 성공/폐기로 큐를 실제로 변경할 때 saveQueue로 영속화되므로 다음 읽기부터는 태깅된 상태로 고정된다. getRetryQueueLength()·flushRetryQueue() 모두 이 함수로 자기 프로필의 id를 넘겨 호출한다.

필터링 flush: 큐를 인덱스로 순회하며 entry.profileId !== profileId인 항목은 건드리지 않고 인덱스만 증가시켜 넘어간다(다른 프로필 항목 보존). 일치하는 항목만 전송을 시도한다. await 도중 새 항목이 append될 수 있으므로(기존 로직과 같은 이유), 항목 제거 시마다 readQueue(profileId)로 재조회한 뒤 해당 인덱스를 제거하고 저장한다 — enqueue는 항상 뒤쪽에 append만 하므로 앞쪽 인덱스는 안정적이다.

실패 분류: api.ts에 상태 코드를 담는 ApiError extends Error를 추가하고 postAnswer/postReviewFail이 이를 던지도록 바꾼다(에러 메시지 포맷은 유지 — 기존 api.test.ts의 toThrow("404") 스타일 검증과 호환). flush에서 err instanceof ApiError && err.status >= 400 && err.status < 500이면 해당 항목만 제거(폐기)하고 같은 인덱스에서 계속(다음 항목이 그 자리로 밀려옴); 그 외(네트워크 예외, 5xx)면 즉시 반환해 그 항목과 잔여를 큐에 그대로 유지 — 기존 "첫 실패 중단" 시맨틱을 실패 성격별로 정밀화한 것.

기각한 대안: enqueueAnswer/enqueueReviewFail에 profileId 인자를 추가해 StudyScreen.tsx가 명시적으로 넘기는 방식 — getStoredProfile()이 이미 동기 조회 가능해 모듈 내부에서 해결 가능하므로, 호출부 3곳(App.tsx/StudyScreen.tsx/HomeScreen.tsx)을 건드리지 않는 현재 설계가 더 단순하다.

4작업 단계

  1. api.ts에 상태 코드를 싣는 ApiError 클래스를 추가하고, postAnswer·postReviewFail이 new Error(...) 대신 new ApiError(message, response.status)를 던지도록 바꾼다. 메시지 포맷("POST /api/answer 실패 (${status})")은 그대로 유지한다. src/lib/api.ts
  2. RetryQueueEntry 두 variant에 profileId?: string를 추가한다. src/lib/retryQueue.ts
  3. readQueue()를 readQueue(currentProfileId: string | undefined)로 바꿔, kind 승격과 함께 profileId가 없는 엔트리를 currentProfileId로 채워 반환한다. src/lib/retryQueue.ts
  4. enqueue()가 getStoredProfile()?.id를 조회해 새 엔트리에 profileId를 태깅하고, readQueue(profileId)로 기존 큐를 읽어 append하도록 바꾼다. enqueueAnswer/enqueueReviewFail 시그니처는 유지. src/lib/retryQueue.ts
  5. getRetryQueueLength()가 getStoredProfile()?.id를 조회해 readQueue(profileId) 결과 중 entry.profileId === profileId인 것만 세도록 바꾼다(외부 시그니처는 인자 없이 유지). src/lib/retryQueue.ts
  6. flushRetryQueue()를 재작성: 활성 프로필 id를 조회하고, 인덱스 기반 순회로 프로필 불일치 항목은 건너뛰고(보존), 일치 항목만 전송 시도 — 성공/4xx 폐기는 해당 인덱스를 재조회 후 제거·저장하고 계속, 네트워크 예외·5xx는 즉시 반환해 중단·유지. src/lib/retryQueue.ts
  7. 테스트 확장: (a) api.test.ts — postAnswer/postReviewFail 실패가 ApiError 인스턴스이고 status가 응답 상태 코드와 일치하는지, (b) retryQueue.test.ts — 프로필 태깅 적재, 프로필 불일치 항목 보존(현재 프로필만 전송), 무태그 레거시 항목 현재 프로필 승격, 4xx 폐기 후 다음 항목 계속 전송, 5xx·네트워크 예외 중단·유지(기존 회귀 포함), getRetryQueueLength 프로필 필터링. src/lib/api.test.ts, src/lib/retryQueue.test.ts
  8. npm test(vitest)와 npm run build(tsc -b + vite build)로 회귀·타입 검증.

5리스크

리스크영향완화책
레거시 승격이 "잘못된" 프로필로 배정될 가능성 — 무태그 시절 항목의 원 소속을 알 방법이 없음드물게 다른 프로필 시트로 오기록될 수 있음(단일 프로필 운영 중이던 사용자 기준으로는 발생 안 함)PRD-general §8이 명시한 기각 트레이드오프 — #43과 동일하게 "유실 방지 > 완전 정확성" 우선. 다중 프로필 실사용 전 배포이므로 실질 영향 없음
flush 중 재조회(readQueue) 인덱스 정합성 — enqueue가 append 외 동작을 하게 되면 인덱스가 어긋날 수 있음잘못된 항목 제거enqueue는 항상 끝에 append만 함을 코드로 보장(현재도 동일 불변식에 의존) — 테스트로 "flush 중 새 항목 적재" 케이스 유지
ApiError 도입이 기존 .rejects.toThrow("404") 스타일 단언에 영향기존 api.test.ts 깨짐메시지 포맷 그대로 유지 + Error 상속이라 toThrow 매처 호환 확인

6테스트 계획

  • npm test 전체 통과 — 기존 retryQueue.test.ts 회귀 케이스(중간 실패 중단, 재진입 가드, flush 중 신규 적재, review-fail 혼재 등) 그대로 유지되는지.
  • 신규: 프로필 A로 적재한 answer/review-fail 엔트리가 프로필 B 활성 상태에서 flush해도 큐에 남고 전송되지 않는지, B 소속 항목만 전송되는지.
  • 신규: profileId 없는(레거시) 엔트리가 현재 활성 프로필로 승격되어 flush 시 전송·제거되는지.
  • 신규: 400/404 응답(ApiError 4xx) 수신 시 해당 항목이 큐에서 제거되고 다음 항목이 계속 전송되는지.
  • 신규: 500 응답·네트워크 예외(TypeError)에서는 그 항목과 잔여가 모두 보존되고 중단되는지(4xx와 구분).
  • 신규: getRetryQueueLength()가 현재 활성 프로필 항목만(승격된 레거시 포함) 카운트하는지.
  • npm run build — tsc 타입 검증(RetryQueueEntry profileId 추가·ApiError 도입에 따른 컴파일 오류 없는지).

7완료 조건

  • 프로필 A에서 적재 → 프로필 B 로그인 후 flush 시 A 항목 보존·미전송, B 항목만 전송
  • 4xx 응답 항목 폐기 후 다음 항목 계속 전송
  • 네트워크 실패/5xx에서 중단·잔여 유지(기존 동작 보존)
  • 무태그 레거시 항목이 현재 프로필로 승격되어 유실 없음
  • 홈 인디케이터 카운트가 현재 프로필 기준
  • 기존 재시도 큐 테스트 회귀 없음 — npm test·npm run build 모두 통과
