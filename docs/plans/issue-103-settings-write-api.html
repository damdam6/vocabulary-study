#103기능 개선

세션 설정 — POST /api/settings 신설 ('_정보' 탭 문제수 쓰기)

damdam6/vocabulary-study 브랜치 feat/103-settings-write-api ← main 라벨 enhancement 2026-07-28

1요약

세션 문제 수 플랜(docs/plans/session-limit-and-home-utils.md §3.3, §5 작업 B)의 쓰기 절반이다. POST /api/settings를 신설해 인증된 프로필의 시트 '_정보' 탭에 문제수 값을 쓴다 — 정수 1~500 엄격 검증(아니면 400), 탭 없으면 빈 탭 생성, 문제수 행 없으면 첫 빈 행에 추가, 있으면 그 행 B열만 갱신. 행 탐색·쓰기 계획은 worker/lib/settings.ts의 순수 함수로 두어 병렬 진행 중인 작업 A(읽기 파서)와 파일을 공유하되 함수 충돌을 피한다. 클라이언트(src/) 변경은 없다 — 호출자는 작업 E가 만든다.

2현황 분석

  • 설정을 쓸 경로가 없다: Worker 라우트는 words·answer·review-fail·tabs·register 5개뿐이고(worker/index.ts:45-88), 시트 쓰기는 answer(batchUpdateValues)·review-fail·register(updateValues)가 전부 단어 탭 대상이다. '_정보' 탭을 만지는 코드는 아직 없다.
  • Sheets 래퍼는 재사용 가능: worker/lib/sheets.ts에 필요한 프리미티브가 모두 있다 — getSheetTitles(sheets.ts:51, 전 탭 제목), addSheet(sheets.ts:61, 탭 생성 — register가 사용), getValues(sheets.ts:39), updateValues(sheets.ts:68, valueInputOption=RAW 내장). 신규 Sheets 코드는 불필요.
  • 탭 존재 확인에 주의: getWordTabTitles(worker/lib/words.ts:12-15)는 _ 접두 탭을 걸러내므로 '_정보' 존재 확인에 쓰면 항상 "없음"으로 판정된다 — 반드시 raw getSheetTitles를 써야 한다. 반대로 이 필터 덕에 '_정보' 탭은 생성되는 순간부터 words 출제(worker/routes/words.ts:17)·tabs 목록(worker/routes/tabs.ts:7)·등록 헤더 원본 선택(worker/routes/register.ts:54)에서 자동 제외된다(플랜 Q1 — 제외 코드 변경 0).
  • 탭 생성 선례: register의 createTab(worker/routes/register.ts:58-74)은 titles 포함 확인 → addSheet → 헤더 행 복사 순서다. '_정보'는 헤더 없는 키-값 탭이므로 헤더 복사 단계만 뺀 같은 흐름을 쓴다.
  • POST 검증 선례: answer 라우트(worker/routes/answer.ts:25-56)가 "JSON 파싱 실패 400 → 필드 파서 null 반환 시 한국어 문구 400" 패턴의 기준이다. index.ts 배선은 라우트별 try/catch + console.error + 500 JSON(worker/index.ts:54-61) 패턴.
  • 테스트 인프라: register 스위트(worker/routes/register.test.ts:26-70)가 mock fetch로 titles·addSheet·values GET/PUT을 흉내 내고 PUT 호출 전수(putCalls)로 range를 검증한다. sheetId 격리는 worker/index.sheet-isolation.test.ts:54-79의 "URL 전수 기록" 패턴. 이 둘을 조합해 신규 스위트를 만든다.
  • worker/lib/settings.ts는 아직 없다: 작업 A(읽기 파서)가 병렬 브랜치에서 같은 파일을 만들 예정 — 이슈 지시대로 쓰기 계획 함수를 별도 함수로 담아 충돌을 블록 단위로 국한한다.

3설계

  • 순수 로직(worker/lib/settings.ts 신설): 상수 SETTINGS_TAB = "_정보", SESSION_LIMIT_KEY = "문제수", SESSION_LIMIT_MIN = 1, SESSION_LIMIT_MAX = 500 + 쓰기 계획 함수 planSessionLimitWrite(rows, limit). A1:B 읽기 결과에서 A열을 트림 정확 일치로 탐색해 — 있으면 { range: "B{행}", values: [[limit]] }(그 행 B열만), 없으면 첫 빈 행 번호로 { range: "A{행}:B{행}", values: [["문제수", limit]] }를 반환한다.
  • "첫 빈 행" 판정: A·B가 모두 빈 첫 행(트림 기준). A만 비고 B에 값이 있는 비정상 행은 건너뛴다 — "다른 행·열 불가침" 불변식이 문구 해석보다 우선(값을 덮어쓰지 않기 위해). 빈 행이 없으면 데이터 마지막 행 + 1.
  • 라우트(worker/routes/settings.ts 신설): ① JSON 파싱 실패 → 400 "invalid JSON body"(answer 선례) ② 비객체·sessionLimit 누락·비수·비정수·1~500 밖 → 400, 문구에 허용 범위 명시("sessionLimit은 1~500 사이의 정수여야 합니다") ③ getSheetTitles로 '_정보' 존재 확인 → 없으면 addSheet(빈 탭 — 헤더 쓰기 없음, rows는 빈 배열로 확정) / 있으면 getValues(A1:B — 헤더 행 없는 탭이므로 1행부터) ④ planSessionLimitWrite → updateValues(RAW 내장) ⑤ 응답 { "sessionLimit": n }(반영값).
  • 배선(worker/index.ts): register 블록 뒤에 POST /api/settings 분기 — 기존 try/catch·console.error("[POST /api/settings]")·500 { error: "failed to save settings" } 패턴 그대로. 인증·프로필 해석은 기존 Bearer 블록이 이미 감싼다(worker/index.ts:16-36) — 추가 코드 0.
  • 기각한 대안: ⓐ 탭 존재를 getValues 400(catch)으로 판정(findWordRow 선례) — 읽기 1회를 아끼지만, 쓰기 API에서 무관한 400을 "탭 없음"으로 오인하면 탭 생성으로 이어지므로 register의 명시적 titles 확인을 따른다. ⓑ appendValues로 행 추가 — append는 "표"의 끝을 Sheets가 추정해 의도치 않은 위치에 쓸 수 있으므로, 행 번호를 계산해 명시 range로 updateValues하는 편이 불가침 검증에 안전. ⓒ 검증 로직을 lib로 분리 — answer가 파서를 라우트 파일에 두는 선례를 따르고, lib에는 이슈가 지정한 행 탐색·쓰기 계획만 둔다.
  • 재시도 큐 비대상: 실패는 그대로 4xx/5xx 응답 — 클라이언트 오류 표시는 작업 E 소관, Worker에는 관련 코드가 없다.

4작업 단계

  1. worker/lib/settings.ts 신설 — 상수 4개(SETTINGS_TAB·SESSION_LIMIT_KEY·MIN·MAX)와 planSessionLimitWrite(rows, limit) 순수 함수(트림 일치 탐색 → B열 갱신 계획 / 첫 빈 행 추가 계획). 작업 A 병렬 대비 쓰기 쪽만. worker/lib/settings.ts
  2. 라우트 신설 — handleSettingsPost: JSON 400 → sessionLimit 정수 1~500 검증 400(범위 명시 문구) → titles 확인 → addSheet(빈 탭)/getValues(A1:B) → plan → updateValues(RAW) → { sessionLimit } 응답. worker/routes/settings.ts
  3. index.ts 배선 — POST /api/settings 분기(기존 try/catch·로그·500 패턴), import 추가. worker/index.ts
  4. 테스트 신설 — register.test.ts 모킹 패턴 + sheet-isolation URL 전수 패턴: 400 경계(비객체·누락·비정수·0·501·잘못된 JSON)와 경계 성공(1·500), 세 경로(탭 생성/행 추가/B열 갱신)의 putCalls range 전수 검증(다른 셀 불가침·헤더 미복사), 트림 일치, 2프로필 sheetId 격리, '_정보' 존재 시 words·tabs 자연 제외 회귀. worker/routes/settings.test.ts
  5. PRD §7.3 명세 추가 — POST /api/settings 블록을 §7.3 끝에 append(작업 A의 words 응답 수정과 충돌 최소화): 요청/검증/세 경로 동작/RAW/응답/재시도 큐 비대상. docs/PRD.md
  6. 전체 검증 — npm test(기존 스위트 무수정 통과 + 신규 스위트 그린), npm run build(tsc) 통과, src/ diff 없음 확인. package.json scripts (실행만) — 328 테스트·oxlint·tsc 빌드 그린, src/ diff 없음 확인

5리스크

리스크영향완화책
작업 A가 같은 파일(worker/lib/settings.ts)을 병렬 생성 — 머지 충돌 확정적나중에 머지되는 쪽이 충돌 해소 필요이슈 지시대로 쓰기 계획 함수·상수만 담아 함수 블록 단위 충돌로 국한 — 해소가 기계적(두 블록 병기)
탭 존재 확인을 getWordTabTitles로 하는 실수 — _ 필터에 걸려 매번 addSheet 시도 → "already exists" 500두 번째 저장부터 전부 실패raw getSheetTitles 사용 + "탭이 이미 있으면 addSheet 없이 갱신" 테스트로 고정
행 추가가 A만 빈 비정상 행(B에 값)을 덮어쓸 가능성불가침 위반 — 값 유실빈 행 판정을 A·B 모두 빈 행으로 강화, 해당 케이스 단위 검증
PRD §7.3을 작업 A도 수정(words 응답) — 문서 충돌머지 시 수동 해소섹션 끝 신규 블록 append만 — words 블록 본문은 건드리지 않음
숫자를 RAW로 쓰면 셀 타입이 숫자 — 읽기 파서(작업 A)와의 호환없음 — values.get은 문자열 "30"으로 반환, 파서는 정수 문자열 허용 계약(플랜 §3.1)쓰기 값은 number 그대로(answer의 카운트 쓰기 선례), 테스트 기대값도 number로 고정

6테스트 계획

  • npm test(vitest run) — 기존 스위트가 무수정으로 전부 통과(동작 보존), 신규 worker/routes/settings.test.ts 그린.
  • 인증: Authorization 헤더 없음 → 401 (라우트가 인증 블록 안에 배선됐는지 확인).
  • 400 경계: 잘못된 JSON · 비객체 바디("30") · {}(누락) · 1.5 · "30"(문자열) · 0 · 501 → 전부 400, 오류 문구에 "1~500" 포함. 경계 성공: 1·500 → 200.
  • 탭 생성 경로: '_정보' 없는 시트 → addSheet 1회 + PUT은 A1:B1 [["문제수", n]] 단 1건(헤더 복사 PUT 없음), 응답 { sessionLimit: n }.
  • 행 추가 경로: '_정보'에 다른 키 행만 존재 → PUT A2:B2 1건, 기존 행 데이터 불변(모르는 키 불가침).
  • B열 갱신 경로: 문제수 행이 중간에 존재(위아래 다른 행) → PUT B{행} 1건만 — putCalls 전수 비교로 다른 셀 불가침 증명. 트림 일치(" 문제수 ")도 같은 행 갱신.
  • sheetId 격리: 2프로필 PROFILES 구성에서 프로필 B로 호출 → mock fetch URL 전수가 B의 sheetId만 포함.
  • '_정보' 자연 제외 회귀: '_정보' 탭이 존재하는 상태에서 GET /api/tabs 목록·GET /api/words 조회 대상에 '_정보'가 없음(기존 _ 규칙 — 신규 제외 코드 없이).
  • npm run build — tsc 타입 체크 통과.
