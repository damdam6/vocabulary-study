중국어 음성 API의 클라이언트 전송을 구현한다

damdam6/vocabulary-study 브랜치 feat/141-chinese-audio-client-transport ← feat/ch-sound 라벨 enhancement 2026-09-16

1요약

브라우저용 TTS 전송 모듈을 추가해 기존 apiFetch의 Bearer·401·성공 콜백 계약을 그대로 사용하면서 POST /api/tts를 한 번만 호출한다. 응답은 공개 TTS 오류 또는 검증된 MP3 Blob으로 정규화하며, 외부 취소와 20초 준비 제한을 fetch부터 스트림 바디 완료까지 하나의 수명으로 묶는다. Audio·Blob 캐시·자동재생·React·재시도 큐는 후속 이슈의 책임으로 남기고, 실제 서버·키·R2 없이 제어 가능한 fetch/stream/clock 더블로 계약을 검증한다.

2현황 분석

  • 모든 인증 API의 공통 입구인 src/lib/api.ts:90-103은 저장된 비밀번호를 Bearer로 붙이고, 401이면 자격 정보 삭제와 로그인 복귀 핸들러를, 성공 응답이면 기존 성공 핸들러를 호출한 뒤 원본 Response를 반환한다. TTS도 이 함수를 거쳐야 이 앱 전역 계약이 보존된다.
  • src/lib/api.ts:75-83의 성공 핸들러는 이미 쌓인 학습 기록 flush를 촉발할 수 있지만, 이는 정상 API 응답의 기존 동작이다. src/lib/ttsApi.ts가 retryQueue를 import하거나 TTS 실패를 적재해서는 안 된다.
  • 선행 #135가 src/lib/ttsTypes.ts:15-39에 요청, 허용 오류 코드, 성공 진단의 가능한 조합, TtsTransportFailure, TtsTransport 포트를 정의했다. 새 모듈은 이 타입을 재정의하지 않고 구현해야 하며, STORED/PRESENT와 GENERATED/SAVED|UNCONFIRMED 외 조합은 잘못된 응답이다.
  • 서버 계약은 성공 시 audio/mpeg과 X-TTS-Source, X-TTS-Storage, X-TTS-Pronunciation, X-TTS-Revision을 반환한다(docs/architecture/chinese-tts-audio.md:166-183). 현재 클라이언트에는 이 헤더와 스트림을 검증해 TtsAudioResponse로 만드는 구현이 없다.
  • src/lib/wordsApi.ts:41-48와 src/lib/registerApi.ts:31-84는 apiFetch를 재사용하고 비정상 응답을 호출자용 오류로 바꾸는 선례지만, JSON 전체 읽기만 사용한다. TTS는 Content-Length가 없거나 거짓이어도 실제 스트림 누적값으로 빈 바디와 4MiB 초과를 판정해야 하므로 별도 bounded reader가 필요하다.
  • Vitest는 node 환경에서 fetch·localStorage를 전역 더블로 주입하는 패턴을 쓴다(src/lib/api.test.ts:21-39, src/lib/wordsApi.test.ts:5-21). 이슈 전용 테스트도 실제 네트워크 대신 Response, ReadableStream, fake timer를 제어할 수 있다.

3설계

경계선택한 설계
공개 함수와 실패src/lib/ttsApi.ts에 기존 TtsTransport 포트를 만족하는 전송 함수를 두고, 예상 실패는 기존 TtsTransportFailure 형태로 reject한다. 새 오류 enum이나 서버 타입을 복제하지 않는다.
요청허용된 text와 정의된 경우의 pinyin만 새 객체로 구성해 JSON POST한다. provider·profile·음색·URL 등 원본 객체의 다른 값은 전송할 수 없게 하고, 자동 재요청은 만들지 않는다.
deadline·취소호출 시작 시 내부 AbortController 하나를 만들고 외부 signal과 20초 timer를 연결한다. 이미 취소된 입력은 fetch 전에 중단하며, deadline은 헤더 수신이 아니라 스트림 읽기와 진단 검증이 끝난 뒤에만 해제한다. 대기 중인 reader도 abort와 경쟁시키고 종료 경로에서 timer·외부 listener·reader를 정리한다.
바디 상한arrayBuffer()로 전체를 먼저 할당하지 않고 reader chunk마다 누적 크기를 검사해 4MiB를 넘기기 전에 실패·취소한다. 유효한 과대 Content-Length는 조기 거부 힌트로만 사용하고, 누락·비정상·작게 거짓인 값은 신뢰하지 않은 채 실제 바이트로 최종 판정한다.
성공 검증media type이 audio/mpeg인지, 실제 바디가 1바이트 이상 4MiB 이하인지, 네 진단 헤더가 허용 값이며 source/storage 조합이 가능한지, revision이 비어 있지 않은지 확인한 뒤 audio/mpeg Blob과 진단을 반환한다. 계약에 HTTP 헤더가 없는 billedCharacters는 추정하지 않는다.
오류 검증비정상 HTTP 응답의 공개 { error, message }를 안전하게 읽고 TTS_ERROR_CODES에 있는 코드만 kind: "http"로 전달한다. JSON이 아니거나 알 수 없는 코드·메시지·성공 헤더 조합은 invalid_response, fetch 자체 실패는 network, 외부 취소는 aborted, 내부 deadline은 timeout으로 구분한다. 빈 본문 401도 먼저 apiFetch의 기존 로그아웃 부수효과를 수행하며 공개 TTS 코드를 꾸며내지 않는다.
소유 경계MP3 구조 파싱, Audio/Object URL/LRU, 요청 합치기와 질문 generation, 사용자 메시지, React 연결은 각각 #137·#142·#143 이후 이슈의 책임이다. 이번 모듈은 HTTP 전송 한 건의 수명만 소유한다.

4작업 단계

  1. TtsRequest에서 허용 필드만 직렬화하고 apiFetch("/api/tts", ...)를 정확히 한 번 호출하는 전송 진입점을 만든다. 기존 Bearer·401·성공 콜백을 우회하지 않고, 외부 signal과 내부 20초 deadline의 원인을 구분하는 요청 수명 및 공통 정리 경로를 함께 구성한다. src/lib/ttsApi.ts, src/lib/api.ts (기존 계약 참조만)
  2. 비정상 응답은 공개 JSON을 bounded하게 해석해 기존 TtsTransportFailure로 정규화한다. tts_disabled와 tts_not_configured를 다른 503과 구별하고, 알 수 없는 코드·깨진 JSON·빈 401에는 서버 오류를 발명하지 않으며 retryQueue나 자동 재시도 경로를 추가하지 않는다. src/lib/ttsApi.ts, src/lib/ttsTypes.ts (기존 타입 재사용)
  3. 성공 응답의 MIME과 TTS 진단 헤더를 허용 조합으로 검증하고, ReadableStream을 chunk 단위로 읽어 실제 1..4MiB만 audio/mpeg Blob으로 조립한다. header 수신 뒤 멈춘 바디에도 외부 취소·20초 제한이 작동하게 하며 과대·실패 시 reader를 취소한다. src/lib/ttsApi.ts, src/lib/ttsTypes.ts (성공 진단 union 참조)
  4. 실제 서버가 필요 없는 응답/스트림/clock 더블로 요청·정상 진단·HTTP 오류·MIME·빈/과대 바디·거짓 Content-Length·fetch 및 바디 읽기 취소/timeout·정리 계약을 고정한다. 테스트용 응답 생성기는 전용 테스트 파일 안에 두어 공유 fixture와 후속 이슈의 파일 충돌을 피한다. src/lib/ttsApi.test.ts, src/lib/api.test.ts (공통 콜백 회귀 선례 참조)
  5. 전용 테스트 후 전체 test/lint/build를 실행해 타입 포트 호환성과 기존 앱 회귀를 확인한다. 운영 설정 파일은 수정하지 않고 TTS_ENABLED=false를 유지하며, 실제 키·유료 합성·청취·모바일·R2 접근은 미검증으로 명시한다. package.json, docs/plans/issue-141-chinese-audio-client-transport.html

5리스크

리스크영향완화책
외부 취소와 20초 timer가 같은 시점에 경쟁aborted와 timeout이 비결정적으로 바뀌거나 Promise가 두 번 끝날 수 있다.첫 종료 원인을 한 번만 기록하고 단일 finalize 경로에서 timer·listener·reader를 정리하는 테스트를 둔다.
fetch 응답 뒤 body stream이 영원히 대기fetch에 signal을 전달한 것만으로는 커스텀/이상 스트림의 reader.read()가 즉시 끝난다고 보장할 수 없다.각 read를 abort 알림과 경쟁시키고 취소/timeout 테스트에 never-resolving stream을 사용한다.
Content-Length를 신뢰하거나 arrayBuffer() 후 검사헤더 누락·축소 거짓값으로 4MiB 상한을 우회하거나 과대 응답을 메모리에 먼저 적재한다.헤더는 과대 조기 거부에만 쓰고 모든 성공은 chunk 누적값으로 검사하며 초과 즉시 reader를 취소한다.
진단 헤더의 불가능한 조합을 타입 단언으로 통과예: STORED/SAVED를 정상 응답으로 오인해 후속 controller의 진단과 정책이 왜곡된다.런타임 allowlist와 source/storage 조합 검증을 테스트하고 검증 이후에만 기존 discriminated union을 구성한다.
TTS 성공 콜백과 학습 retryQueue의 책임 혼동TTS 실패가 학습 기록 큐에 들어가거나 성공 콜백 회귀를 막을 수 있다.apiFetch 성공 콜백은 유지하되 ttsApi.ts는 retryQueue를 import하지 않으며 자동 재요청이 0회인지 검증한다.

6테스트 계획

  • npm test -- src/lib/ttsApi.test.ts: text만인 요청은 pinyin을 생략하고, pinyin이 있으면 두 필드만 JSON POST되는지, apiFetch를 통해 Authorization과 정상 응답 콜백이 유지되며 fetch 호출은 1회인지 확인한다.
  • 정상 계약 fixture: STORED/PRESENT, GENERATED/SAVED, GENERATED/UNCONFIRMED 및 absent/ignored 헤더를 각각 Blob과 진단 union으로 반환하고 billedCharacters를 추정하지 않는지 확인한다.
  • 응답 방어 fixture: 잘못된/누락 MIME, null/빈 바디, 비어 있는 revision, 알 수 없는 진단값, 불가능한 source/storage 조합을 invalid_response로 거부한다.
  • 크기 fixture: Content-Length 없음, 실제보다 작은 거짓값, chunk 경계의 정확히 4MiB는 실제 누적값으로 성공하며 4MiB+1은 전부 조립하기 전에 실패하고 reader가 취소되는지 확인한다. 유효한 과대 Content-Length도 조기 거부한다.
  • 오류 fixture: 모든 공개 TTS 코드, 특히 tts_disabled/tts_not_configured가 status·code·message를 보존하고, 알 수 없는/깨진 오류 본문은 invalid_response인지 확인한다. 빈 본문 401에서는 기존 비밀번호 삭제·unauthorized handler 호출을 회귀 검증한다.
  • 취소/시간 fixture: fetch 대기 중과 body read 대기 중 각각 외부 abort는 aborted, 20초 경과는 timeout으로 끝나며, 이미 취소된 signal은 fetch 0회다. 완료·HTTP 실패·network 실패·취소·timeout마다 pending timer와 외부 abort listener가 남지 않고 재요청도 없는지 fake timer로 확인한다.
  • npm test, npm run lint, npm run build: 전체 회귀와 TypeScript의 TtsTransport 호환성을 확인한다. 실제 키·Qwen 호출·R2·청취·모바일 브라우저는 이 단계의 자동 테스트 결과로 검증됐다고 기록하지 않는다.

7완료 조건

  • src/lib/ttsApi.ts가 TtsTransport 계약을 만족하고 apiFetch로만 POST /api/tts를 호출하며 요청 바디에 text/pinyin 외 필드가 없다.
  • Bearer 첨부, 앱 401 정리·로그인 복귀, 정상 응답 콜백이 유지되고 TTS 실패가 retryQueue에 적재되거나 자동 재요청되지 않는다.
  • 공개 HTTP 오류가 기존 오류 코드로 전달되며 tts_disabled와 tts_not_configured를 호출자가 구별할 수 있다. 깨진/알 수 없는 응답은 안전하게 invalid_response가 된다.
  • audio/mpeg, 진단 헤더의 값·조합, 비어 있지 않은 실제 바디를 모두 검증한 뒤에만 기존 TtsAudioResponse 형태의 Blob을 반환한다.
  • Content-Length 누락·거짓값으로 실제 4MiB 상한을 우회할 수 없고, 과대 응답은 chunk 누적 중 즉시 중단된다.
  • fetch 중과 body read 중 외부 취소·20초 timeout이 각각 끝나며 모든 완료·실패 경로에서 timer·listener·reader가 정리된다.
  • 실제 서버 없이 계약 fixture로 전용 테스트가 통과하고 npm test, npm run lint, npm run build가 모두 성공한다.
  • Audio·Blob 캐시·자동재생·React·사용자 메시지·후속 controller를 선행 구현하지 않고, 운영 TTS_ENABLED=false와 비밀값 비노출을 유지한다.
  • PR은 feat/ch-sound를 base로 하며 변경 범위·자동 검증 결과와 실제 키·청취·모바일·R2 미검증 항목을 기록한다.
