클라이언트 상태 판정 M 파라미터화 — wordState·homeStats에 modes 인자

damdam6/vocabulary-study 브랜치 feat/75-word-state-modes-parameterization ← main 라벨 enhancement 2026-07-26

1요약

getWordState·computeHomeStats는 현재 모드가 항상 m1·m2 둘이라고 하드코딩돼 있다. PRD-general §4.1은 상태 판정을 "활성 모드 집합 M" 기준으로 일반화하므로, 두 함수에 modes 인자를 추가해 M 기준 판정으로 바꾼다. 이번 이슈에서 호출부는 전부 ["m1","m2"] 고정 주입으로 유지해 동작을 보존한다 — 실제 프로필 modes 연결은 #78(화면 프로필 배선), buildSessionQueue 자체의 출제 모드 제한은 #76(세션 큐 M 파라미터화)이 각각 후속으로 다룬다.

2현황 분석

  • src/lib/wordState.ts:36-51 getWordState(word, today) — word.m1 < 3 || word.m2 < 3이면 learning. 둘 다 ≥3인데 nextReview가 null이면(데이터 이상) reviewDue로 취급하는 자가치유 규칙, nextReview <= today면 reviewDue 아니면 reviewScheduled.
  • src/lib/homeStats.ts:20-42 computeHomeStats(words, today) — 각 단어에 getWordState를 호출해 세 상태로 분류·집계할 뿐, 자체 판정 로직은 없다.
  • 호출부는 세 곳: src/screens/HomeScreen.tsx:38 computeHomeStats(fetched, getSeoulToday()), 같은 파일 :75 buildSessionQueue(words, getSeoulToday())가 내부적으로 src/lib/sessionQueue.ts:39 getWordState(word, today)를 직접 호출한다.
  • sessionQueue.ts는 QuizMode = "m1" | "m2"(:13)와 randomMode/learningMode(:84-97)가 이미 두 모드를 하드코딩하고 있다. 이 로직 자체(출제 모드를 M으로 제한)는 이슈 #76 범위 — 이 이슈에서는 getWordState 호출 시그니처를 맞추는 최소 변경만 한다.
  • 테스트는 src/lib/wordState.test.ts(7 케이스, it.each)와 src/lib/homeStats.test.ts(4 케이스) — 둘 다 현재 modes 없이 호출한다.

3설계

  • 채택: wordState.ts에 export type Mode = "m1" | "m2"를 새로 정의하고, getWordState(word, today, modes: readonly Mode[])로 확장한다. 판정은 modes.some((m) => word[m] < 3)이면 learning — PRD §4.1 "M의 어느 한 모드라도 카운트 < 3"과 정확히 대응. 나머지(nextReview 비교, 데이터 이상 자가치유)는 그대로 둔다 — 이미 M 기준으로 맞는 로직이라 손댈 필요가 없다(§4.3에서도 이 자가치유 경로를 그대로 재사용한다고 명시).
  • Mode를 sessionQueue.ts의 QuizMode와 통합하지 않는다: sessionQueue.ts가 이미 wordState.ts를 import하므로 반대 방향 import는 순환 참조가 된다. 두 타입은 구조적으로 동일한 리터럴 유니온이라 별도 정의로도 인터페이스가 어긋나지 않는다. QuizMode 자체의 정리는 #76이 다룰 문제.
  • computeHomeStats(words, today, modes: readonly Mode[])는 자체 판정 없이 getWordState(word, today, modes)에 그대로 전달만 한다(이슈 문구 "modes 전달만"과 일치).
  • 호출부(HomeScreen.tsx, sessionQueue.ts)는 인라인 배열 리터럴 ["m1", "m2"]를 그대로 전달한다 — 컨텍스트 타이핑으로 readonly Mode[]에 맞춰 리터럴 타입이 좁혀지므로 as const가 필요 없다. 각 호출부에 후속 이슈(#76/#78) 참조 주석을 남겨 "고정 주입은 임시"임을 코드에서 바로 알 수 있게 한다.
  • 기각: 모드를 전역 설정/React 컨텍스트로 주입 — PRD-general 결정 이력("학습 로직 전달 방식")에서 이미 순수 함수 인자 방식으로 확정했다(테스트 오염 방지, lib의 React 비의존 구조 보존). 재론하지 않는다.

4작업 단계

  1. Mode 타입 추가 + getWordState에 modes 인자 추가, 판정 로직을 modes.some(...) 기반으로 교체, JSDoc을 M 기준 설명으로 갱신. src/lib/wordState.ts
  2. computeHomeStats에 modes 인자 추가해 getWordState 호출에 전달, JSDoc 갱신. src/lib/homeStats.ts
  3. getWordState 호출부에 ["m1", "m2"] 고정 전달(동작 불변) + #76 참조 주석. src/lib/sessionQueue.ts
  4. computeHomeStats 호출부에 ["m1", "m2"] 고정 전달(동작 불변) + #78 참조 주석. src/screens/HomeScreen.tsx
  5. 기존 7개 케이스에 modes: ["m1","m2"] 추가(인자 추가만으로 통과 = 동작 보존 증명) + M={m1}/{m2} 각각 학습 중·복습 대기(경계값: 단일 모드 3회 도달, nextReview null/오늘)·복습 예약 케이스 + 모드 축소 재해석 엣지(m1≥3·m2<3, nextReview null, M={m1} → reviewDue) 케이스 추가. src/lib/wordState.test.ts
  6. 기존 4개 케이스에 modes: ["m1","m2"] 추가 + modes 전달이 실제로 판정에 반영되는지 확인하는 케이스 1건(M={m1}에서만 졸업하는 단어로 홈 집계가 달라짐) 추가. src/lib/homeStats.test.ts

5리스크

리스크영향완화책
sessionQueue.ts의 고정 주입이 #76의 진짜 M 연결과 헷갈릴 수 있음#76 작업자가 이미 연결된 것으로 착각호출부에 "#76에서 실제 M으로 교체" 주석 명시
word[mode] 동적 인덱싱과 WordProgress 필드 불일치타입 에러 또는 런타임 undefined 비교Mode를 WordProgress의 수치 필드 키("m1"|"m2")와 동일하게 정의 — 컴파일러가 보증
modes 빈 배열 입력 시 .some()이 항상 false → 즉시 졸업 취급비정상 프로필 구성에서 오판정클라이언트에서 별도 검증하지 않음 — 프로필 구성 검증은 Worker profiles.ts(#70) 책임, PRD도 여기서 방어를 요구하지 않음
