#71기능 개선

인증을 프로필 해석으로 전환 — resolveProfile + 설정 오류 500 + /api/health profile 블록

damdam6/vocabulary-study 브랜치 feat/71-auth-profile-resolution ← main 라벨 enhancement 2026-07-26

1요약

#70에서 만든 worker/lib/profiles.ts(파싱·검증·폴백 합성·isolate 캐시)를 실제 인증 경로에 배선한다. isAuthorized의 단일 비밀번호 비교를 resolveProfile(request, env): Promise<Profile | null>로 다중화하고(프로필별 SHA-256 다이제스트 상수시간 비교, 첫 일치 반환), 프로필 구성 오류는 401과 구분해 /api/* 전체 500 + console.error로 관측 가능하게 하며, /api/health 응답에 profile: { id, name, modes, contentType } 블록을 추가한다. 라우트 전반의 프로필 스레딩은 후속 이슈 — 이번에는 health까지만.

2현황 분석

  • 인증: worker/lib/auth.ts:8 isAuthorized(request, env) — 단일 APP_PASSWORD의 SHA-256 다이제스트를 isolate 캐시(auth.ts:6)하고 토큰 다이제스트와 상수시간 비교(auth.ts:26), boolean 반환.
  • 게이트: worker/index.ts:14 — /api/* 전부에서 isAuthorized 실패 시 401 + WWW-Authenticate: Bearer + X-Worker-Version. index.ts:21 health 응답은 { ok, time, version }.
  • 프로필 파서(#70): worker/lib/profiles.ts:51 getProfiles — 성공만 isolate 캐시(동일 배열 참조 반환), 실패는 매 호출 ProfileConfigError(profiles.ts:39) 재던짐(fail closed). PROFILES 미설정이면 APP_PASSWORD+SHEET_ID로 default 프로필 폴백 합성(profiles.ts:84) — 둘 중 하나라도 없으면 역시 설정 오류.
  • 클라이언트: src/lib/api.ts:68 verifyPassword — health 호출에서 response.ok/401/그외만 구분. 응답 body의 필드 추가는 무영향(profile 저장은 후속 이슈 범위).
  • 스모크(#23/#67): scripts/deploy-auth-smoke.sh — wrong/none → 401, SMOKE_PASSWORD → 200을 감시하고 X-Worker-Version을 기록.
  • 테스트 제약: worker/index.test.ts:5 주석 — auth 다이제스트 isolate 캐시 때문에 파일 내 전 테스트가 같은 비밀번호를 써야 한다. worker/lib/profiles.test.ts:154 — 같은 이유로 getProfiles는 전용 블록에서만 호출. 이 규약이 이번 테스트 설계의 핵심 제약이다.

3설계

  • auth.ts — resolveProfile: getProfiles(env)를 헤더 검사보다 먼저 호출(설정 오류는 그대로 전파 — 변환은 호출자 몫). 헤더 없음/Bearer 아님 → null. 토큰 다이제스트를 1회 계산해 프로필별 비밀번호 다이제스트와 순서대로 상수시간 비교, 첫 일치 프로필 반환(유일성은 #70 구성 검증이 보장하므로 첫 일치 = 유일 일치). 불일치 순회는 항상 전 프로필을 도는 고정 비용.
  • 다이제스트 캐시 확장: { profiles, digests } 쌍을 모듈 스코프에 캐시하고 profiles 배열 참조 동일성으로 히트 판정 — getProfiles가 isolate 수명 동안 동일 참조를 반환하므로 수명이 정확히 일치한다. 시크릿 갱신은 새 Worker 버전(새 isolate) 배포이므로 stale 위험 없음.
  • index.ts 배선: /api/* 블록에서 try { resolveProfile } → ProfileConfigError면 console.error("[profiles]", err) + 500 { error: "invalid profile configuration" } + X-Worker-Version(관측성 일관), 그 외 오류는 재던짐. null이면 기존 401 계약 그대로. health는 profile: toPublicProfile(profile) 추가.
  • profiles.ts — toPublicProfile: { id, name, modes, contentType }만 추리는 헬퍼를 파서 모듈에 둔다 — "sheetId·password는 응답 금지" 불변식을 한 곳에서 보장하고, /api/words profile 블록(후속 이슈)이 재사용.
  • 계약 변경(의도): 설정 오류가 401보다 우선한다 — 깨진 구성에서는 무헤더 요청도 500. 스모크의 wrong/none 프로브가 설정 사고를 즉시 드러낸다(fail-loud). 기존 "APP_PASSWORD 미설정 → 401"은 이 이슈가 명시적으로 재정의한 동작(→ 500).
  • 기각 대안: ⓐ 헤더 검사를 먼저 하고 설정 오류를 401로 눌러두기 — 설정 사고가 비밀번호 오답으로 위장돼 관측 불가. ⓑ 비밀번호 문자열 키 Map 다이제스트 캐시 — 배열 참조 캐시보다 복잡하고 이득 없음. ⓒ toPublicProfile을 index 인라인 — 후속 이슈에서 중복 발생.
  • 테스트 전략(캐시 제약 대응): vitest는 테스트 파일마다 새 모듈 isolate이므로 구성별로 파일을 분리한다 — ① 기존 index.test.ts는 폴백 경로 스위트로 유지(완료 조건 "기존 비밀번호 로그인 동작"을 그대로 증명), ② 신규 index.profiles.test.ts는 2프로필 구성, ③ 신규 index.config-error.test.ts는 깨진 구성 전용(실패는 캐시되지 않으므로 여러 깨진 변형을 한 파일에서 검증 가능 — 단 성공 케이스 금지). 각 파일 상단에 기존 패턴대로 규약 주석.

4작업 단계

  1. ​profiles.ts에 toPublicProfile(profile) 추가 + 단위 테스트(반환 객체에 sheetId/password 키 자체가 없음을 고정) worker/lib/profiles.ts, worker/lib/profiles.test.ts
  2. ​auth.ts를 resolveProfile(request, env): Promise<Profile | null>로 재작성 — 프로필 배열 참조 기준 다이제스트 캐시, 상수시간 비교·SHA-256 헬퍼 유지, isAuthorized 제거 worker/lib/auth.ts
  3. ​index.ts 배선 — /api/* 게이트를 try/catch로 감싸 ProfileConfigError → 500 + console.error, null → 기존 401, health에 profile 블록(X-Worker-Version은 500에도) worker/index.ts
  4. ​index.test.ts를 폴백 경로 스위트로 개정 — 공용 env에 SHEET_ID 추가, health 응답의 profile(id "default")·비유출 단언 추가, "APP_PASSWORD 미설정 → 401" 테스트는 계약 재정의에 따라 config-error 스위트로 이동 worker/index.test.ts
  5. ​신규 index.profiles.test.ts — 2프로필 PROFILES 구성: 각 비밀번호 → 해당 프로필(health profile.id로 확인), 전 프로필 불일치·무헤더 → 401, 응답 직렬화에 sheetId/password 문자열 미포함 worker/index.profiles.test.ts
  6. ​신규 index.config-error.test.ts — 깨진 PROFILES(JSON 오류·검증 실패)와 전 변수 미설정: /api/* → 500(401 아님) + console.error 호출 + 500에도 X-Worker-Version worker/index.config-error.test.ts
  7. ​전체 검증 — npm test(vitest run)·npm run build(tsc -b 포함)·npm run lint(oxlint) 그린 확인 package.json scripts
