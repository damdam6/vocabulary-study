#118기능 개선

등록 화면 — 탭 선택을 붙여넣기 위로 이동, 새 탭은 생성 버튼으로 먼저 확정

damdam6/vocabulary-study 브랜치 feat/118-register-tab-first-flow ← main 라벨 enhancement 2026-07-28

1요약

등록 화면의 "등록할 탭" 섹션을 스키마 붙여넣기 위로 올려 탭 먼저 → 붙여넣기 순서로 바꾸고, "+ 새 탭"에는 이름 입력란 우측 "생성" 버튼을 붙여 클릭 시 그 이름이 탭 선택지에 추가·선택되게 한다. 실제 구글 시트 탭 생성 시점은 (a) 현행 유지 — 제출 시 createTab을 채택한다: "생성" 버튼은 로컬 선택지 추가·선택 확정만 하므로 빈 탭 방지 결정(word-registration-system §8 Q5)이 유지되고 Worker 변경이 전혀 없다. 이름 타이핑 중(생성 확정 전)에는 제출이 불가능해지며, 검증 게이트·중복 배너·제출 로직은 불변이다.

2현황 분석

등록 화면의 렌더 순서(위→아래)는 src/screens/RegisterScreen.tsx:277-390에서 헤더 → 문제수 필드(:281-309) → 스키마 JSON 붙여넣기 + 확인 버튼(:311-333) → 등록할 탭(:335-356) → 검증 테이블·요약·중복 배너·제출(:362-388)이다. 이슈가 지적한 대로 붙여넣기가 탭 선택보다 위에 있다.

  • 새 탭 상태 모델: 드롭다운 값이 센티널 NEW_TAB_VALUE('__new__')면 새 탭 모드(RegisterScreen.tsx:49,134)다. 이름 입력란(:345-352)에 확정 동작이 없고, effectiveTab = isNewTab ? newTabName.trim() : selectedTab(:135)로 트림된 타이핑 값이 곧바로 대상 탭이 된다 — 이슈의 "입력만 하다 마는 느낌"의 원인.
  • 제출 게이트: canSubmit(:170-176)이 (!isNewTab || newTabError === null)이라 새 탭 모드에서도 이름만 유효하면 제출된다. 이름 선검증은 validateNewTabName(src/lib/registerValidation.ts:167-172) — 트림 후 빈 값·_ 시작 차단.
  • 시트 탭 생성: 제출 시 createTab = isNewTab && !tabs.includes(effectiveTab)(:186)로 플래그만 보내고, 실제 생성은 Worker(worker/routes/register.ts:58-74)가 수행한다. Worker는 wordTabs.includes(targetTab)이면 생성 분기를 건너뛰므로 기존 탭에 createTab: true를 보내도 no-op으로 안전하다.
  • 탭 목록 로딩: fetchTabs 성공 시 첫 탭 자동 선택(:122), 실패 시 드롭다운은 "+ 새 탭" 옵션만 남고 수동 입력 안내 힌트(:340-342)가 뜬다 — 이 폴백은 새 흐름에서도 유지해야 한다.
  • 중복 대조: existingHanziInTab(:143-146)이 effectiveTab 기준으로 재계산되므로 탭이 먼저 확정되는 새 흐름과 정합적이다(이슈 본문 확인 사항).
  • 테스트 현황: src/screens/RegisterScreen.test.tsx는 문제수 필드만 다루고 붙여넣기→탭→제출 흐름 테스트는 없다(파일 머리 주석 :3-6). 새 흐름 테스트는 신규 작성이 필요하다. 드롭다운은 커스텀 리스트박스(src/components/Dropdown.tsx)라 테스트에서 트리거 버튼·옵션 클릭으로 조작한다.
  • 문서: docs/design-prd.md §6 "구성(위→아래)" 불릿과 "새 탭 규칙" 불릿이 현행 순서를 명시한다(:146 절).

3설계

채택: (a) 시트 탭 생성은 현행대로 제출 시 — "생성" 버튼은 클라 로컬에서 선택지 추가·선택 전환만 수행한다. 소유자 체감 요구("생성 후 선택된 채로 붙여넣기")를 충족하면서 §8 Q5(빈 탭 방지) 결정과 Worker 계약이 그대로다. 기각: (b) 버튼 클릭 즉시 Worker 생성 — 빈 탭 위험 감수 + 탭 생성 API 신설이 필요한데 체감 이득이 없다.

  • 로컬 생성 탭 상태 추가: localTabs: string[] state 신설. 드롭다운 옵션은 [...tabs, ...localTabs, '+ 새 탭'](tabOptions 메모 :138-141 확장).
  • "생성" 버튼 핸들러: 트림한 이름이 validateNewTabName 통과 시 — 기존 탭(tabs·localTabs)과 중복이면 그 탭을 선택(추가 없음), 아니면 localTabs에 추가 후 그 이름을 setSelectedTab. 어느 쪽이든 newTabName은 비운다. 버튼은 newTabError !== null이면 비활성(빈 값·_ 시작).
  • 제출 게이트 단순화: canSubmit의 (!isNewTab || newTabError === null)를 !isNewTab으로 교체 — 생성 확정 전(새 탭 모드)에는 무조건 제출 불가. 확정 후에는 selectedTab이 실제 이름이라 기존 경로와 동일.
  • createTab 재계산: 확정 후에는 isNewTab === false가 되므로 기존 식이 깨진다. createTab = !tabs.includes(effectiveTab)(서버 조회 목록 기준)로 교체 — 로컬 생성 탭이면 true, 서버 탭이면 false. 탭 조회 실패 시 tabs = []라 항상 true가 되지만 Worker가 기존 탭이면 no-op이므로 현행과 동일하게 안전(worker/routes/register.ts:58).
  • JSX 순서 이동: 탭 필드 블록(:335-356)을 문제수 필드 바로 아래, textarea 필드 위로 이동. 이름 입력란은 .register-new-tab-row(flex, gap 10px — .register-limit-row 패턴 재사용)로 감싸 우측에 "생성" 버튼 배치.
  • 불변: 확인 버튼 게이트(#55)·effectiveTab 파생식·중복 서명 배너·제출 로직·문제수 필드 독립성. 새 탭 모드 중 타이핑 값 기준 중복 재계산도 유지(제출이 막혀 있어 무해).

4작업 단계

  1. 탭 섹션을 붙여넣기 위로 이동 — 탭 필드 JSX 블록을 문제수 필드와 textarea 필드 사이로 옮기고, 파일 머리 주석의 흐름 서술("붙여넣기 → … → 탭 선택/생성")을 새 순서로 갱신 src/screens/RegisterScreen.tsx
  2. "생성" 버튼 구현 — localTabs state·handleCreateTab 추가(중복이면 기존 탭 선택, 아니면 선택지 추가+선택, 입력란 비움), 이름 입력란을 행 컨테이너로 감싸 우측 버튼 배치, 버튼 비활성 조건은 newTabError !== null src/screens/RegisterScreen.tsx
  3. 제출 게이트·createTab 갱신 — canSubmit에서 새 탭 모드 전면 차단(!isNewTab), handleSubmit의 createTab을 !tabs.includes(effectiveTab)로 교체 src/screens/RegisterScreen.tsx
  4. 스타일 추가 — .register-new-tab-row(flex·gap), .register-new-tab-input에 flex: 1, .register-new-tab-create-button(.register-limit-save-button과 동일 톤: accent 배경·48px·disabled 0.5) src/index.css
  5. 테스트 — 새 describe 블록: ① 탭 섹션이 textarea보다 위(DOM 순서) ② 생성 클릭 → 선택지 추가+선택 상태+입력란 제거 ③ 빈 이름·_ 시작이면 생성 버튼 비활성 ④ 기존 탭과 같은 이름 생성 → 그 탭 선택(선택지 중복 없음) ⑤ 새 탭 모드에서는 확인 완료 후에도 제출 비활성, 생성 확정 후 활성 ⑥ 제출 바디: 로컬 생성 탭이면 createTab: true, 서버 탭이면 미포함. 파일 머리 주석의 범위 서술도 갱신 src/screens/RegisterScreen.test.tsx 추가: jsdom이 scrollIntoView를 구현하지 않아 드롭다운을 여는 테스트가 던짐 — 테스트 파일에 no-op 스텁 1줄 추가(이 레포 첫 드롭다운 열기 DOM 테스트).
  6. design-prd §6 개정 — "구성(위→아래)" 순서 교체(탭 선택이 붙여넣기 앞), "새 탭 규칙" 불릿에 생성 버튼 흐름·제출 차단·시트 생성 시점 유지(Q5) 명시, §9 결정 로그에 탭 생성 시점 재확인 행 추가, §10 이슈 매핑에 #118 행 추가 docs/design-prd.md
  7. 전체 테스트 실행·수동 확인 후 커밋 — npx vitest run 그린 확인, 레포 스타일 커밋 메시지(한국어 요약 + (#118)) 결과: 전체 397 테스트 그린 + tsc -b && vite build·oxlint 통과. 워크트리에 npm ci로 의존성 별도 설치(메인 체크아웃 pnpm 설치본에 jsdom 미링크). src/, docs/

6테스트 계획

  • 신규(화면 순서): 렌더 후 탭 섹션 요소가 textarea보다 DOM 앞순서인지 compareDocumentPosition으로 검증.
  • 신규(생성 흐름): 빈 목록 응답 → 새 탭 모드에서 이름 입력·생성 클릭 → 드롭다운 선택값이 그 이름, 입력란 사라짐, 다시 "+ 새 탭" 진입 시 선택지에 남아 있음.
  • 신규(선검증): 빈 이름·공백만·_ 시작 → 생성 버튼 비활성 + 오류 문구. 기존 탭(['HSK6'] 응답)과 같은 이름 → 그 탭 선택 전환, 옵션 중복 추가 없음.
  • 신규(제출 게이트): 유효 JSON 붙여넣기·확인까지 마쳐도 새 탭 모드면 제출 버튼 비활성 → 생성 클릭 후 활성. 제출 시 registerWords 바디에 로컬 생성 탭이면 createTab: true 포함, 서버 탭 선택이면 미포함.
  • 회귀: 기존 문제수 필드 테스트 6건(RegisterScreen.test.tsx)·검증 로직(registerValidation.test.ts)·API(registerApi.test.ts)·Worker(worker/**/*.test.ts) 전체 그린 — npx vitest run.

7완료 조건

  • 화면 순서: 등록할 탭 섹션이 스키마 붙여넣기보다 위 (문제수 필드 → 탭 → 붙여넣기+확인 → 테이블 → 제출)
  • "+ 새 탭" 이름 입력란 우측 "생성" 버튼 — 클릭 시 선택지 추가 + 선택 상태 전환, 트림·_ 차단·기존 탭 중복 시 그 탭 선택 유지
  • 생성 확정 전(새 탭 모드)에는 제출 불가, 확정 후 붙여넣기→확인→제출 흐름 정상 (createTab은 서버 목록 기준으로 정확)
  • 기존 등록 검증·중복 배너·제출 게이트 로직 불변, 신규 흐름 테스트 추가 + 전체 테스트 통과
  • design-prd §6 구성 순서·새 탭 규칙 개정, §9 결정 로그·§10 이슈 매핑 갱신
  • Worker 변경 없음 — (a) 채택으로 클라 전용 (§8 Q5 빈 탭 방지 결정 유지)
