등록 일반화 — 영어 추출 킷 신설 + schema_check 두 스키마 겸용 + 등록 문서 개정

1요약

등록 일반화 플랜(docs/plans/registration-generalization.md) §5 작업 A — 킷·문서 담당. 영어 추출 킷 en-extraction-prompt.md를 신설해 "언어별 프롬프트" 패턴(플랜 §8 Q5)의 첫 사례를 만들고, schema_check.py를 최상위 contentType 필드로 zh·generic 두 스키마를 겸용 판별하도록 확장한다. 나머지는 문서 정합화 — 기존 zh 프롬프트에 sibling 포인터, PRD-general의 낡은 "generic 등록은 시트 직접 편집" 서술 개정, word-registration-system 머리에 스키마 원본 분담 포인터.

src/·worker/ 코드는 한 줄도 건드리지 않는다. 작업 B(Worker)·C(화면)와 의존 없이 병렬이며, 이 작업 단독 머지로 사용자 가시 변화는 없다(킷은 리포 밖 claude.ai 프로젝트에 수동 업로드되는 산출물).

2현황 분석

추출 킷은 중국어 전용 1벌뿐이다. docs/registration-kit/에는 두 파일만 있다.

  • docs/registration-kit/extraction-prompt.md:20 — 제목이 "Chinese Vocabulary Extractor". 규칙 절(:29-48)이 hanzi(간체 강제·번체 변환)·pinyin(성조 부호·다음자)·meaning(한국어)로 짜여 있고, 출력 스키마 블록(:54-61)은 contentType 없는 zh 형태다. 헤더 HTML 주석(:1-18)이 claude.ai 프로젝트 세팅 절차와 "스키마 원본 = word-registration-system §3"을 명시한다 — 신설 영어 킷이 그대로 따를 구조.
  • docs/registration-kit/schema_check.py — zh 스키마 단일 검증기. check_word()(:47-94)가 hanzi/pinyin/meaning 3필드 필수(:59-63), 여분 필드 거부(:65-67), 한자 기본 블록 범위(:69-72, HANZI_RANGES :34), 성조 부호 형식(:74-88), 배치 내 hanzi 중복(:90-94)을 검사한다. main()(:103-140)은 version == 1과 words 배열만 최상위에서 보고, 최상위 여분 필드는 무시한다 — 즉 지금도 contentType이 섞인 JSON은 조용히 zh로 검사된다.

문서 3건이 플랜 확정(2026-07-27) 이전 상태로 남아 있다.

  • docs/PRD-general.md:138 (§5.2) — POST /api/words/register를 "계약 불변이며 대상 스프레드시트만 프로필로 결정된다"로 분류. 플랜 §3.3이 와이어 형태는 유지하되 Worker 검증을 profile.contentType으로 분기하고 탭 0개 부트스트랩을 추가하기로 확정했으므로 "언급 없음 = 완전 불변"은 더 이상 사실이 아니다.
  • docs/PRD-general.md:166 (§7 단어 등록) — "contentType: "zh" 프로필에만 홈 진입 링크를 노출한다 … generic 프로필의 단어 추가는 구글 시트 직접 편집으로 한다 … 후속 플랜으로 분리한다". 플랜 §3.4·§9가 전 프로필 노출로 뒤집었다.
  • docs/PRD-general.md:193 (§10 Q4) — "등록 화면 자체의 일반화는 후속 플랜으로 분리". 그 후속 플랜이 2026-07-27 확정됐으므로 결론에 실행 사실과 포인터가 필요하다.
  • docs/PRD-general.md:217 (§11 결정 이력) — "generic 등록 = 시트 직접 편집, 등록 링크는 zh 전용" 행. §7을 고치면 이 행과 문서 내부에서 모순된다.
  • docs/plans/word-registration-system.md:33-47 (§3) — zh 스키마의 원본이지만 "generic 스키마는 다른 문서"라는 안내가 없다. 반대편(registration-generalization.md:46)은 이미 분담을 명시하고 있어 링크가 한쪽 방향으로만 걸려 있다.

테스트 인프라: 리포의 npm test는 vitest(TS)뿐이고 파이썬 테스트 하네스는 없다(schema_check.py가 리포 유일 .py). 검증기의 소비자는 claude.ai 코드 실행 샌드박스이므로 표준 라이브러리 전용 제약도 유지해야 한다(schema_check.py:18-20).

3설계

스키마 판별 규칙 (schema_check.py). 최상위 contentType을 읽어 검사기를 고른다.

contentType동작근거
필드 없음zh 검사 (현행 그대로)기존 킷 출력 하위 호환 — 플랜 §3.1 "필드 없음 = zh"
"zh"zh 검사지금도 최상위 여분 필드는 무시돼 PASS하므로 명시 표기를 새로 막지 않는다 (zh 결과 불변)
"generic"generic 검사플랜 §3.1
그 외 값·비문자열FAIL (알 수 없는 contentType)zh도 generic도 아닌 문서를 조용히 zh로 검사하면 오독성 오류가 난다

generic 항목 검사 (플랜 §3.1·§3.2): term 비공백 문자열(범위 제한 없음 — 공백·문장부호·한자 혼입 허용), meaning 비공백 문자열, note는 선택(생략 가능, 있으면 문자열이면 되고 빈 문자열도 허용 → B열 빈칸), {term, note, meaning} 외 여분 필드 거부, 배치 내 term 중복 거부. zh 전용 검사(한자 유니코드 범위·성조 부호)는 적용하지 않는다.

중복 판정은 트림 후 비교한다 — generic term은 공백을 포함하는 자유 텍스트라 앞뒤 공백 변형이 실제로 생기고, Worker가 hanzi.trim() 기준으로 배치 중복을 잡는다(worker/lib/register.ts:60,67). 대소문자는 구분한다(플랜 §8 Q4 — 시트 중복 판정과 같은 방침). zh 경로의 중복 비교는 손대지 않는다(한자에 공백이 못 들어와 트림 여부가 결과에 무관).

구조: check_word()를 check_word_zh()로 개명하고 check_word_generic()을 추가, main()이 판별 후 디스패치한다. PASS/FAIL 출력 문자열과 종료 코드는 현행 유지 — zh 입력의 stdout이 한 글자도 달라지지 않게 해서 "zh 동작 불변"을 관측 가능한 형태로 보장한다. (검사한 스키마 이름을 PASS 줄에 덧붙이는 안은 기각: 유용성은 작은데 zh 출력이 바뀐다. 오배치는 어차피 FAIL로 잡힌다.)

영어 킷은 별도 파일, 검증기는 공용. 프롬프트는 언어 의존(영어 숙어·구동사 인식, 발음기호 처리)이라 언어별로 분리하고, 스키마는 콘텐츠 중립(term/note/meaning)이라 검증기는 한 파일이 두 스키마를 겸한다 — 플랜 §8 Q5·§9의 소유자 확정. 운영상 claude.ai 프로젝트마다 프롬프트만 다르고 같은 schema_check.py를 올린다.

PRD-general 개정 원칙. 개별 문장을 지우지 않고 2026-07-27 개정 노트 + 플랜 포인터를 붙여 결정이 바뀐 사실을 남긴다(§11 결정 이력이 존재하는 문서 관행). §11의 낡은 결정 행에도 "→ 2026-07-27 개정" 한 줄을 더한다 — 이슈 본문이 명시한 §5.2·§7·§10 Q4에는 없지만, 이 행을 그대로 두면 §7과 정면으로 모순되므로 같은 개정의 일부로 처리한다.

구현 상태 표기. PRD는 확정된 사양을 서술하되, 링크 전 프로필 노출과 검증 분기는 아직 코드에 없다(플랜 §5 작업 B~D). 개정 노트에 "구현은 플랜 §5 작업 B~D"를 병기해 문서가 현실을 앞질러 거짓말하지 않게 한다.

4작업 단계

  1. en-extraction-prompt.md 신설 — zh 킷과 동형 구조(헤더 HTML 주석에 claude.ai 프로젝트 세팅 절차·스키마 원본 = registration-generalization §3.1·sibling 포인터 / # English Vocabulary Extractor / 추출 규칙 / 출력 형식 / 자체 검증 / Never). 규칙은 영어 단어·표현·숙어 추출, note는 원문 근거 있을 때만(발음기호·품사 등), meaning은 한국어 간결, 배치 내 term 중복 금지, 출력은 contentType: "generic" JSON 코드블록 하나. 시트·자격증명 무지 원칙 유지. docs/registration-kit/en-extraction-prompt.md (신규)
  2. schema_check.py 두 스키마 겸용 확장 — 모듈 docstring에 두 스키마와 각 원본 문서 표기, check_word() → check_word_zh() 개명, check_word_generic() 추가(§3 규칙), main()에 contentType 판별·디스패치·알 수 없는 값 FAIL. 표준 라이브러리 전용·종료 코드·출력 문자열 유지. docs/registration-kit/schema_check.py 디스패치는 resolve_checker()로 분리했고, contentType: null(명시적 JSON null)도 "알 수 없는 값"으로 FAIL 처리한다 — data.get("contentType", "zh")가 키 부재와 null을 구분하기 때문.
  3. 검증 픽스처로 두 스키마 실행 확인 — zh PASS/FAIL 각 케이스(정상·한자 범위 위반·숫자 성조·중복)와 generic 케이스(정상·note 생략·note 빈 문자열·term 빈값·meaning 누락·term 중복·여분 필드·zh 규칙 미적용·알 수 없는 contentType)를 스크래치패드 픽스처로 돌려 기대 종료 코드와 메시지를 확인한다. 리포에 파이썬 테스트 하네스가 없고 킷은 claude.ai 프로젝트에 통째로 업로드되는 산출물이라 픽스처는 커밋하지 않는다(업로드 대상 오염 방지) — 실행 결과는 PR 본문에 남긴다. 스크래치패드 (커밋 없음) 실행 결과: zh 픽스처 4종은 origin/main 버전과 stdout·종료 코드가 완전 동일(문자열 대조), generic 10종·디스패치 6종 전부 기대대로. 상세는 PR 본문.

6테스트 계획

  • zh 회귀 (결과 불변 증명) — 확장 전 schema_check.py와 확장 후 파일에 같은 픽스처를 넣어 stdout·종료 코드가 동일한지 대조: ① 정상 zh JSON → PASS: N word(s) validated. / exit 0, ② hanzi에 라틴 문자 → 비CJK 오류 / exit 1, ③ pinyin이 jing1ji4 → 숫자 성조 오류 / exit 1, ④ 같은 hanzi 2회 → 중복 오류 / exit 1.
  • generic PASS — 플랜 §3.1 예시 JSON(take off + note, run into note 생략) → exit 0. note: ""(빈 문자열)도 exit 0.
  • generic FAIL — term 공백만/누락, meaning 누락·빈값, 배치 내 term 중복(앞뒤 공백 변형 포함), {term,note,meaning} 외 여분 필드(hanzi 등), version ≠ 1, words 빈 배열 → 각각 exit 1 + 해당 행·사유가 메시지에 표시.
  • zh 규칙 미적용 확인 — generic JSON에 term: "take off"(공백·라틴), note: "/teɪk ɒf/"(성조 없음·특수문자) → PASS. 역으로 같은 값이 zh 스키마에 오면 FAIL.
  • 스키마 판별 — contentType 없음 → zh 검사(generic 필드 JSON을 넣으면 hanzi 누락으로 FAIL), contentType: "zh" → zh 검사, contentType: "en"·숫자 → 알 수 없는 contentType FAIL.
  • 코드 블록 래핑 내성 — generic JSON을 ```json … ```으로 감싼 입력도 동일하게 PASS(strip_code_fence 경로가 두 스키마에 공통 적용되는지).
  • 리포 회귀 — npm test(vitest 전량) · npm run build · npm run lint 통과, git diff --stat origin/main에 src/·worker/ 항목 0건.
