#74기능 개선

POST /api/answer 프로필 대응 — 비활성 모드 400 + 졸업 판정 활성 모드 집합(M) 파라미터화

damdam6/vocabulary-study 브랜치 feat/74-answer-profile-modes ← main 라벨 enhancement 2026-07-27

1요약

computeAnswerUpdate의 졸업 판정이 m1 >= 3 && m2 >= 3으로 하드코딩돼 있어, 단일 모드 프로필(M={m1} 등)에서 비활성 모드 카운트 때문에 영원히 졸업하지 못한다. 또한 POST /api/answer 라우트는 요청 mode가 프로필의 활성 모드 집합에 속하는지 전혀 검사하지 않는다. 이번 작업은 computeAnswerUpdate에 활성 모드 집합 modes 인자를 추가해 졸업 판정을 M 기준으로 일반화하고, 라우트에 "mode ∉ profile.modes → 400, 시트 쓰기 없음" 방어선을 배선한다. M={m1,m2}일 때는 인자 추가만으로 기존 동작이 완전히 보존돼야 한다.

2현황 분석

worker/lib/answer.ts:53-74의 computeAnswerUpdate(current, mode, isReview, now)는 순수 계산 함수(시트 I/O 없음)로, wasGraduated/justGraduated를 current.m1 >= 3 && current.m2 >= 3으로 하드코딩 판정한다(worker/lib/answer.ts:59,68). 복습(isReview) 분기는 졸업 여부와 무관하게 간격 사다리(nextLadderInterval)만 적용하므로 이번 변경의 영향 밖이다.

worker/routes/answer.ts:38-92의 handleAnswerPost는 요청 바디를 parseAnswerRequest로 파싱한 뒤(mode는 "m1"|"m2"인지만 확인, worker/routes/answer.ts:32) 곧바로 findRowNumber로 시트를 조회한다 — 프로필의 활성 모드 집합과의 교차 검증이 전혀 없다. 시그니처에 profile: Profile이 이미 들어와 있으므로(worker/routes/answer.ts:38-42, #73에서 배선 완료) profile.modes는 이미 핸들러 안에서 접근 가능하다.

worker/lib/profiles.ts:9,22에 QuizMode = "m1" | "m2"와 Profile.modes: QuizMode[]가 이미 정의돼 있다 — answer.ts의 AnswerMode(worker/lib/answer.ts:9)와 구조적으로 동일한 타입이라 별도 import 없이 구조적 호환이 된다.

같은 파라미터화 패턴이 이미 클라이언트 쪽에서 두 번 적용됐다: src/lib/wordState.ts:40의 getWordState(word, today, modes)는 modes.some((mode) => word[mode] < 3)로 "학습 중"을 판정하고(#75), src/lib/sessionQueue.ts의 buildSessionQueue는 출제 모드를 M으로 제한한다(#76). 두 커밋 모두 it.each로 "M={m1,m2} 기존 동작 보존" / "M={m1}" / "M={m2}" 세 describe 블록을 나누는 테스트 스타일을 확립했다 (src/lib/wordState.test.ts:6-45) — 이번 작업의 worker/lib/answer.test.ts도 같은 스타일을 따른다.

worker/lib/answer.ts·worker/routes/answer.ts에는 현재 자동 테스트가 전혀 없다(#8 구현 당시 임시 _test 탭으로 실제 시트에 수동 왕복 검증만 했다 — 커밋 8b87fa8 메시지). 반면 같은 성격의 파서/라우트 파일(worker/lib/profiles.test.ts, worker/routes/register.test.ts, worker/index.profiles.test.ts)은 vitest로 자동화돼 있다. 이번 이슈는 졸업 판정처럼 회귀 위험이 큰 로직을 건드리므로, 기존 관례(수동 검증)보다 최근 M-파라미터화 이슈들의 관례(자동 테스트 신설)를 따르는 것이 안전하다.

3설계

채택: computeAnswerUpdate에 5번째 인자 modes: AnswerMode[]를 추가하고, wasGraduated/justGraduated 계산을 current.m1 >= 3 && current.m2 >= 3 하드코딩 대신 로컬 헬퍼 graduated(m1, m2) => modes.every((m) => (m === "m1" ? m1 : m2) >= 3)로 대체한다. modes=["m1","m2"]를 넘기면 산술적으로 기존 식과 완전히 동일해 회귀가 없다. MODE_COLUMN·간격 사다리·G열 append 로직은 건드리지 않는다.

기각: Record<AnswerMode, boolean> 형태의 맵을 만들어 순회하는 방식 — 모드가 2개뿐인 현재 도메인에서 삼항 분기보다 코드가 늘어나고 가독성 이득이 없다. 별도 타입 QuizMode를 answer.ts에 import하는 방식도 검토했으나, AnswerMode와 구조적으로 동일한 유니언이라(둘 다 "m1" | "m2") TypeScript가 구조적 타이핑으로 profile.modes(QuizMode[])를 AnswerMode[] 매개변수에 그대로 전달받을 수 있다 — 불필요한 교차 모듈 import를 만들지 않는다.

라우트 400 검사 위치: parseAnswerRequest 성공 직후, findRowNumber 호출(첫 시트 I/O) 이전에 if (!profile.modes.includes(answer.mode)) 가드를 둔다 — 완료 조건이 요구하는 "시트 쓰기 없음"을 넘어 어떤 시트 호출도 만들지 않아 더 강한 보장이면서 구현도 더 단순하다.

4작업 단계

  1. computeAnswerUpdate에 modes: AnswerMode[] 인자를 추가하고, 졸업 판정을 로컬 graduated() 헬퍼로 교체한다. JSDoc 주석에 M 기준 판정임을 한 줄 추가한다. worker/lib/answer.ts
  2. worker/lib/answer.test.ts 신설 — describe 3블록(M={m1,m2} 기존 동작 보존 / M={m1} / M={m2}), it.each로 학습 중·첫 졸업(경계값 포함)·복습 사다리 진행· 비졸업 정답(F열 미변경, nextReviewChanged: false) 케이스를 검증한다. M={m1} 블록은 "E열 값과 무관하게 D열 3회째 졸업"을, M={m2} 블록은 대칭 케이스를 명시적으로 포함한다. worker/lib/answer.test.ts
  3. handleAnswerPost에 profile.modes.includes(answer.mode) 가드를 findRowNumber 호출 이전에 추가 — 불일치 시 400과 함께 어떤 시트 호출도 만들지 않고 즉시 반환한다. computeAnswerUpdate 호출부에 profile.modes를 전달하도록 갱신한다. worker/routes/answer.ts
  4. worker/routes/answer.test.ts 신설 — register.test.ts와 동일한 방식으로 google-auth.ts를 모킹하고 Sheets API를 흉내 내는 stubSheetsFetch를 작성한다(단, answer.ts가 쓰는 A2:A/{row}:{row} GET 범위와 /values:batchUpdate POST 범위 어휘에 맞춘 새 구현). PROFILES 2프로필 (M={m1} 단일 프로필 + M={m1,m2} 프로필)로 다음을 검증한다: (a) M={m1} 프로필에 mode: "m2" 요청 → 400, batchUpdate 호출 0회, (b) M={m1} 프로필에서 D열 3번째 정답 → 200 + F열 내일|1 기록, (c) M={m1,m2} 프로필의 학습 중·졸업·복습·G열 append가 응답 단어 객체 형태까지 포함해 회귀 없이 통과. worker/routes/answer.test.ts
  5. npm test(vitest 전체)와 npm run build(tsc 타입체크 포함)를 실행해 회귀가 없는지 확인한다. 전체 246개 테스트(23 파일) 통과, tsc/vite 빌드 성공, oxlint 클린.

5리스크

리스크영향완화책
졸업 판정 리팩토링이 M={m1,m2} 기존 동작을 미묘하게 바꿈 이미 졸업한 단어의 F열이 잘못 갱신되거나 정상 학습자의 졸업이 지연됨 graduated()가 m1>=3 && m2>=3과 산술적으로 동치임을 단위 테스트의 "M={m1,m2} 기존 동작 보존" 블록으로 고정
400 가드 위치가 늦어 비활성 모드 요청도 시트를 읽어버림 완료 조건("시트 쓰기 없음")은 지키지만 불필요한 Sheets API 호출 낭비 가드를 findRowNumber 호출보다 먼저 배치 — 읽기까지 포함해 0회 호출 보장, 라우트 테스트에서 batchUpdate/GET 모두 0회임을 확인
라우트 테스트용 Sheets 목이 실제 batchUpdateValues의 URL/바디 형태 (/values:batchUpdate, data: [{range: "'tab'!D3", values}])와 어긋나면 테스트가 거짓 통과함 회귀를 못 잡는 테스트 구현 중 worker/lib/sheets.ts의 batchUpdateValues·encodeRange· fullRange 실제 구현을 그대로 따라 목을 작성하고, 목이 파싱한 range를 상태에 반영한 뒤 응답 바디로 재확인

6테스트 계획

  • npm test — 신설 worker/lib/answer.test.ts·worker/routes/answer.test.ts 포함 전체 vitest 스위트 통과.
