#113버그 수정

세션 문제 수 설정이 재삽입 상한에 미적용 — 35 설정에도 세션이 60까지 커진다

damdam6/vocabulary-study 브랜치 fix/113-requeue-cap-session-limit ← main 라벨 bug 2026-07-28

1요약

시트별 "1회 문제 수" 설정(_정보 탭 문제수)은 초기 큐 구성과 홈 집계에는 반영되지만, 학습 중 오답의 재삽입 상한에는 반영되지 않는다 — 그 조건이 고정 상수 SESSION_CAP(60)을 그대로 쓰기 때문이다. 그래서 35로 설정해도 오답이 쌓이면 진행도 분모가 60까지 자란다. 수정은 세션의 limit을 StudySessionState에 실어 recordAnswer가 그 값으로 판정하게 하고, 홈이 이미 들고 있는 sessionLimit을 큐와 함께 학습 화면까지 스레딩하는 것이다. Worker는 건드리지 않는다.

2현황 분석

세션 상한 limit이 흐르는 경로는 현재 세 갈래이고, 그중 두 갈래만 #106에서 파라미터화됐다.

  • ① 초기 큐 구성 — 반영됨. src/lib/sessionQueue.ts:36 buildSessionQueue(words, today, modes, rng, limit = SESSION_CAP)가 복습 대기 컷(:57 .slice(0, limit))과 총 상한(:67 learningQuestions.slice(0, limit - reviewQuestions.length))에 모두 limit을 쓴다.
  • ② 홈 집계 — 반영됨. src/lib/homeStats.ts:25의 limit 인자로 :46 sessionCount를 산출한다. 그래서 홈의 "오늘 세션 · 35문제" 표시는 정상이다.
  • ③ 학습 중 오답 재삽입 상한 — 누락. src/lib/studySession.ts:85의 조건이 state.queue.length < SESSION_CAP — 임포트된 고정 상수 60이다. 세션이 아는 limit이 없어서 참조할 값 자체가 없다.

스레딩 배선의 현재 상태 — limit은 홈까지만 도달하고 학습 화면으로 넘어가지 않는다.

  • src/screens/HomeScreen.tsx:32가 sessionLimit 상태를 갖고 :46에서 fetchWords의 settings.sessionLimit으로 채운다 — 값은 이미 홈에 있다.
  • src/screens/HomeScreen.tsx:84 onStart(buildSessionQueue(..., sessionLimit)) — 큐만 올리고 limit은 버린다.
  • src/App.tsx:52 startSession(queue)가 sessionQueue 상태만 두고, :81에서 StudyScreen에 queue만 내린다.
  • src/screens/StudyScreen.tsx:46 useState(() => startSession(queue)) — 세션 시작 시점에 limit을 모른다.

진행도 분모는 src/screens/StudyScreen.tsx:127의 session.queue.length라, 재삽입이 곧 분모 증가로 즉시 보인다(실측 38 → 57).

3원인 분석

근본 원인: #106이 "세션 총 상한은 전부 같은 limit을 쓴다"(세션 설정 플랜 §3.2)를 구현하면서 sessionQueue·homeStats 두 사용처만 인자화하고, 세 번째 사용처인 studySession.recordAnswer의 재삽입 상한을 놓쳤다. 근거는 src/lib/studySession.ts:9가 여전히 SESSION_CAP을 값으로 임포트해 :85에서 비교에 쓰는 것 하나로 충분하다 — 이 파일에는 limit이 도달할 통로가 아예 없다.

설계 (이슈 본문에서 확정된 방향):

  • startSession(questions, limit = SESSION_CAP) — limit을 StudySessionState.limit으로 보관한다. 세션은 시작 시점에 상한을 확정하며(세션 설정 플랜 §3.2 "진행 중인 세션에는 영향 없다"와 같은 성질), recordAnswer는 state.queue.length < state.limit으로 판정한다.
  • 기본값을 둬 v1 경로를 보존한다 — 인자를 생략하면 60이라 기존 studySession.test.ts는 한 줄도 고치지 않고 통과해야 한다. sessionQueue·homeStats가 이미 쓰는 것과 같은 관례라 파일 간 일관성도 유지된다.
  • 경계 의미론은 현행과 동일 — < 비교라 초기 34 + 재삽입 1 = 35는 허용, 이미 35면 재삽입 생략. 세션 총 문제 수가 설정값을 절대 넘지 않는 것이 계약이다.
  • limit 도달로 재삽입이 생략된 단어는 상태가 그대로 "학습 중"이라 다음 세션에 자연 재출제된다 — v1에서 60 도달 시와 같은 의미론이라 별도 보상 로직이 없다.

배제한 대안:

  • 모듈 전역에 limit을 세팅 — studySession은 vitest node 환경의 순수 모듈(파일 헤더 주석의 설계 의도)이라 전역 가변 상태는 그 성질을 깬다.
  • recordAnswer(state, isCorrect, limit)로 호출부마다 전달 — 상한은 세션의 성질이지 판정 1회의 성질이 아니다. 호출부(StudyScreen)가 매번 같은 값을 되먹여야 해 불일치 여지가 생긴다.
  • 큐 길이로 역산(초기 queue.length를 상한으로) — 초기 큐가 limit보다 짧은 경우(단어 부족)에 상한이 잘못 좁아진다. 35 설정·초기 12문제면 재삽입이 전면 금지돼 버린다.

4작업 단계

  1. studySession에 세션 limit 도입 — StudySessionState에 limit 필드 추가, startSession(questions, limit = SESSION_CAP)으로 시그니처 확장, recordAnswer의 재삽입 조건을 state.queue.length < state.limit으로 교체. :82의 "60문제 상한 내" 주석도 설정값 기준으로 개정. src/lib/studySession.ts
  2. 회귀 테스트 추가 — limit 35 세션에서 오답이 반복돼도 queue.length가 35를 넘지 않음(경계: 34 → 재삽입 1회 허용해 35, 35면 생략), 그리고 limit 미전달 시 기존 SESSION_CAP 동작 유지. 기존 테스트는 수정하지 않는다 — 무수정 통과가 v1 보존의 증거다. src/lib/studySession.test.ts
  3. 홈 → App 배선 — onStart 시그니처를 (queue, limit)로 넓히고 handleStart가 sessionLimit을 함께 올린다. App은 sessionLimit 상태를 추가해 보관. src/screens/HomeScreen.tsx, src/App.tsx
  4. App → StudyScreen 배선 — StudyScreenProps에 limit 추가, useState(() => startSession(queue, limit))로 세션 생성 시 전달. src/App.tsx, src/screens/StudyScreen.tsx
  5. 스레딩 회귀 테스트 — fetchWords가 settings.sessionLimit: 35를 주는 홈에서 "학습 시작"을 누르면 onStart가 두 번째 인자로 35를 받는지 검증(현 테스트는 onStart 인자를 보지 않는다). src/screens/HomeScreen.test.tsx
  6. PRD §6.2 개정 — 재삽입 문구의 "(§6.1 상한 내에서)"를 설정 기반 상한(시트 설정, 기본 60)으로 명시하도록 개정. §6.1은 #106에서 이미 개정됐으므로 손대지 않는다. docs/PRD.md 실제 원문은 이슈가 인용한 "60문제 상한 내"가 아니라 "(§6.1 상한 내에서)"였다 — 같은 취지로, 상한이 시트 `문제수` 설정(기본 60)임과 상한 도달 시 다음 세션 재출제 의미론을 명시하도록 개정했다.
  7. 전체 검증 — npm test, npm run lint, npm run build(tsc 타입 체크 포함) 그린 확인. Worker 디렉터리 무변경 확인. worker/ (변경 없음 확인) 워크트리의 node_modules가 비어 있어 jsdom 해석에 실패 → pnpm install 1회 실행(레포 표준 의존성 그대로, package.json 무변경). 생성된 pnpm-lock.yaml은 로컬 산출물이라 커밋하지 않는다.

5리스크

리스크영향완화책
StudySessionState에 필수 필드가 늘어 기존 상태 리터럴이 깨진다 테스트·호출부 타입 에러 상태는 항상 startSession으로만 만들어진다(테스트 포함 — studySession.test.ts:37 sessionAt). 기본값 인자라 호출부 무수정. tsc -b로 확인.
onStart 시그니처 확장이 다른 호출부를 깬다 홈 테스트/타입 에러 호출부는 App.tsx 하나, 테스트의 vi.fn()은 인자 수에 무관. 확장(추가 인자)이라 기존 assertion도 유효.
limit 도달 시 재삽입이 생략돼 오답 단어가 그 세션에 다시 안 나온다 사용자 체감 변화 의도된 계약이다(이슈 기대 동작). 단어 상태는 "학습 중" 그대로라 다음 세션에 재출제 — v1의 60 도달 시와 동일 의미론.
설정값이 초기 큐보다 작거나 큰 비정상 조합 경계 동작 혼선 Worker가 1~500·비정상 시 60 폴백을 이미 강제(세션 설정 플랜 §3.1). 클라는 받은 값을 그대로 상한으로 쓰고 < 비교라 초기 큐가 limit 이상이면 자연히 재삽입 0.

6테스트 계획

  • 회귀(핵심): limit 35 · 학습 중 문제 35개 큐에서 연속 오답을 내도 queue.length가 35를 유지 — 재삽입이 한 건도 일어나지 않는다.
  • 경계: limit 35 · 초기 34개 큐에서 학습 중 오답 1건 → 35로 증가(허용), 그 상태에서 또 다른 원본 오답 → 35 유지(생략).
  • v1 보존: 기존 src/lib/studySession.test.ts 전체가 무수정 통과 — 특히 "큐가 SESSION_CAP이면 재삽입하지 않는다"(:141)가 limit 미전달 경로로 그대로 성립.
  • 불변식: "재삽입은 1회만"(requeued 플래그) 규칙이 limit 도입 후에도 유지 — 기존 :130 테스트로 커버.
  • 스레딩: HomeScreen.test.tsx에서 settings.sessionLimit: 35 응답 + 학습 중 단어로 "학습 시작" 클릭 → onStart가 (큐, 35)로 호출.
  • 전체: npm test(vitest 전체) · npm run lint(oxlint) · npm run build(tsc -b + vite build) 모두 그린.
  • 범위 확인: git status/git diff --stat에 worker/ 변경이 없음.
